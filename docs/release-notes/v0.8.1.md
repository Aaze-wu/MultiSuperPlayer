# v0.8.1 封面增强

发布日期：2026-10-04
基于版本：v0.8.0-alpha.2

---

## 一、这一版做了什么

列表、网格、播放页开始显示封面。取图分两条**完全不同**的路：

| 类型 | 第一优先 | 第二优先 |
| --- | --- | --- |
| 音频 | 内嵌封面（Android 10+ 上先问系统媒体库要缩略图） | 文件里内嵌的那张图 |
| 视频 | 容器里内嵌的封面 | 在时间轴上抽一帧 |

外加一条兜底：**取不到图时垫在底下的类型图标仍然是那个颜色**，所以
「能播 / 是字幕 / 其它」三态一眼可辨（见第五节）。

顺手修掉一个真问题：内置文件选择器里**可播放但没有封面的文件**原来显示成灰色图标，
和不能播的文件一模一样（见第六节）。

---

## 二、抽哪一帧：10% 是启发式，不是常数

### 为什么不是第 0 秒

片头那几秒通常是黑场、淡入或者台标：抽出来要么是一张纯黑图，要么是一帧写着
发行公司名字的画面，两者都不能回答「这是哪一片」。所以第一个候选点是**时长的 10%**。

### 为什么太暗要重试，而「全都暗」时仍然画

算一下这一帧的平均亮度（Rec.709 加权后除以 255），低于 `0.12` 就退到**时长的 40%** 再抽一次。
两个数的分工是有理由的：0.12 偏保守——真正全黑的帧在 0.02 上下，夜景画面大概 0.05~0.15，
有内容的画面普遍高于 0.2——所以只会「只有真的很黑才重试」，代价是多抽一帧。
第二个点取 40% 而不是 20%：开场附近往往**整段**都是黑的（黑底字幕、渐入黑场），
只往后挪 10% 很容易落回同一段黑。

**两个候选都太暗时，返回最后那**一张，而不是返回空。这是刻意的取舍：

- 一张黑封面至少还能让人认出「哦这是那部黑底的片子」；
- 什么都不画等于退回类型图标，而用户分不出「这个功能没生效」和「这片子没有封面」，
  只会认为封面功能坏了。

代价是**本身就是黑底的素材**（纯语音录制、纯音频画面）会得到一张几乎全黑的封面——
这是这条规则的第一后果，写进「已知限制」了，不是漏掉的 bug。

### 为什么不做「不超过 N 秒」的封顶

3 小时的视频意味着第一个候选在 18 分钟处。直觉会想给它加个「最多 30 秒」的上限，
但那样抽出来的就**不是**「这片子 10% 处」了：对一集 45 分钟的剧，18 分钟处很可能还在
正片开头，而 30 秒处大概率还是黑场或台标——正是要躲开的东西。
抽帧用的是 `OPTION_CLOSEST_SYNC`（跳到最近的关键帧），对本地文件是毫秒级的 seek，
不必为它牺牲取景位置。

## 三、为什么让系统缩，也不先拿整帧

4K 视频的一整帧是 33MB。如果先 `getFrameAtTime` 拿全尺寸、再自己缩到 512，
那 33MB 是**真真切切要分配出来的**——列表滚动时每行来一次，OOM 只是时间问题。
所以 API 27+ 走 `getScaledFrameAtTime`，让系统在解码器里直接出小图
（目标尺寸按视频自己的宽高算出「长边不超过 512」）。低版本、拿不到视频尺寸、
或者缩放抽帧失败时才退回全尺寸那一版——**能出图比出小图重要**。

算平均亮度这一步也是同样的思路：把帧缩到 **16×16** 再求均值，而不是逐像素遍历
一张 1080p（200 万次循环 + 8MB 的 `IntArray`）。这里只想知道「它是不是黑的」，
16×16 的均值足够回答这个问题，而且缩放的代价反而盖过了采样的代价。

抽出来的图统一按 512 长边压成 JPEG（质量 88，缩略图性质，看不出压缩痕迹）再落盘。

## 四、缓存：自己写一份，而且键要带类型

图取到之后写进应用私有目录的 `cache/artwork/`，磁盘文件名不是 uri 本身，而是
`类型 + uri 两次哈希`。两个细节都是必要的：

- **带类型**：同一个文件在不同判定下可能既是音频又是视频，键里不带类型就会互相顶掉；
- **两次哈希而不是直接拼 uri**：uri 里有 `/`、`:`、`?`，直接当文件名在部分机型上
  会静默失败；取 `hashCode` 的正反两次拼起来，撞车概率可以忽略，长度也固定。

写入是**先写临时文件再改名**（`promoteAtomically`）。半写的文件比没有文件更糟：
它在缓存目录里长得和正常缓存一模一样，下次读到的就是一张截断的图。
读取前还要过一道 `cacheFileIsUsable`（存在、非 0 字节），0 字节的文件一律当没有。

**Coil 自带的磁盘缓存被显式关掉了**（`.diskCache(null)`）。我们自己已经落了一份
512 长边的 JPEG，让 Coil 再缓存一份同样的字节只会让磁盘占用翻倍，而且两份缓存
谁也不清谁。内存缓存留着——列表滚回去不重新解码靠的就是它。

同时最多允许 2 个解码任务（`Semaphore(2)`）。抽帧是 CPU 密集且会分配大块内存的操作，
不设上限的话「快速划过一屏视频」就是一次自制的 OOM。

最后一条：**取图失败绝不冒泡**。`ArtworkLoader` 里整个渲染过程包在 `runCatching` 里，
失败只留一行 DEBUG 日志然后返回 `null`。封面是装饰，装饰出错不能让列表也出错。

## 五、颜色是三态，不是两态

内置文件选择器里每一行的图标颜色是**有含义**的：

| 这一行是什么 | 颜色 | 图标 |
| --- | --- | --- |
| 文件夹 | 强调色（紫） | 打开的文件夹 |
| 可播放的媒体 | 强调色（紫） | 封面，取不到就是类型图标 |
| 字幕文件（含 `.lrc`） | 强调色（紫） | 字幕 |
| 其它（压缩包、文本等） | `onSurfaceVariant`（灰） | 文档 |

颜色本身就是在回答「这个能不能点」，所以它必须是**稳定**的：不能因为「这张图恰好
取不到」就从紫变灰。

## 六、顺手修掉的一个真问题

这一版在模拟器上逐分支核对三态颜色时，发现**可播放但没有封面的文件显示成了灰色**。
原因值得记下来：

`ArtworkSourceRules.requestFor(entry) != null` **等价于**「这一行可播放」，
所以可播放的文件**一定**走 `ArtworkImage` 分支。而当时算好的 `tint` 只传给了
「没有封面」那一支的 `Icon`，`ArtworkImage` 分支里没传 `fallbackTint`——
于是它退回组件默认的 `onSurfaceVariant`，**和旁边不能播的文件长得一模一样**。

一个「两边颜色由同一个变量决定」的界面，如果这个变量只喂给了其中一支，
另一支就会静默退化。修法是把 `tint` 一起传下去，并把这个理由写在调用处。

## 七、哪些条目会去取图

判据只有两条，写成一个纯函数对象（`ArtworkSourceRules`）并用单测钉死，
因为**判错的代价不对称**：判成「不能取」只是少一张图，判成「能取」会让
**每一行**都挂一次注定失败的取图，而且列表每次滚回来都重试一遍。

1. **类型**：只有音、视频有封面这回事。连自己是音频还是视频都不知道的条目不给它抽帧。
2. **来源**：网络来源（`REMOTE`）不取图——既抽不了帧，也不该为了一个列表缩略图
   把整个视频下下来。

其余来源（媒体库、SAF、文件浏览器）一律放行：拿到的都是本机可打开的 uri，
取不到时有兜底图标，白跑一次的成本只有一次失败的解码。

## 八、验证

- **单元测试**：`ArtworkRulesTest`（37 条）+ `ArtworkSourceRulesTest`（15 条）。
  覆盖候选时间点（含时长未知 / 极短媒体去重 / 长视频不设上限）、Rec.709 亮度加权
  （纯蓝要被判成暗）、太暗重试、等比缩放（含「不用缩」与「没法缩」要分得开）、
  缓存键（同 uri 不同类型不撞车）、原子改名、0 字节缓存不可用。
- **全套**：`SUITES=152 CASES=1978 SKIPPED=0 FAIL=0 ERR=0`。
- **模拟器（1080×2400，API 37）**：音频内嵌封面出现在列表行 / 网格瓦片 / 播放页竖屏
  圆形封面 / 横屏左栏；视频抽帧出现在列表与网格（`cache/artwork/` 下确实出现
  `video-*.jpg`）；无封面时退回类型图标；强杀重启后封面立即出现（磁盘缓存复用）；
  内置文件选择器的文件夹 / 可播放有封面 / 可播放无封面 / 字幕 / 其它五个分支颜色逐一核对。

## 九、新增与修改

**新增**

- `core:model`：`ArtworkRequest`、`ArtworkSourceRules`（`core:model` 保持零依赖，
  所以请求类型和判据放这里，`core:ui` 与 `core:data` 都够得着）。
- `core:data`：`ArtworkRules`（全部纯函数判据）、`ArtworkLoader`（解码、重试、落盘）、
  `ArtworkComponents`（Coil 的 `Fetcher` + `Keyer`）。
- `core:ui`：`ArtworkImage`（统一的「图标垫底、图淡入」组件）。
- 依赖：Coil 3.5.0（自带 `okio`）。

**修改**

- `MspApplication`：`startKoin` 之后装配 Coil 单例 `ImageLoader`（自定义组件 +
  显式关掉 Coil 磁盘缓存）。
- `DataModule`：注册 `ArtworkLoader`。
- 列表行 / 网格瓦片 / 播放页音频封面接入 `ArtworkImage`。
- `BrowserPane`：把 `tint` 作为 `fallbackTint` 传进 `ArtworkImage`（第六节）。

## 十、已知限制

1. **封面是自动取的，没有手动换一张的入口。** 没有「换到另一帧」，也没有
   「清掉这张封面」这个动作。
2. **本身就是黑底的片段会得到一张黑封面**（见第二节的取舍说明）。
   阈值 0.12 是启发式，不是「黑」的定义。
3. 32 位设备仍然装不上（ABI 只保留 `arm64-v8a` / `x86_64`，与上一版相同）。
