## 一、这一版做了什么

一件事，但它是**三个入口**：播放器第一次能接收「不是从它自己的媒体库点进来」的东西。

| 入口 | 谁发起 | 递给我们什么 |
| --- | --- | --- |
| 外部打开 | 文件管理器 / 浏览器里的「用其它应用打开」 | 一个 `file://` 或 `content://` 的文件 |
| 分享 | 任意应用里的「分享」 | 一串 `content://` / `file://`（可以多条） |
| 网络地址 | 用户自己在浏览页里填 | 一条 `http://` / `https://` 地址 |

三者在应用里的落点是同一个：**变成 `MediaEntry` 进队列，从第一条开始播**。所以「播放」这一层
一行都没改——队列、续播、字幕、倍速、通知栏全部照旧走原来的路。

除此之外新增的只有两样支撑物：一条地址的**历史记录**（最近 20 条，只在网络地址页用），
以及一个**跨生命周期的信箱**（见第四节）。

这一版不改既有行为：媒体库、浏览、最近、播放列表、设置、字幕、翻译都没动。

## 二、外部打开：为什么「打开方式」里要按类型收窄

### `<data>` 是「并集里求交集」，不是「随便哪个都行」

「打开方式」列表由 manifest 决定，而 `<data>` 元素的语义是**同一组内取并集、不同组之间取交集**。
所以下面这两块的含义完全不同：

```xml
<!-- 写法 A：会被理解成「(file 或 content) 且 (audio/* 或 video/*)」 -->
<data android:scheme="file" />
<data android:scheme="content" />
<data android:mimeType="audio/*" />
<data android:mimeType="video/*" />
```

A 这种把 scheme 与 mimeType 分两组的写法，等于要求「有一个类型叫 audio/*或者 video/*」——
它不是我们想要的「本地文件且是音视频」。正确的写法是**成对**列出来：

```xml
<data android:scheme="content" android:mimeType="audio/*" />
<data android:scheme="content" android:mimeType="video/*" />
<data android:scheme="file"    android:mimeType="audio/*" />
<data android:scheme="file"    android:mimeType="video/*" />
<data android:scheme="http"    android:mimeType="audio/*" />
<data android:scheme="http"    android:mimeType="video/*" />
<data android:scheme="https"   android:mimeType="audio/*" />
<data android:scheme="https"   android:mimeType="video/*" />
```

### 为什么不写裸的 `scheme="http"`

**一条不带 mimeType 的 `http` 会让本应用出现在每一个网页链接的「打开方式」里**：用户在聊天
软件里点一个新闻链接，弹出来的选择框里有一个「MultiSuperPlayer」。这不是「多一个入口」，
而是把一个本该由浏览器处理的动作抢了过来——而且抢错了以后播放页只会显示一个错误。

所以 http / https 那两条**必须**带上 `audio/*` / `video/*`：只有发送方明确声明「这是一个
音视频」时（`ACTION_VIEW` + `-t video/mp4`，或网页给的头部就是这么写的）才会出现在选择框里。
验证过这个取舍：`text/html` 的链接查询结果里只有浏览器，没有本应用。

`ACTION_SEND` 是**另一个 action**，不是 `VIEW` 的变体，所以必须单独声明一个 `<intent-filter>`；
`ACTION_SEND_MULTIPLE` 同理（多选分享走的是它，不是 SEND）。两个都声明了，因为「分享一条」
和「分享一叠」在系统看来是两件不同的事，只声明一个会导致另一个在分享面板里看不到本应用。

### `singleTask` 下的 `onNewIntent`

`MainActivity` 是 `launchMode="singleTask"`：应用已经在运行时再收到一次「打开方式」，
系统**不会**创建新 Activity，而是把 Intent 送到已有的实例上、只调 `onNewIntent`。
不在那里处理的话，症状是「应用开着的时候从文件管理器点一个视频，什么都没发生」——
既没有新页面，也没有报错，`adb` 那边还会打印一句 `Activity not started, intent has been
delivered to currently running top-most instance`。

`onNewIntent` 里必须显式调 `setIntent(intent)`：不调的话 `getIntent()` 还是启动时那一个，
配置变更（旋转屏幕）重建时会拿到过期的 Intent。

## 三、从一条 uri 到一条能播的条目

### 两个新前缀：`url:` 与 `shared:`

`MediaEntry.id` 是这个项目里唯一能跨重启活着的东西（播放位置、最近播放、播放列表条目全按 id 记），
所以新来源必须有新前缀：

| 前缀 | 谁造的 | uri 长什么样 | 回放时的来源 |
| --- | --- | --- | --- |
| `url:` | 网络地址页里填的地址 | `https://host/path/a.mp4` | `MediaSource.REMOTE` |
| `shared:` | 别的应用递进来的文件 | `content://…`、`file://…` | `MediaSource.SHARED` |

**都不能复用 `file:`**。那个前缀的含义是「本机文件系统里的一个绝对路径」，回放时会被送去
**同目录**找字幕；把 `content://` 或 `https://` 套上它，字幕查找会去问一个根本不存在的目录，
然后安静地返回「没找到字幕」——不报错，只是永远不生效。`saf:` 也不行：那个前缀的语义是
「我们自己扫出来的、有目录层级的树」，而这两个新来源恰恰没有目录可查，字幕查找对它们
显式返回 `Unavailable`。

id 从 uri 推导而不是另造一个随机 id，还有一个好处：它**可以被重新造出来**。播放列表里存的是
id + uri + 标题，导入之后 uri 还在，id 就能还原，来源也跟着还原（`PlaylistItem.sourceOf`）。

### `content://` 要查真名，`ClipData` 要做兜底

`content://` uri 的最后一段往往是一串数字（`…/media/123`），所以进来之后要查
`OpenableColumns.DISPLAY_NAME` / `SIZE` 补上真实文件名与大小，列表里才不会显示成一串编号。
查不到就退回用路径段当名字——**不抛异常**，查不到是常态而不是错误。

`EXTRA_STREAM` 不是 uri 唯一的落脚点：有些发送方不写这个 extra，而是把 uri 塞在
`ClipData` 里（`setData` + `addFlags(FLAG_GRANT_READ_URI_PERMISSION)` 的写法）。
两条路都读，`EXTRA_STREAM` 优先。读的过程中任何异常都吞掉并记一行日志——那是**发 uri 的
那个应用**的问题，不能因此崩在接收方。

顺带说清楚两处**刻意的**不对称：

- **分享过来的、后缀明确不是媒体的东西直接剔掉**（`.lrc` / `.jpg` / `.txt`）：一次分享一叠
  文件是常见操作，把图片混进播放队列只会让「下一首」卡在一个必然失败的条目上；
- **网络地址不剔**：那是用户主动填进来的一条地址，「地址后面不是媒体」交给内核去报错，
  比我们把它变成一个安静的空结果好。

## 四、跨生命周期的那个信箱

收到 Intent 的地方是 `MainActivity`（`onCreate` / `onNewIntent`），真正播放的地方是
Compose 里的 `MspApp`（它拿着 `PlaybackController` 和 `NavController`）。这两头分属不同的
生命周期对象：

- 冷启动时 Compose 还没组合出来，**不能直接调用播放**；
- 收到请求时界面可能停在任意一页（甚至在播放页），**也不能假设重新组合时会再读一次 Intent**。

所以中间放一个 Koin `single`（`PendingExternalPlayback`）：写在收 Intent 的地方，
读在 `MspApp` 的一个 `LaunchedEffect` 里。

**为什么不用 ViewModel**：`koinViewModel()` 的作用域取决于 `LocalViewModelStoreOwner`——
根组合里是 Activity、`NavHost.composable{}` 里是 `NavBackStackEntry`，同一个类型在两处
拿到的是**两个实例**。这一条在这个项目里已经踩过一次。而进程级的 `StateFlow` 恰好满足
「谁先谁后都对」：当前值会在订阅那一刻发给收集方，所以「先收到请求、后组合」也拿得到。

两处顺序不能反的细节：

1. **先 `consume()` 再 `playFrom()`**。`consume()` 清掉待播状态，之后配置变更（旋转屏幕）
   重新组合时才不会**重播一次**；反过来写的话，`playFrom` 之后到下一次组合之间还留着一个
   非 null 的值，旋转屏幕就等于又点了一次播放。
2. **多文件整队进队列、从第一条开始播**，而不是只播第一个。多选分享（一次分享一整个文件夹）
   是这个入口最常见的用法，只播第一个等于把用户选的其他文件悄悄丢掉。

## 五、网络地址：白名单 + 「像不像主机名」

判据是**白名单**：只有 `http` / `https` 能通过（协议可以省略，省略时补 `http://`）。
不做 `rtsp:` / `rtmp:` / `magnet:`——内核虽然认识一部分协议，但它们的缓冲、seek、
断点续播行为都和 HTTP 不一样，没有验证过的路径不该出现在地址栏里：那种「能填进去但放不出来」
的入口比没有入口更糟。

`sanitize` 的顺序是固定的：去首尾空白 + 全角标点归位 → 拒掉中间有空白或反斜杠的输入
（前者是「粘进来两行」、后者是「从资源管理器复制的路径」）→ 协议必须在白名单里
（大小写无关，`HTTP://X` 是人手写的）→ 主机名不能为空、不能以点开头或结尾 →
**省略协议时剩下的那一段必须「像主机名」**。

### 全角标点

中文输入法下敲 `http://192.168.1.5:11434/v1` 实际会得到
`http：／／192.168.1.5：11434／v1`（`：` U+FF1A、`／` U+FF0F），有时 `.` 还会变成 `。`。
这类输入看起来「地址填好了」，实际是一个必然失败的字符串，而错误信息（网络错误）完全指不到
真正的起因。所以只把**在 URL 里有明确含义**的那几个全角字符换回 ASCII；中文逗号、括号不换——
它们可能真的是文件名或查询参数的一部分，改掉反而是我们弄坏了用户的地址。

### 「像不像主机名」这条规则是真机上改出来的

第一版规则是「省略协议时必须有 `.`」。真机上试的时候发现：从文件管理器复制一个片名
（`TestClip.mp4`）粘进地址框，**它被接受了**——因为它含有点。于是界面会先转十几秒，
再报一个和输入毫无关系的网络错误；而提示文案当时写着「必须以 http:// 或 https:// 开头」，
既不准确（域名其实可以省略协议），也没能拦住这个最常见的错。

现在判据是两条：**含有点**，且**整段不是一个文件名**。「是不是文件名」借的
`SafScanRules.kindOf` 那张后缀表，不另写一份——地址栏里 `.mp4` 是文件名、在本地文件里是媒体，
这两件事必须用同一张表，否则同一个字符串在两条路上会有两种结论。于是：

- `TestClip.mp4` / `movie.mkv` / `song.flac` / `lyrics.lrc` ⇒ 立刻报「这不是一个能播放的地址」；
- `nas.local/a.mp4` / `192.168.1.5:8080/a.mp4` ⇒ 接受，补成 `http://…`；
- `http://nas/movies/a.mp4`（显式写了协议）⇒ 照收。显式写协议的人意图明确，判断对错是他的事。

提示与错误文案也跟着改成了真实规则：「以 http:// 或 https:// 开头，**也可以只写域名**」——
文案说谎和规则说谎一样糟，而它只在真机上才看得出来（JVM 单测看不到界面文案与规则是否一致，
那一条是靠 `NetworkStringsTest` 把「必须提到域名」这件事钉住的）。

### 历史记录

最近用过的 20 条存在独立的 DataStore（`files/datastore/msp_remote.preferences_pb`）里，
键是地址、值是「我们记下的添加时间」。时间戳是**我们的簿记**、不是用户的数据，所以它坏掉
（读不出数字）时把那条排到最后而不是整条丢掉。写盘失败只记日志、不抛：一次地址历史写不进去
不该让「播放」这个动作失败。

同一个地址第二次点开会**接着上次的位置播**（和媒体库条目走同一条续播规则，id 相同即同一条
记录）——这是刻意的，也是「最近用过」那一栏的意义所在。

### 浏览页那一行是「动作」，不是「目录」

网络地址入口放在浏览页最上面，但它**不是**一个 `BrowserRoot`（那套类型要求「能列出子项」），
而是一个动作行：点进去是地址页，没有层级。放在 `roots` 判断之外，因为进这一页不需要任何
存储权限——它是唯一在本应用没有任何权限时也能用的播放入口。

  因为 `Intent.ACTION_VIEW` 在单测里是空的。

## 八、已知限制

- **网络播放没有自定义请求头 / User-Agent 的入口**：需要登录态或带防盗链校验的地址放不了。
  要支持它得在 `core:player` 里加一层 `DataSource.Factory`，这一版没做——把它做成一个半成品
  （能填 header 但影响不到内核）比不做更糟。
- **只支持 http / https**：`rtsp:` / `rtmp:` / `magnet:` 一律判为非法地址，理由见第五节。
- **外部进来的条目不进「最近播放」**：那一页是「续播记录 × 当前媒体库条目」的交集，
  而网络地址与分享进来的文件都不在媒体库里。要重播只能从网络地址页的历史、或再从原应用
  打开一次（会接着上次的位置）。
- **同一个文件经「打开方式」播和从媒体库播是两个身份**（`shared:` vs `MediaStore` id），
  续播位置不共享。
- **没有自定义 scheme**：`msp://play?url=…` 这类协议这一版不做。
- 不做音乐选择器（`ACTION_GET_CONTENT` / `ACTION_PICK`）入口——「浏览」页已经有内部入口，
  多一个系统选择器只会让「到底从哪儿选文件」多一种答案。
- 不含 32 位原生库（沿用上一版的取舍）。

## 九、升级注意

- 这是**测试版**：正式版通道的用户不会收到它。想试就切通道，或者直接装这一份 APK。
- `versionCode` 10100 > 10000，可直接覆盖安装 v1.0.0。
- 网络地址的历史存在**一个新文件**里（`files/datastore/msp_remote.preferences_pb`），
  与既有设置/续播记录互不影响；卸载或清数据会一起丢掉。
- 「打开方式」是**安装后自动生效**的，不需要用户授权任何东西——但它只对音频 / 视频出现，
  这是刻意的（见第二节）。
