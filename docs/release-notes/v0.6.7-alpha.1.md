# v0.6.7-alpha.1 预发行测试版

> **这是预发行测试版（pre-release）。** 功能与界面文案仍可能调整，不建议作为日常主力使用。
> 遇到问题请到 [Issues](https://github.com/Aaze-wu/MultiSuperPlayer/issues) 反馈。

基于版本：v0.6.6-alpha.1

## 一、这一版做了什么

需求② + 需求③ 一起做完：

1. **设置页新增「权限」页**（原「文件访问」那一行改造成入口）：把应用**能申请**的四项
   （媒体读取 / 所有文件访问 / 通知 / 蓝牙）连**状态**和**动作**一起列出来，下面另有一段
   折叠说明列出**安装即授予、应用自己关不掉**的六条。
2. **安装后首次启动申请一次**：依次弹**通知** → **音乐和音频** → **照片和视频**。
   「所有文件访问」与蓝牙**不在这一批里**，之后也不会再自动弹。
3. 顺带修掉三个真机上才露出来的毛病（媒体库不刷新、蓝牙申请没反应、已允许的权限被写成
   「已被拒绝」），见 §三。

## 二、权限页怎么设计的

### 1. 只列「你能改的」，其余折叠起来说清楚

一页里同时出现 13 条权限只会让人放弃阅读。所以分成两段：

| 段 | 内容 | 能不能动 |
| --- | --- | --- |
| 可以更改的权限 | 媒体读取 / 所有文件访问 / 通知 / 蓝牙 | ✅ 每行都带状态 + 动作按钮 |
| 其他权限（折叠） | 网络访问 / 查看网络状态 / 前台服务 / 前台媒体播放服务 / 阻止休眠 / 更改音频设置 | ❌ 只列出原始权限名，说明「安装时就已经授予」 |

折叠区那一段存在的理由是**透明**：用户有权知道这个应用一共申请了什么。它不带任何操作，
因为这几条本来就没有 UI（`INTERNET` 这类根本没有授权框）。

### 2. 五个状态，对应五种不同的下一步

| 状态 | 界面文案 | 动作 |
| --- | --- | --- |
| `GRANTED` | 已允许 | 去设置 |
| `PARTIAL` | 只允许了一部分 | 申请 |
| `NOT_ASKED` | 未开启，可以在这里申请 | 申请 |
| `ASK_AGAIN` | 未开启，可以再申请一次 | 申请 |
| `GO_TO_SETTINGS` | 已被拒绝 | 去设置 |
| `UNSUPPORTED` | 本机系统版本不支持 | （无按钮） |

**关键是 `ASK_AGAIN` 与 `GO_TO_SETTINGS` 必须分开**：系统的
`shouldShowRequestPermissionRationale` 在「拒绝过一次、还能再弹」时为真、在「已经不允许
再弹了」时为假；把这两种情况合并成一句话，用户就会点一个**按下去什么都不发生**的按钮。
`GO_TO_SETTINGS` 这一格给的按钮是「去设置」而不是「申请」，正是因为系统已经不会再弹框了。

### 3. 「所有文件访问」走系统专属页

它有独立的系统页面（`ACTION_MANAGE_APP_ALL_FILES_ACCESS_PERMISSION`），在应用内申请不到，
所以那一行的动作固定是「去设置」，跳的是系统那个页而不是应用详情页。

### 4. 蓝牙：声明保留，但列出来

本版本**没有任何代码使用蓝牙**（media3 三个 jar 的字节码里 0 命中 `BLUETOOTH_CONNECT`）。
保留声明的理由是将来接蓝牙播放设备时不必再走一次「新权限 → 用户重新授权」，
而把它列进权限页是为了不藏事：这一行会老老实实说「当前版本还没有功能需要它」。

## 三、三个真机上才露出来的毛病

### 1. 启动时授权完，媒体库还停在「需要媒体授权」

首次启动那三个系统框是**应用根部**统一发的，而媒体库自己那个 launcher 拿不到那一次回调；
`MediaLibraryRepository` 又只在初始化时扫一次。结果：用户刚点完「允许」，回到媒体库看到的是
「需要媒体授权」，得再点一下按钮才出列表——一个看起来像授权失败、其实只是**没人去重扫**
的状态。

修法：媒体库在**切回前台**时，如果上次的结论是「一个权限都没有」，就重扫一次。

```kotlin
internal fun shouldRescanOnResume(state: MediaLibraryState): Boolean =
    state is MediaLibraryState.NeedsPermission
```

这条策略抽成顶层纯函数是为了能**正反两向钉住**：`NeedsPermission` 要重扫（补上别人申请的
权限），而 `Ready` **不重扫**（每次回前台都查一遍 MediaStore 是白花钱）、`Loading` 不重扫
（本来就在扫）、`Error` 不重扫（别把失败循环成反复重试）。

### 2. 权限页点「申请」什么都不弹（蓝牙那一行）

根因不在蓝牙，而在**「问过系统了」和「系统真的弹过框」是两件事**：

- 记账（`markAsked`）必须在调起系统框**之前**完成，否则用户中途切掉应用就丢了这一笔；
- 于是「记过账」被当成了「系统弹过框」的证据，一旦某次请求因为任何原因没弹出来，
  界面就会把「从没问过」显示成「已被拒绝」。

而这一版还叠了第二个原因：**权限页的 ViewModel 和应用根的 ViewModel 不是同一个实例**
（前者挂在 `NavBackStackEntry` 上，后者挂在 `Activity` 上）。请求写进了权限页自己那份待办，
而全应用唯一会去调系统框的 launcher 挂在根上、观察的是另一份待办——按下去什么都不弹，
可账已经记下了。

修法：**把「待办」和「状态」从 ViewModel 搬进 `AppPermissions` 这个 Koin 单例**，
谁发起、谁显示、谁弹框看到的都是同一份。实测：蓝牙行点「申请」→ 系统弹出
「要允许 MultiSuperPlayer 查找、连接到附近设备…」→ 允许后该行变成「已允许」。

### 3. 刚允许过的权限显示成「已被拒绝」

`rememberLauncherForActivityResult` 的回调触发得**早于系统落盘**权限状态，那一刻读
`shouldShowRequestPermissionRationale` 读到的是旧值，于是刚「允许」的权限被判成
「系统不会再弹框了」。

修法：系统框返回时**带着 Activity 顺手重算一次状态**（`refresh(activity)`），而不是只等
页面的 `ON_RESUME`。这也覆盖了「系统压根没弹框就直接拒」的情况——那种情况不会产生 resume
事件，不在这里刷新的话权限页会一直停在一个按了没反应的按钮上。

## 四、真机验证结果

在 `emulator-5554`（Android 17 / API 37，zh-Hans-CN）上 `pm clear` 之后从头走一遍：

| 项 | 操作 | 结果 |
| --- | --- | --- |
| 首次启动申请顺序 | 启动后延迟 1.2 秒 | ✅ 通知 → 音乐和音频 → 照片和视频，依次弹出 |
| 申请范围 | 观察三个框 | ✅ 只有通知与媒体两项，**没有**「所有文件访问」，**没有**蓝牙 |
| 媒体库自愈 | 三个框全部允许后回到媒体库 | ✅ **自动**出列表：全部 22 / 音乐 10 / 视频 12（无需再点按钮） |
| 设置入口 | 设置页 | ✅ 「权限 · 已允许读取媒体库」 |
| 权限页四行 | 设置 → 权限 | ✅ 媒体库读取「已允许」/ 文件访问「未开启…」/ 通知「已允许」/ 蓝牙「未开启，可以在这里申请」 |
| 蓝牙申请 | 点蓝牙行的「申请」 | ✅ 弹出「要允许…查找、连接到附近设备」；允许后该行变「已允许」，`dumpsys` 确认 `granted=true` |
| 已允许不再误判 | 看媒体与通知行 | ✅ 都显示「已允许」而不是「已被拒绝」 |
| 部分授权 | `pm revoke READ_MEDIA_AUDIO` 后回前台 | ✅ 媒体库提示「只授权了部分媒体访问，列表可能不完整」（音乐 0 / 视频 12）；权限页显示「只允许了一部分」+「申请」 |
| 拒绝一次 | 点「申请」→ 弹框里点「不允许」 | ✅ 回到权限页仍是「只允许了一部分」+「申请」（系统还能再弹，所以不该是「去设置」） |
| 跳系统页 | 文件访问 →「去设置」 | ✅ 打开系统的「所有文件访问权限」页；在那里开启后返回，行变成「已开启，可以浏览任意文件夹」 |
| 折叠区 | 展开「其他权限」 | ✅ 六条 + 原始权限名（`android.permission.INTERNET` 等），无操作按钮 |

## 五、已知取舍

1. **`POST_NOTIFICATIONS` 对媒体播放通知没有影响。** Media3 发播放通知的路径是
   `@SuppressLint("MissingPermission")` 的，A/B 实测（允许 / 拒绝该权限）通知行为一致。
   它影响的只是**应用自己主动发的**通知——而当前版本一处都不发
   （全仓库 `NotificationCompat` / `NotificationManagerCompat` 0 命中）。
   列在权限页里是因为用户有权控制它，不是因为这一版需要它。
2. **`GO_TO_SETTINGS` 不给「申请」按钮。** 系统在用户拒绝之后不会再弹框，给按钮就是骗人。
   代价是「其实还能再弹，只是我们判断错了」这种情况会让用户多走一次系统页——所以判定
   一律以系统的 `rationale` 为准，只在**真的读不到**（没有 `Activity`）时才退化成保守的那一边。
3. **「问过系统了」仍然自己记在 `SharedPreferences("msp_permissions")` 里**，而不是问系统。
   系统答不出「问没问过」（`rationale` 对「没问过」和「问过并被永拒」都答假）。
   这一份记忆和 `msp_settings` 那份 DataStore 分开存：它是系统状态的镜像，不是用户的设置。
4. **「所有文件访问」不在首次启动申请**（README §7 的承诺不变），需要时从权限页跳系统页开。
5. **0.6B 照抄提示词示例、翻译缓存没有「清空」入口**——这两个问题按既定决定保留，本版不动。

## 六、升级提示

- 从 v0.6.6-alpha.1 升级**不需要任何迁移**：
  - 新增的都是界面与权限请求逻辑，没有动任何持久化格式；
  - `msp_permissions`（权限记账）是全新的一份文件，升级后第一次启动会当成「还没问过」——
    于是**升级后第一次打开会申请一次通知与媒体读取**，这与「安装后第一次启动申请一次」
    是同一条规则（一次性开关本来就跟着安装走）。
  - 已经允许的权限不会再弹：`startupRequest()` 会把**已授予的**排除掉，只申请缺的那几条。
- **versionCode 从 606 涨到 607**。
- 如果你之前在系统设置里手动关掉过某项权限：升级后权限页会如实显示「已被拒绝」，
  动作是「去设置」——系统在拒绝之后不会再弹框，这条路只能从系统页走。
