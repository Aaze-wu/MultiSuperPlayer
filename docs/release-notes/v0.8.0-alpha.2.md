## 一、这一版做了什么

两件事，都是 v0.6.3 / v0.5.18 就欠下的（当初都写了「留到后续版本」）：

1. **拖动排序自动滚动。** 拖到列表上/下边缘附近时列表自己滚起来，越贴边越快。
   队列面板、播放列表清单页、播放列表详情页**三处共用同一套实现**。

   面板在播放页的控制条上（和「队列」「睡眠定时」并排）。

## 二、自动滚动：为什么要「速度 × 帧间隔」而不是「每帧滚 N 像素」

最直觉的写法是「贴到边缘就每帧滚 8px」。它在 60Hz 的手机上看着正常，换到 120Hz 的机器上
**滚得快一倍**——同一段代码、同一份手感设置，两台机器两个结果。所以规则函数返回的是
**速度（像素/秒）**，循环里再乘上这一帧的真实间隔：

```
位移 = 速度 × 本帧间隔
```

帧间隔本身还夹了一道上限（`MAX_FRAME_SECONDS = 0.05f`，约三帧）：掉帧或者应用被切到后台
再切回来时，两帧可能隔几百毫秒，照实乘上去就是「抖一下滚过去半屏」。夹住之后最坏也只是
慢一拍，用户看不见列表突然跳。

**越贴边越快**也是刻意的：全程匀速会让「只想滚一点点」变成做不到的事（要么不动，要么
一直滚），而只有最快那一档又会让长列表一路冲过头。所以离边缘 `EDGE = 72dp` 以内开始滚，
在带子里线性加速到 `MAX_SPEED = 900dp/s`（大约一秒一屏）。带子比半个视口还高时按半个视口
夹住——不夹的话上下两条带子会重叠，同一个位置既算贴顶又算贴底，结果取决于先判断哪一边，
在真机上表现成「拖着拖着列表突然往反方向滚」。

### 滚动和手指是两条输入，落点必须只有一个真相

自动滚动改了内容的位置，手指位移也改，两者都会改被拎起来那一行的落点。如果各算各的，
就会出现「列表滚了、落点还停在原处」。所以滚动这一路把**真正滚掉的像素**（`scrollBy`
的返回值）喂回拖动状态（`ReorderDragState.contentScrolledBy`），和手指位移记进同一个数里：

- 内容滚到头时 `scrollBy` 返回 0 ⇒ 那一行**不跟着动**（否则它会从手指底下溜走，落点还在变）；
- 否则落点跟着内容走，滚多少就多算多少。

另外这个循环**只在拖动期间存在**：`state.from` 一变 `LaunchedEffect` 就重开，松手即结束。
写成常驻空转的话，列表只要在屏幕上就会一直吃满垂直同步。

## 三、均衡器：为什么曲线按「频率」存，而不是按「第几段」

`android.media.audiofx.Equalizer` 的**段数、每段的中心频率、增益范围**全是设备上报的：
5 段是常见值，10 段也不少，模拟器上往往根本建不出来。如果按段下标存「第 3 段 +6dB」，
换一台设备后那台机器的第 3 段可能是 910Hz 也可能是 1.2kHz——**用户看到的界面数字完全一样，
听到的声音却不一样**。所以存的是 `(中心频率, 增益)` 对（`"60:7.0,230:4.0,…"`），
下发给设备时再用 `toDeviceGains` 把曲线**贴到设备自己的**中心频率上、并按设备范围夹取。

同理，**预设不用系统自带的**（`usePreset`）：它们的名字是厂商/系统的（同一个 id 在两家
手机上叫两个名字），段数取决于设备，而设置里存下的那个 id 换台设备可能指向完全不同的曲线。
整套曲线写在 `EqualizerPreset` 里，于是名字归我们自己的三种语言管，跨设备也是同一条曲线。

### 界面固定画五根滑块

画的是**标准频率**（60 / 230 / 910 / 3.6k / 14k），不是「设备上报的那几段」。跟着设备走的话，
设备段数只有在开始播放之后才知道，面板会在用户眼皮底下从 5 根变成 10 根。曲线的下标和
界面的下标永远是同一件事，设备那侧的差异由下发那一步抹平。

滑块能拖到的区间是**我们自己的 ±12dB 与设备上报范围的交集**。不取交集的话会出现
「滑块能拖到 +12、设备只认到 +6」——用户看到数字在变、声音不变，这种问题在真机上极难认出来。

### 「不能用」的三种原因必须分开说

- **开关关着**：控件变灰，原因就在旁边的开关上，不用解释。
- **还没开始播放**（`Idle`）：控件**照样能调**，设置会存下来、开始播放后生效。
  这是可以提前配置的状态，不是错误——所以说「开始播放后可用」，而不是「你的设备不支持」。
- **设备建不出来**（`Unsupported`）：控件变灰并明说。否则用户会一直拖滑块等一个永远不会
  出现的声音变化。

均衡器挂在 `ExoPlayer` 的**音频会话**上，而不是界面的生命周期：退出播放页之后音乐还在放，
均衡器也还得在。会话号在开始播放前是 0、播放器重建后会变，所以实现是「订阅会话号，
变了就重建效果」。`AudioEffect` 在模拟器、部分驱动、效果槽位被占满的设备上会抛异常——
每一次和效果打交道都夹在 try/catch 里，整个功能在这些设备上的正确行为是「面板上说一句
不支持」，而不是崩掉播放页。

## 四、修掉一个只在真机上露头的 bug：长按拖动完全不生效

这是本版**最容易被误判成「模拟器/注入手势的问题」**的一个 bug，记在这里给以后的自己看。

现象：播放列表详情页上长按一行，**长按成立、那一行也高亮了，就是拖不动**。

拖动循环原来这样算位移：

```kotlin
val dy = change.positionChange().y   // 恒为 0
```

`positionChange()` = `position − previousPosition`，而 `previousPosition` 在 Android 后端
取自 **`MotionEvent` 的历史采样点**。一次事件里没有历史采样点（手指采样率低、被系统合并
成一个事件，或者事件由 `input motionevent` 这类工具逐条注入）时 `previousPosition == position`，
**delta 恒为 0.0**。日志把它钉死了——位置一直在变，增量一直是 0：

```
down Offset(540.0, 184.0)
长按成立
onStart data=0 row=189.0
move pos=406.0 dy=0.0     ← 手指明明走了 222px
move pos=606.0 dy=0.0
move pos=806.0 dy=0.0
```

修法是**自己维护上一次的位置**、取相邻两次事件的绝对位置之差。真机上语义完全等价
（相邻事件的绝对位置之差就是这一小段位移），而且对事件合并天然免疫。

### 顺带修的次生 bug：丢失的 113 像素

验证队列面板（即时触发那一路）时发现 `onStart y = 107.0` —— 那是**跨过 `touchSlop` 那一帧**
的位置。也就是说 `down → 跨阈值` 那一段位移被**永久吞掉了**：实测一个横跨 113px 的手势
只累到 24px，连半行（73.5px）都够不到，表现成「拖了很远却不换位」。

现在两条路各取各的起点：

| 触发方式 | 起点 | 理由 |
| --- | --- | --- |
| 长按（`LongPress`） | **长按成立那一刻**的手指位置 | 按住那几百毫秒里手指可能已经游走几像素，那段不该在拖起来的一瞬间弹出来 |
| 即时（`Immediate`） | **按下那一刻**的位置 | 过阈值那一段同样是手在动，算进去才跟手 |

## 六、已知限制

- **均衡器能不能用、能拖到多少 dB，取决于设备和当前音频会话。** 段数、每段频率、增益范围
  都是设备上报的；模拟器和部分设备上根本建不出效果（面板会说「不支持」，这是安静降级）。
- **滑块固定五根**（标准频率），不是设备实际段数。曲线按频率存并按频率插值，所以贴到
  10 段设备上仍是同一条曲线，只是中间多几个采样点。
- **自动滚动的速度是按「一秒一屏」定的**（900dp/s 上限）。列表特别长（几千条）时想滚到很远
  的地方，仍然要贴着边缘等一会儿——它不是一个「扔一下就飞过去」的惯性滚动。
- 更新系统与后台保活的限制同 v0.7.0-alpha.1（未变）；字幕与翻译的限制同 v0.8.0-alpha.1（未变）。

- 本版**没有**做「音视频同步」（用户已明确不做）；内嵌位图字幕（PGS / VobSub / DVB）仍排在
