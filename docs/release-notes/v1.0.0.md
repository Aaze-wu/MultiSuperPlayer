# v1.0.0 多语言收尾、自定义强调色、翻译缓存清空、播放记录与播放列表导出/导入

发布日期：2026-10-04
基于版本：v0.9.0

---

## 一、这一版做了什么

五件事：**三件是把以前留着的小口子补上**（多语言、自定义强调色、翻译缓存清空），
**一件是把已经攒在播放器里的数据交还给用户**（导出），
还有一件是**让交出去的数据能拿回来**（导入）。

**多语言收尾。** 界面早就三语齐全了，但 `core:subtitle` 的解析告警一直还是中文——「这个文件
不是 UTF-8，已按 GBK 猜着读」这类话，在英文界面上照样印出汉字。原因是它的类型是 `List<String>`，
而承载多语言的 `MspText` 当时住在 `core:common`，`core:subtitle` 不方便依赖它。现在把 `MspText`
下沉到**零依赖的 `core:model`**（见第二节），告警随之变成 `List<MspText>`，三语界面上都不再漏中文。

**自定义强调色。** 以前强调色只有「系统取色 / 封面取色 / 6 个预设」三种来源。现在多了一条：
**色相 / 饱和度 / 明度三根滑块拖出自己的颜色**，上面实时预览。它与预设是**互斥**的，也随时可以
「回到预设强调色」（见第三节）。

**翻译缓存清空。** 缓存是全局共享的一份 JSONL，以前**没有任何入口能碰它**——想强制重译只能
改字幕内容或换目标语言。现在设置 → 翻译里多了一行，写着「已缓存 128 条译文 · 1.2 MB」和一个
「清空」按钮（见第四节）。

**导出播放记录与播放列表。** 「最近」页可以把播放记录导出成文件，播放列表可以导**全部**、
也可以只导**当前打开的那一个**，格式二选一：CSV 或 JSON（见第五节）。

**导入播放列表。** 导出做完之后立刻显出一个洞：**数据能出来，回不去**。所以清单页顶上多了一个
「导入」，把以前导出的 CSV 或 JSON 读回来，文件里每个列表各建一个（见第五节）。
这是本版唯一一件**在原计划之外**的事，它值得进 1.0 的理由是：一个「导出」按钮如果只是单向的，
用户能做的唯一一件事就是把数据交出去保管——而备份的意义本来就在于能拿回来。

## 二、`MspText` 为什么要下沉到 `core:model`

### 问题不是「翻译告警」，是「类型放错了地方」

`MspText` 的形状是「资源 id + 参数列表」（`Res(id, args)`）或者「一段现成的字」（`Plain`）。
它**零依赖**——只用得到 `androidx.annotation` 的 `@StringRes`。这一点很关键：它描述的是
「一句话怎么取到」，而不是「这句话怎么显示」，所以它不需要 Compose、不需要 Context、
不需要任何业务模块。

它原先住在 `core:common`，而 `core:common` 依赖 `core:model`（`api core:model`）。
于是 `core:subtitle` 要写 `List<MspText>` 就得反过来依赖 `core:common`——一个**只做字幕解析**
的模块，为了「一句话的类型」去依赖「通用工具模块」。下沉之后这件事就没了：

```
core:model   （谁都可以依赖，自己零依赖）
    ↑
core:common / core:subtitle / core:ui / core:player ...
```

包名跟着走：`com.multisuperplayer.core.model.text`，`R` 用 `core:model` 自己的。

### 顺带修好的两类「漏中文」

1. **解析告警**（`SubtitleParser.warnings`）：ASS / LRC / SRT / VTT / TTML 五个解析器一共
   20 条告警文案，全部变成 `MspText.Res`，三语文案齐全（`core:subtitle/.../values{,-en,-b+zh+Hant}`）。
2. **解析失败的异常**（`SubtitleParseException`）：它的字段由 `String` 变成 `MspText`
   （字段名也从原来那个含糊的叫法改成 `text`）。**异常里的文案也是要给用户看的**，
   而异常是跨模块传递的，这一处漏了的话，同样是「英文界面上弹一句中文」。

`SubtitleRepository.detailOr(...)` 现在**先**匹配 `SubtitleReadException` / `SubtitleParseException`
再退回通用错误——顺序反过来会把这两类已经带好 `MspText` 的失败又重新包成一句笼统的话。

### 为什么不做「字符串 + 翻译函数」

一个诱人的替代方案是：告警继续用 `String`，显示的时候再过一遍 `tr()`。它不行，因为
**「哪条告警」这个信息在拼成字符串之后就丢了**——`tr("无法解码，已按 GBK 猜着读")` 只能按
**中文原文**做键，改一个标点就失配，而且没人会发现，只是悄悄退回中文。`MspText` 把「是哪条告警」
留在资源 id 上，这才是可校验的（`SubtitleStringsTest` 逐条断言三语齐全）。

## 三、自定义强调色：三根滑块、一个预览、一条退路

### 三个数就是全部

颜色用 HSL 描述：**色相 0–360°、饱和度 0–1、明度 0–1**。四个种子色（primary / secondary /
tertiary / 容器色）由 `customAccentColors(hue, saturation, lightness)` 一次算出来。

**明度被夹在 10%~80%**，不是 0~100%：纯黑和纯白的强调色等于「用户把界面改坏了而且没有回头路」，
而界面此刻正是靠这个颜色在告诉他哪些东西能按。夹住范围，最坏情况也只是「这个颜色不太好看」。

### 滑块不预置当前颜色

进这一页时三根滑块从**固定的起点**开始（色相 250°、饱和度 0.55、明度 0.45），
而不是从「当前正在用的颜色」反推出来。理由是反推这件事**有损**：当前色可能是系统取色或封面取色
来的，把它转成 HSL 再夹一次范围，就再也回不到原来那个颜色了——而界面会假装它回得去。
定一个说得通的起点，比假装精确更诚实。

### 拖动时预览，松手才保存

`Slider` 的 `onValueChange` 只更新界面，`onValueChangeFinished` 才写盘。否则拖一下会往
`DataStore` 写几十次，而用户只是在找一个好看的角度。

### 与预设是「互斥」，不是「覆盖」

优先级是 **封面取色 > 系统取色（莫奈）> 自定义 > 用户选的预设**。

自定义排在预设前面，但**不是替掉预设**：选了自定义色之后，预设的 id 仍然留在设置里。
因为「回到预设强调色」这个按钮应该回到**他之前选的那个预设**，而不是默认值——用户点一下
「回到预设」，结果颜色跳到一个他从来没选过的颜色，他会以为按钮坏了。

两个「取色」开关（系统取色 / 封面取色）在选颜色（预设或自定义）时会**被主动关掉**：
那是一个明确的「我要这个颜色」，而这两个开关的优先级更高，不关掉的话用户滑了半天滑块、
一点变化都没有。

## 四、翻译缓存清空：两个「看起来一样」的按钮不能合

### 缓存和人工修正不是一回事

这个项目里有两份「翻译结果」：

| | 存在哪 | 是什么 | 清空入口 |
| --- | --- | --- | --- |
| 翻译缓存 | `filesDir/translation_cache.jsonl`（全局一份） | 模型以前给过什么 | 有 |
| 人工修正的译文 | `filesDir/translation_edits/<媒体 key>.json`（每部片子一份） | **用户自己改过的** | **没有，也不该有** |

把两者合成一个「清空翻译数据」按钮，用户点一次就会输掉自己改过的字幕。所以界面上写着
「清空只删这份缓存；你手动修改过的译文保存在另一个文件里，不会被删掉」——**这句话是用户敢不敢按
的关键**：少了它，凡是改过译文的人都不敢清缓存，而那正是最需要清的人（缓存攒得最满的就是他）。

### 失败时不清内存索引

`TranslationCacheStore.clear()` 的返回值是「**是否真的删掉了**」。删失败时索引**保留**。

以前这里有个坑：删不掉也照样把索引清空，于是界面显示「已清空」、下次翻译却全部命中旧缓存
（钱是省了，但用户唯一的结论是「这个按钮是假的」）。索引留着，界面才能诚实地告诉他
「还剩 128 条 · 1.2 MB」。

### 三句话都是 `MspText`，而且长得不一样

「已缓存多少」「清空失败还剩多少」「清空前会删掉多少」三句话由 `TranslationCacheStats`
的三个方法产出（`describe` / `describeClearFailure` / `describeClearConfirmation`），
**和产生它们的两个数字放在同一个类里**：这三句话的每个参数都由这两个数算出来，搬到设置页去拼的话，
「条数为 0 时说什么」这类分支就会在界面里再写一遍（然后写漏）。

`describeClearFailure()` **必须和 `describe()` 长得不一样**：只写一句「清空失败」的话，
用户会把它当成无关痛痒的提示，而缓存其实还在。真正的失败现象是「我明明清过了，怎么还是没花钱」。

条数为 0 时**不显示**「清空」按钮（而不是置灰）——置灰的按钮会让人去猜「怎样才算可以按」。

## 五、导出与导入：CSV 还是 JSON，以及几处刻意的取舍

### 两个格式，两个用途

- **CSV** 是给**人和表格软件**看的：列名中文、时长同时给「mm:ss」和毫秒两列（后者才能排序），
  **带 UTF-8 BOM**——不带的话，简体中文环境里双击打开就是乱码。
- **JSON** 是给**程序和备份**用的：保留「哪个列表里有哪些曲目」这个结构，区分 `0` 和「没有」。

**BOM 的方向由格式自己决定**（`PlaybackExportFormat.needsBom`），不由调用方记着。
调用点上写 `withBom = format == PlaybackExportFormat.CSV` 也能跑，但那是一个**每个新格式都要
重新判断一次**的表达式，而它错了的表现是「导出的文件在某些软件里乱码」——没人会报 bug，
因为文件看起来是好的。放进枚举里之后，「BOM 对不对」变成一条可以断言的性质。

**刻意不做 M3U8**：那是「交给播放器按一下就播」的清单格式，混进导出菜单里会让用户以为
导出的文件能在别处直接打开。这不是本项目的定位。

### 三处取舍

1. **失效的条目照样导出，并在行里标记。** 播放列表本来就把「库里暂时找不到」的条目
   **保留在队列里**（v0.5.6 起就是这样），丢掉的话导出文件就和「这个播放器实际会播什么」
   对不上——而用户导出播放列表，八成就是为了知道这件事。所以给一列「文件已不在」，让接收方
   自己决定，而不是替他把这一行删掉。
2. **导出的是屏幕上那一份数据，不重新去读仓库。** 重读会引入时间差：删掉的记录又回来了、
   标题又变了，而用户在外面完全没法解释这件事。
3. **空的结果不是失败。** 一个播放列表都没建的用户点导出，报红字是冤枉他。
   所以「我浏览完了没有任何东西」和「我确实有东西，但可能空」是两回事——
   `PlaybackExportState.Empty` 只在**所有**集合都空的时候才出现（是 `any` 不是 `all`，
   这一点写到名字里：`List<PlaybackExportCollection>.hasExportableTracks`）。

### 两个入口

- 「最近」页 → 导出**全部播放记录**（一份集合，名字叫「播放记录」）。
- 播放列表**清单页** → 导出**全部**播放列表（每个列表一份集合，各自有名字）。
- 播放列表**详情页** → 只导出**打开的那一个**。

写文件走系统选择器（`ActivityResultContracts.CreateDocument`），**不需要任何存储权限**；
建议文件名是 `<清理过的集合名>-yyyyMMdd-HHmmss.csv`。写失败不抛异常，只返回 `false` 并记日志——
导出失败不该让界面崩掉。

### 导入：把导出反过来读一遍，但只有三个地方真的能反过来

入口只有**一个**：播放列表清单页顶部。详情页不导入，因为「导进来的东西放哪个列表」在那里
是一道没有答案的题；而清单页上的「导入」语义天然是「文件里的列表各建一个」。

**播放记录不在导入范围里。** 那是历史，不是清单——把一份旧播放记录导回去只会把「最近」页
弄得真伪难辨。需求的原文也是这个意思（「播放记录不需要」）。

剩下三件事各自都有一个「看起来更聪明、但是错的」的替代做法：

1. **按内容认格式，不按扩展名。** `decode()` 去掉 BOM 之后看头一个非空白字符是 `{` 还是 `[`，
   而不是看文件名。重命名一个文件太容易了（手机上的文件管理器换个名就改了扩展名），
   而判错的代价是「整份文件读不出来」。
2. **按列名认列，不按第几列。** 这一条是被**自己写的导出**逼出来的：CSV 的列名是**本地化**的
   （简体中文界面上导出来就是「标题 / 艺术家」），所以导入必须认简/英/繁三语列名
   （`msp_import_alias_*` 那十个 `string-array`）。按位置认列在「只导出一个列表」时还会额外崩：
   单集合的 CSV **没有「列表」列**（`withCollection` 是 `collections.size > 1` 时才加），
   列号整体错位一格。
3. **单集合的 CSV 用文件名当列表名。** 上面那个洞的补法不是「把「列表」列永远写上」，
   而是接受「文件名就是集合名」这件事——导出时建议的文件名本来就是集合名加时间戳，
   所以 `fallbackNameOf` 把 `-yyyyMMdd-HHmmss` 尾巴剪掉就得到了「播放记录」。
   反过来做（永远写「列表」列）的好处也有限：那只是一个每行都重复的值。

**同名不替用户决定。** 文件里的列表和现有列表重名时，弹窗问「合并还是新建」，并把两个选项的
后果写清楚（合并 = 把文件里的条目加进已有的那个；新建 = 另建一个同名的新列表）。
多个同名时多一个「剩下的都这样处理」的勾选框——因为一份文件里十来个列表全重名是正常情况
（本来就是从这台机器导出的），逐个问会把人问烦。选择由 `PlaylistImportOptions` 带着走，
「全部套用」记的是**选中的那一个答案**（`applyToAllAs`），而不是「以后都合并」这种固定语义。

合并的语义是**追加并去重**（按媒体 id）：已经在这个列表里的条目不会变成两条。
导进来的条目照样跑「库里查不到就标注、队列位置保留」那套既有规则，所以导一个满是不存在文件
的列表回来不会把列表弄坏（只会让每一行都带上「文件已不在」）。上限沿用播放列表自己的那一套：
100 个列表 / 每个 5000 项 / 名字 80 字（`PlaylistRules`），超了如实告诉用户，不静默丢数据。

## 六、验证

- **单元测试：165 个测试类 / 2187 个用例 / 0 跳过 / 0 失败 / 0 错误。**
- 这一版新增/强化的测试：
  - `core:data`：`PlaybackExportTest`（20 条，含 CSV 转义、失效条目保留、BOM 方向）、
    `PlaybackImportTest`（45 条，三语列名、缺列、行字段数不等、JSON 与 CSV 分派、文件名兜底、
    JSON 里有列表和没列表两种形状）、`PlaylistImporterTest`（27 条，同名决策、全部套用、
    去重、上限）、`PlaylistRulesTest`（含 `uniqueName` 重名递增 7 条）、
    `CustomAccentTest`（8 条，含编解码往返与脏输入）、`SubtitleWarningsTest`（3 条）。
  - `core:ui`：`CustomAccentColorsTest`（9 条，含明度夹取边界）。
  - `core:subtitle`：`SubtitleStringsTest`（5 条，逐条断言三语齐全）。
  - `core:translate`：`TranslationCacheTest`（15 条）、`TranslationCacheTextTest`（5 条）、
    `TranslationExporterTest`（9 条）。
  - `feature:library`：`PlaybackExportStateTest`（15 条）、`PlaylistImportStringsTest`（9 条）。
  - `feature:settings`：`ThemeSettingsTest`（+3 条）。
- **三语文案键对齐**：9 个带资源的模块逐一核对 `values/` / `values-en/` / `values-b+zh+Hant/`
  的键集合完全一致（`app_name` 只住在 `values/`，是有意的）。
  `AppLanguageTest` 里那条守卫这一版被**收窄**过一次：原先它同时禁「裸撇号」和「裸双引号」，
  后者把 9 条本来就正确的 `values-en` 文案（`MspText` 那句里带 `\n` 的多行帮助文本）判成了错的。
  aapt2 的真话是只禁裸撇号（`unescaped apostrophe in string`），裸双引号合法（`msp_keep_alive_switch_help`
  一直就是那样，正式包能打出来）——**守卫多查一条，会把正确的写法判成错**，所以删掉了双引号那一半。
- **导出这一层为什么能被单测**：`exportPlaybackTo(...)` 本身需要 `Context` 和 `android.net.Uri`，
  而 `feature:library` 的测试依赖只有 JUnit（没有 Robolectric）。与其造假对象让失败分支变成
  死代码，不如把两段纯逻辑**抽出来**——BOM 方向归格式自己（`needsBom`），
  「有没有东西可导」归一个命名清晰的扩展属性（`hasExportableTracks`）——然后对着它们断言。
  编码是否正确的把关留在 `core:data`（那里有 `Context`，测得到）。
  导入也一样：`PlaylistImporter` 收的是接口（`PlaylistImportSink`）而不是 `PlaylistStore`，
  于是「同名时问不问」「合并之后是几条」这类逻辑在单测里不用 Android 就能走完。
- **单测盖不住的两类失败（这一版真碰上了，都是发版前才现出来的）：**
  1. **库模块的 `values` 编译**只有 `:app:mergeDebugResources` / `assembleDebug` 会碰，
     `:feature:xxx:testDebugUnitTest` 一路绿灯。一句带裸撇号的英文文案让 `assembleDebug` 挂掉，
     而它的报错文案（`Invalid unicode escape sequence in string`）把原因指向了 `\u`——那句文案里
     根本没有 `\u`。只有拿 `aapt2 compile` 直接编那个文件才看得到真话。
  2. **Koin 的依赖图**：`PlaylistImporter(sink = get())` 要的是接口，而 `PlaylistStore` 只按具体类注册过。
     单测注入的是 Fake，永远不经过 Koin，所以整类错误对 2187 个用例完全不可见——
     真机上点开「播放列表」页当场 `NoDefinitionFoundException`。修法是显式绑一次接口
     （`single<PlaylistImportSink> { get<PlaylistStore>() }`，转发式注册保证两条路是同一个实例），
     而**验证方法只有一个：真机把新页面点开一遍**。

## 八、已知限制

1. **导入只认自己导出的那两种文件。** 导回来的必须是 CSV 或 JSON，而且必须带「标题 / 路径 /
   媒体 id」这三列（缺哪一列会直接说缺哪一列，不静默当空）。M3U8、`.srt` 等等都不是导入格式，
   也不能把「一份随便的表格」当成播放列表——宁可拒绝，不要猜出一个列表给用户。
   另外：**播放记录只有导出，没有导入**（那是历史，不是清单）。
2. **导入不会重新扫库，也不会自动去掉已失效的条目。** 文件里的条目原样进来（媒体 id 对得上
   就接回库里那一条），本机没有的照样占着位置、带上「文件已不在」标记——和播放列表一贯的做法一致。
3. **播放列表里的条目仍然没有保存「显示名字」**（与上一版相同）：从播放列表恢复的条目，
   字幕发现的那行日志会少一个名字。
4. **导出的是屏幕上的数据快照**，不是「导出那一刻的仓库状态」（第五节）；
   导入的合并是**追加并去重**，不会按文件里的顺序重排已有条目。
5. **自定义强调色没有「随手吸一个颜色」的入口**，只能拖三根滑块。
6. **翻译缓存清空之后，下一次翻译要重新付费**——这是清空的本意，但值得再说一次。
7. 位图字幕的微调与样式、封面不能手动换、32 位设备装不上、均衡器取决于设备——
   这些都与 v0.9.0 相同，见 `README.md` 的「已知限制」一节。

## 九、升级注意

- **`versionCode` 从 900 跳到 10000。** 这不是笔误：版本号公式是
  `major*10000 + minor*100 + patch`，而 `major` 这是第一次不是 0，所以那串数字从三位变成了五位。
  Android 只在**降级**时拒绝安装，所以覆盖安装不受影响；但如果你用过基于
  「versionCode 不超过三位」的脚本，它需要跟着改。
- **设置是向后兼容的**：新增的键（自定义强调色）在旧版本里不存在，读出来就是「没自定义过」，
  不需要迁移。反过来，回退到 v0.9.0 会忽略那个键，但**不会**删掉它。
- **翻译缓存格式没有变**，v0.9.0 攒下的缓存可以直接接着用（也就意味着第一次翻译不会
  因为它而变慢）。
- **导入不改存储格式**：导进来的列表走的是**原来那两条写路径**（新建一个列表 / 往列表里追加），
  只是包在一次 `store.edit` 里，所以播放列表的存储格式没有变，回退到旧版本也读得懂
  （旧版本看到的就只是「多了几个列表」）。
