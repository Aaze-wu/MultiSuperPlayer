## 二、清空识别缓存：两个数字、一次删除、三句确认

### 放在哪，为什么放在那

入口在 **设置 → 语音识别** 页面的**最末尾**，一个叫「生成的字幕」的分节：行标题
「清除生成的字幕」，右边是「清空」，行下面常驻一句说明（识别结果存在应用私有目录里、
不会写到片子旁边、不会上传，清除只删这些字幕）。

它**不在**页面中间那个「本机识别 / 云端识别」的分叉里：那两组设置选的是「用哪种方式识别」，
而**生成的字幕文件是同一批**（都在 `filesDir/generated_subtitles/`）。放进分叉里就会出现
「只有本机那一支能清缓存」这种按不到实际状态的设计。

### 为什么要报两个数字

界面显示的是「已缓存 3 份字幕 · 1.2 MB」，而不是只报份数：用户点「清空」真正想知道的是
「这东西占了我多少地方」，份数说不清这件事——一份两小时电影的字幕和一集 20 分钟的差好几倍。
体积用的是 `TimeFormat.fileSize`，与同一页「模型多大」那两行**同一个格式**，上下两个数字
才好比。

两个数都是 **stat 出来的，不读内容**：设置页要的只是两个数，把每份 SRT 都读进内存
（一部电影的字幕可以有几 MB）纯粹是打开设置页时白付的代价。

### 口径：0 字节不算一份，但它的字节照算

- **0 字节的文件不算「一份」**（写一半被系统杀掉的垃圾不该在界面上显示成「已缓存 1 份」），
  **但它的体积照样算进总量**——占的地方是真的，把它漏掉反而会让「清空之后还剩 0 B」
  这种状态看不见。
- 统计走的是**列目录**，不是遍历已知的媒体 uri：这一层不知道有哪些媒体，目录里现在有什么
  就是全部答案。**删除用的是同一个口径**，两处共用一个列目录的函数，才不会出现
  「统计说 3 份、清空删掉 2 份」。
- 目录还不存在时是空表，不是异常——从没用过语音识别的机器上，这一行就显示「还没有缓存」，
  并且**不显示「清空」按钮**（而不是画一个灰按钮让人去猜为什么点不动）。

### `.tmp` 残留一起删

正常路径产不出 `.tmp`（保存时先写临时文件再改名），留下的那份是「写一半被系统杀掉」的结果，
而它照样占磁盘。只删正常文件的话，用户会看到「已清空」之后体积还在——那是最容易让人
不再相信这个按钮的一种反馈。

### 删不掉时如实报

`clear()` 返回「是不是真的清干净了」，并且**不抛异常、也不假装成功**。失败时那一行会变成
「清空失败，还剩 2 份（1.2 MB）」——把剩下的量算出来告诉用户，而不是只写一句「清空失败」。
因为真正的失败现象是「我明明清过了，怎么还占着地方」，而一句没有数字的提示会被当成
无关痛痒的 toast。

### 确认框说三件事

按下「清空」后的确认框正文是：

> 会删掉 1 份已生成的字幕（603 B）。这些字幕是识别出来的，删掉之后要重新跑一遍识别
> （耗时约等于音频时长）。识别模型不会被删除。

三件一件都不能少：

- **数量**——没有数字的确认对话框只是让人多点一下；
- **代价**（要重跑识别，约等于音频时长）——这是按下去之后会后悔的那个点；
- **什么不会被删**（模型文件）——这句话是用户敢不敢按的关键。这一页上「清空」的邻居恰好是
  「删除模型」（那一项释放的是 78 MB 级别的空间，删了要重新下），不说清楚，刚下完模型的人
  会以为清缓存顺手把模型也清了。

**「清空缓存」与「删除模型」是两个按钮、两种代价**，所以没有合并成一个「清理」。

### 文案和数字住在同一个类里

`GeneratedSubtitleCacheStats(entries, bytes)` 是 `core:data` 里的一个 data class，三句话
（常态那句、失败那句、确认那句）都是它的方法，而不是搬到设置页去用字符串模板拼。理由：
这三句话的每个参数都由这两个数算出来，分开之后「一份都没有时说什么」这类分支就会在界面里
再写一遍（然后写漏）。副作用也正好是好的：它们能在纯 JVM 单测里被断言
（见 `GeneratedSubtitleCacheTextTest`）。

## 三、播放时禁止熄屏：三个条件、一个窗口标志位

### 判据是一个纯函数

```
shouldKeepScreenOn(isPlaying, preference, inPip)
    = 正在播放 && 设置开启 && 不在画中画
```

拆成纯函数是为了让「什么时候该亮」这件事能被单测穷尽（见第七节），而 Composable 里只剩
「把标志位加上 / 拿掉」这两行。

### 为什么是窗口标志位，而不是 `view.keepScreenOn`

上一版播放页的做法是 `PlayerVideoSurface` 里的 `view.keepScreenOn = isPlaying`。它有一个
很难发现的洞：**音频播放时根本没有 `PlayerView`**（音频版面画的是封面与波形），所以那行代码
对音频一点作用都没有——「听歌时不熄屏」这个诉求从头到尾没被实现过，而且不报错。

现在用的是 **Activity 窗口**上的 `FLAG_KEEP_SCREEN_ON`，视频与音频两种版面都覆盖。

### 移除标志位是功能的一半

`DisposableEffect(activity, keepOn)` 在 `onDispose` 里 `clearFlags`。不加这一句的话，
暂停、退出播放页、转成画中画之后标志位还留在窗口上，屏幕会**一直**亮着——一个「只在播放时
生效」的功能就是这么变成「永久常亮」的，而且症状（费电）要过很久才会被怀疑到这里。

`activity` 也在 `DisposableEffect` 的 key 里：`window` 是 Activity 的属性，转屏后
（未声明 configChanges 的情况下）会换一个 Activity，key 不带它就会一直握着旧窗口的标志位。

### 「暂停就还给系统」是你选的语义

一开始就定的是：**只有真的在播放时才拦着系统熄屏**。暂停、播完、进入画中画、退出播放页
都立刻把屏幕还给系统——暂停那一刻正是用户最想放下手机的时候。这一条写在了设置项的说明里
（「只在真的在播放时生效：暂停之后屏幕就可以按系统超时熄灭了」），不是隐藏行为。

标志位挂在窗口上还带来一个符合直觉的副作用：**按 Home 键回到桌面之后它自然不生效**，
后台继续播音频不会让屏幕亮着。

### 持久化开关：默认开，且必须 `?: true`

- 键名 `playback.keep_screen_on_while_playing`，属性 `PlaybackSettings.keepScreenOnWhilePlaying`；
- 它是 `Boolean?`，**从未设置过是 `null` 而不是 `false`**；消费方一律写
  `it.keepScreenOnWhilePlaying ?: true`。用 `== true` 会把「从未设置过」读成关闭——
  装机默认开启就只能靠 `?: true` 表达。这是本项目所有「默认开」开关的统一约定。
- 设置 → 播放 里是 `SettingsSwitchRow` + 常驻说明；关掉之后设置首页「播放」的摘要会多一个
  尾标「不阻止熄屏」。

### 播放页上的临时开关

控制条上多了一个芯片，它说的话是**屏幕接下来会怎样**，而不是功能叫什么：

| 状态 | 芯片文案 | 无障碍名（TalkBack 读的） |
| --- | --- | --- |
| 开 | 屏幕常亮 | 播放时禁止熄屏，屏幕常亮，已启用 |
| 关 | 允许熄屏 | 播放时禁止熄屏，允许熄屏 |

芯片的 `active` 跟着当前是否常亮走。用「屏幕会怎样」而不是「功能开没开」，是因为用户在这一页
关心的是「我接下来会不会黑屏」，而「播放时禁止熄屏：开 / 关」这种说法需要先在脑子里
做一次否定运算。

### 临时开关**不写回**设置

`PlayerUiState.keepScreenOnOverride: Boolean? = null` + `keepScreenOn(default) = override ?: default`，
跟随既有的 `aspectRatioOverride`（画面比例）那套模式。理由：**这一次别熄屏**与
**我的默认偏好**是两件事；写回的话，一次临时切换会永久改掉默认值，而用户没有第二个地方
能看到它被改掉了。

代价是明确的，也写进了已知限制：转屏、退出播放页再进来，芯片会回到设置里的值。

顺带一处命名：状态类上的方法是 `applyKeepScreenOn(value: Boolean?)` 而不是
`setKeepScreenOn`——`keepScreenOnOverride` 这个属性在 JVM 上会生成 `setKeepScreenOn…`
形态的方法名，同名会撞 `Platform declaration clash`。

## 四、为什么这一版没有 `beta.1`

1.1.0 那一档先发过 beta，理由是「打开方式 / 分享」碰的是系统的 intent 解析与清单匹配：
**匹配规则由系统决定，`Intent` 在 JVM 单测里是空壳**，只能在真机上才发现问题。

这一版两处都不碰系统行为：一块是对私有目录里文件的统计与删除，一块是窗口上的一个标志位。
判据、取舍、文案全部是纯函数，能在 JVM 单测里钉死；剩下「真的没熄屏」这一件必须出门去验
（第七节有一张表），但它不会因为机型或系统版本而变成另一件事。风险面在应用内部、
不在系统边界上，所以直接发正式版。

## 六、测试怎么盖住这两处，以及一个构建期陷阱

两处都是「纯函数 + 一层薄壳」的结构：

- **常亮**：`PlayerKeepScreenOnRules.shouldKeepScreenOn` 是纯函数；`PlayerUiState.keepScreenOn(default)`
  也是；`PlayerKeepScreenOnEffect` 里只剩 `addFlags` / `clearFlags` 两行，没有可测的逻辑。
- **缓存**：`GeneratedSubtitleCacheStats`（两个数字 + 三句话）与统计口径（0 字节算不算一份）
  都能在 JVM 里直接喂数据测，不必去构造真实的磁盘状态（那种测试会因为磁盘报错而时红时绿）。
  只有「目录里真实的文件到底删掉了没有」必须出门验。

另外记录一个**这一版踩到并确认了的构建期陷阱**，因为它会让「文案守卫根本没跑」这件事
完全静默：

> `res/values*/strings.xml` **不是** JVM 单测任务的声明输入（字符串是共享代码在运行时
> 从真实文件里读的）。所以改完三语文案之后跑 `gradlew test`，这些测试任务会被判成
> `UP-TO-DATE`，甚至**从构建缓存里 `FROM-CACHE` 恢复**——于是改坏的文案照样「全绿」。
> 可靠做法是删掉各模块的 `build/test-results` 并加 `--no-build-cache`；
> `cleanTest` 只清掉根工程的 `:app:test*UnitTest`，库模块照样跳过。

## 九、已知限制

- **清空之后要重新跑一遍识别**（耗时约等于音频时长）。清除只删本机识别出来的字幕文件；
  已经下载的识别模型、已经人工修正过的译文、续播位置、播放列表都不受影响。
- **「播放时禁止熄屏」只在真的在播放时生效**：暂停、播完、进入画中画、退出播放页都会立刻
  把屏幕还给系统。这是设计，不是缺陷。
- **播放页上的临时开关不写回设置**：转屏、退出播放页再进来会回到设置里的值。
- **画中画里不常亮**（有意为之）：那一态用户在看别的东西，本应用不该霸着屏幕。
- 沿用 1.1.0 的全部已知限制：网络播放没有自定义请求头 / User-Agent 的入口；只支持
  http / https（`rtsp:` / `rtmp:` / `magnet:` 判为非法地址）；外部打开与分享进来的条目不进
  「最近播放」，且与媒体库里的同一个文件算两个身份（续播位置不共享）；没有自定义 scheme；
  不做系统音乐选择器；「允许不受信任的证书」打开后不再校验任何 https 证书；
  不含 32 位原生库。

## 十、升级注意

- `versionCode` **10200 > 10100**，可直接覆盖安装 v1.1.0（以及更早的版本），不报降级。
- **「播放时禁止熄屏」默认开启**，升级后不需要做任何事；不想用它就在 设置 → 播放 里关掉
  （关掉之后设置首页「播放」的摘要会显示「不阻止熄屏」，说明当前状态）。
- 清空生成的字幕只动应用私有目录里的 `generated_subtitles/`，与模型目录、设置、续播记录
  互不影响；卸载或清数据会一起丢掉。
- 关于页不显示「测试版」徽章（正式版不显示徽章）。
