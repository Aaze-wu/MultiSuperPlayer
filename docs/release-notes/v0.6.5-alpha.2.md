## 一、这一版做了什么

只修一个 bug：**「上一首」要按两次才切得上一条**。

### 1. 症状与根因

用户报的原话：*「在音视频播放一段时间后，点击上一首，会先回到当前音视频首，再点一次才能切到上一个。」*

根因在播放内核（Media3 `ExoPlayer`）而不是我们的代码里。反编译 `BasePlayer.seekToPrevious()`
可以看到它其实有**两个分支**：

```text
有上一条 且 当前播放位置 <= 3000 ms  → 切到上一条
否则                               → 回到本条目开头（seekToCurrentItem(0L)）
```

那个 3000 ms 是 `ExoPlayer.DEFAULT_MAX_SEEK_TO_PREVIOUS_POSITION_MS`，也就是行业惯例里的
「播放超过 3 秒后，按「上一首」= 重播当前项」（老式 CD 机就是这么做的）。所以这个行为
**不是 bug 而是内核的默认设计**，只是在这个 App 里它变成了「先重播、再点才走」的两步操作。

### 2. 改法：两个入口必须一起改

这一版把「上一首」定成**按一次就切上一条**，并把决定收进一个纯函数
`PreviousTrackRules.actionFor(hasPreviousItem)`（有上一条 ⇒ 切上一条；没有 ⇒ 回到本条目开头）。

但同一个「上一首」在这个 App 里有**两条完全不同的入口**：

| 入口 | 走到哪 | 改法 |
| --- | --- | --- |
| 播放页 / 迷你播放器上的「上一首」按钮 | 我们的 `ExoPlayerController.skipToPrevious()` | 不再调 `seekToPrevious()`，改按 `PreviousTrackRules` 分支调用 |
| **通知栏 / 锁屏 / 耳机线上的「上一首」** | Media3 `MediaSession` 直接调内核 `seekToPrevious()` | **那条路上没有一行我们的代码**，只能改内核配置 |

第二条是关键：`MediaSessionStub` 收到媒体按键后走 `queueSessionTaskWithPlayerCommand(…, 7, …)`，
最终调的就是 `player.seekToPrevious()`（`PlayerWrapper` 只是一个纯转发的 `ForwardingPlayer`），
而本项目**没有覆写 `MediaSession.Callback`**，应用层插不进去。所以只能把内核的阈值调掉：

```kotlin
setMaxSeekToPreviousPositionMs(Long.MAX_VALUE)   // ⇒ 永不「超过阈值」⇒ 永远走「切上一条」那一支
```

**只改一处就会出现「应用里按一下切走、通知栏得按两下」**，而且这种不一致没有任何单元测试能发现——
所以这个决定同时写进了 `PreviousTrackRules` 的 KDoc、`ExoPlayerController` 的注释和
`PlaybackController` 的接口文档里。

### 3. 队列里没有上一条时：回到本条目开头

内核的 `seekToPreviousMediaItem()` 在队首时会 `ignoreSeek()`，即**静默什么都不做**。
如果照搬它，单条队列（或停在第一条且循环关闭）时「上一首」按钮就变成死的——按下去毫无反应。
所以那个分支明确退化成 `seekTo(0L)`（回到本条目开头），这也正是 `seekToPrevious()` 在
「没有上一条」时自己会做的事。

## 二、真机验证结果

在 `emulator-5554` 上用 22 条队列（aac / ac3 / Alarm01…audio1 / dts …）实测：

| 项 | 操作 | 结果 |
| --- | --- | --- |
| 应用内 · 有上一条且已播 > 3 秒 | 在 `dts` 播到 00:07 时点播放页「上一首」**一次** | ✅ 直接切回 `audio1`（修复前会先重播 `dts`） |
| 媒体按键 · 有上一条且已播 > 3 秒 | 在 `dts` 播到 00:06 时注入 `KEYCODE_MEDIA_PREVIOUS` **一次** | ✅ 直接切回 `audio1`（验证的正是 `setMaxSeekToPreviousPositionMs` 那一句） |
| 应用内 · 队列里没有上一条 | 在队列第一条 `aac` 播到 00:08 时点「上一首」 | ✅ 回到本条目开头（00:02），**不是按了没反应** |
| 媒体按键 · 队列里没有上一条 | 在 `aac` 播到 00:12 时注入 `KEYCODE_MEDIA_PREVIOUS` | ✅ 回到本条目开头（00:02） |

「切走」与「重播」这两种结果在界面上本来是同一种观感（都是时间回到 0），所以四项都是
**按标题**判断的：标题变成上一条才算切走，标题没变只把进度归零才算重播。

## 三、已知取舍

1. **「播放超过几秒先重播当前项」这个行为没有了。** 这是这一版唯一的行为变更，也是有意为之：
   和「点一下切上一条、点两下仍然回到本条目开头」相比，前者可预期，后者要用户记住一个
   看不见的 3 秒窗口。想同时保留两种语义需要自定义 `MediaSession.Callback` 或改成
   长按/双击之类的入口，本版不做。
2. **阈值是全局的，不区分场景。** `setMaxSeekToPreviousPositionMs` 影响所有
   `seekToPrevious()` 调用者，包括以后可能新增的入口。这是「只能用内核配置改」的必然代价，
   换来的是一致性。
3. **`seekToPreviousMediaItem()` 不做位置判断，所以「上一首」在任何时刻含义相同**——
   即使刚播了 1 秒也是切上一条。这与第 1 条是同一件事的两面。

## 四、升级提示

- 从 v0.6.5-alpha.1 升级**不需要任何迁移**：本版只改了播放控制的一处行为，没有动设置项、
  没有动字幕/翻译/识别相关的存储格式。
- **versionCode 不变（仍是 605）**：同一个版本号段内的 alpha 迭代共用同一个 versionCode 是有意设计。
- 队列、播放位置记录、A-B 循环、睡眠定时等既有功能不受影响；A-B 循环的「上一首的 A 标记」
  指的是别的东西，与本次无关。
