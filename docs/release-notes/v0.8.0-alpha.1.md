## 一、这一版做了什么

三件事，第一件是另外两件的前提：

1. **内嵌字幕「整轨预读」。** 自己驱动 Media3 的解封装器把片源里那条字幕轨**整条**读出来，
   得到一张完整的台词表，而不是像以前那样只能拿到「已经播到的那一段」。
   预读在后台做，播放不等它；读不出来时**原样退回**原来那张流式表，不报错、不黑屏。
2. **字幕速率（比例微调）。** 0.96× / 0.98× / 1.00× / 1.02× / 1.04× 五档快速选，
   另有 ±0.01 / ±0.10 的累加按钮细调，可调范围 0.90× ~ 1.10×。
   它和「字幕时间轴微调」是**两件事**：时间轴是整体平移（全片每一句都早/晚同样多），
   速率是**比例缩放**（越到后面偏得越多）。片源和字幕的帧率对不上时只有速率能修——
   用平移把开头调准，就一定会把结尾调错。
3. **音频页的歌词空间重排（用户本版新增要求）。** 竖屏改为「封面给歌词让位」，
   横屏把芯片与传输控制搬进左栏封面下方，右栏整栏留给歌词。

前两件事本来排在 v0.7.0-alpha.3，版号已按用户要求直接用 0.8。

## 二、为什么速率必须等「整轨预读」

速率本身只是「把当前播放位置乘一个比例再查表」：`查表时刻 = 播放位置 × 速率 − 时间轴偏移`。
它在 v0.7.0-alpha.2 被真机实测拦了下来，原因不在算术，而在**表里有没有那一行**：

Media3 的 `onCues` 回调语义是「**此刻**该显示什么」——它不给未来的行。
所以那张表是流式攒出来的，只覆盖「已经播过」的部分，而且**最后一条 cue 的结束时间是
`Long.MAX_VALUE`**（表示「到现在为止有效」，因为 `Cue` 本身只有开始时间）。于是：

| 方向 | 查表时刻 | 结果 |
| --- | --- | --- |
| 调慢（0.96×） | 落到之前那一句 | ✅ 生效（实测 00:37 → `第 35 秒的台词`） |
| 调快（1.10×） | 落到表尾之后 | ❌ **空操作**，永远退回那条开放 cue（实测 00:37 → `第 37 秒的台词`） |
| 调慢多一点（0.90×） | 落到表起点之前 | ❌ 落进空档，整句消失（实测 00:26 → 无字幕） |

**预读给出的结束时间是真实的**：容器里每条字幕样本自带时长（Matroska 把时长写进字幕样本的
结束时间码），Media3 把它带进 `CuesWithTiming.durationUs`，所以不需要「等下一批到来才回填」。
表尾不再是一条无限长的 cue，两个方向于是都成立——这正是这一点在真机上被逐档验证过的
（见 §四）。

### 一处更正：v0.7.0-alpha.2 的说明写错了根因

那一版的发行说明在「字幕速率：本来在这一版，已推迟到 alpha.3」一节里写的是
「`EmbeddedSubtitleState.receive` 每次只把**刚读到的那一批**放回状态里，表里几乎只有最近一句」。
**这句话是错的**：`receive` 是**累加**的（它还要负责回填结束时间、去重、保持有序）。
真实原因就是上面那三条——表只覆盖已播过的一段，且表尾是一条结束时间为「无限」的 cue。
那个文件里的实测数据（0.90× / 0.96× / 1.10× 三行）都是真实观测，只有「为什么」那一句写错了，
已在本版一并更正。

## 三、实现层面的三个坑（都只在真机上露头）

### 1. 预读出来的每一句时刻都多了一倍

复用了 Media3 公开的 `CueDecoder` 之后，整表看起来完全正常：条数对、顺序对、单调递增。
只有**时间范围**不对——46.88 秒时播出「第 23 秒的台词」。

原因是两边都以为自己该把起点折进去：`CueDecoder.decode(startTimeUs, …)` 的 `startTimeUs`
只用来填 `CuesWithTiming.startTimeUs`，而 Media3 的 `SubtitleTranscodingTrackOutput.outputSample()`
**早就**把它折进了样本时刻（`outputSampleTimeUs = timeUs + cuesWithTiming.startTimeUs`）。
再传一次 `timeUs` 就是 `2 × timeUs`。修法是起点取 `C.TIME_UNSET`，让样本时刻说话。

⇒ 这类错误的教训很直白：**它靠「形状」发现不了**（条数、顺序、单调性全都正常），
只能靠「范围」。所以预读完成的日志打的是时间范围而不是条数：
`整轨预读结束：… → Ready（30 行，20023ms → 50023ms）`。

### 2. 预读把日志刷爆了（而且刷的内容是假的）

修好之后，一次预读会让 logcat 多出 **4085 条** `字节账对不上`、`MSP/` 相关行共 **4099 行**。

根因是 `PreReadTrackOutput.sampleMetadata()` 里的字节账自检对**每一条轨**都在跑，
包括那些「我们根本不收集、只是把字节读走」的轨（一个文件里三条字幕轨时，
另外两条也会各自被记账一次）。修法是这个方法开头就 `if (!wanted) return`。
修后同一个素材：`字节账对不上` **0 条**、`MSP/` **4 行**。

### 3. 横屏版面的判据在浮点下会来回翻

「控件搬不搬进左栏」的判据原来写成「先算出权重，再乘回屏宽看够不够」：

```
W × (320dp ÷ W) ≥ 320dp      // 数学上恒成立，浮点下不成立
```

实测在 **1220dp** 的窗口上左边会算成 `319.99997` ⇒ 同一个屏宽一会儿搬、一会儿不搬。
改成先乘后比：

```
W × 45% ≥ 320dp              // 乘一个正常数在浮点下是单调的
```

分界线因此是 `320 ÷ 0.45 ≈ 711dp`。搬得动时左栏宽度**恒为 320dp**（权重取的是
「刚好够装下那两排」的比例），多出来的宽度全部归歌词——否则平板上歌词会比手机上还窄。

## 四、音频页：谁给歌词让位

「留给歌词的空间太少」不是把某个 dp 调小一点能解决的问题：音频页的高度被切成好几段
（封面 / 标题 / 进度条 / 功能芯片 / 传输控制 / 会话芯片），**每一段都是定高的**，
只有歌词拿剩下的，所以屏幕一矮被挤掉的全是歌词，而且是按比例挤的——
模拟器上看着还行，换台机器就只剩两行。规则抽成了纯函数 `AudioLyricsSpaceRules`
（和 `AudioLandscapeRules` 同一条理由：Compose 布局跑不进 JVM 单测，「判断」可以）。

**竖屏：封面是装饰，歌词是内容。**

- 封面边长 = `min(112dp, 舞台高 − 200dp歌词下限 − 12dp间距)`；
- 小于 **32dp 就完全不画**，连那道 12dp 的空隙一起收掉（否则「封面已经让位了」，
  歌词仍被一条空白压着）。所以封面尺寸**只有两档**：要么 ≥32dp，要么 0——中间没有值。
- 歌词区保底 200dp（约 3 行半，含它自己的 48dp 内边距）。

**横屏：控件块在歌词下面，它多高歌词就少多高**（实测约 172dp ≈ 4 行），所以能搬就搬到左栏去。

- 屏宽 ≥ 711dp：**芯片 + 传输控制搬进左栏**（封面和标题下方），右栏只剩歌词 + 进度条。
  左栏要为这两排预留 120dp 高度，否则封面会把它们顶出屏幕。
- 屏宽 < 711dp（分屏、小屏老设备）：**退回原版面**——控件照旧压在歌词下面，
  那里的歌词本来也够看。

**两种情况都可能把歌词压得很紧**，那时歌词自己把内边距从 24dp 收窄到 16dp / 8dp
（行距 12dp → 8dp），换回来大约半行。**字号不变**：缩字号会让一份歌词在两种屏上看起来是两份。

## 六、已知限制

- **预读要顺序扫一遍整个文件。** 字幕样本在容器里和音视频交错存放，「读完整条字幕轨」
  就等于把文件顺序读一遍。播放不等它（读不到就一直用流式表），**但几十 GB 的片源要读很久**，
  这段时间里速率对「还没读到的部分」仍可能不准——所以面板上有一句
  `正在预读字幕…`，失败时改成 `预读字幕失败，速率调整可能不准`。
- **预读失败的具体原因只在日志里。** 认不出封装格式 / 文件里找不到那条轨 / 一条台词都没有 /
  读取出错，这四种在面板上是同一句话（`EmbeddedPreReadReason` 只进日志）。
- **只对本地文件预读。** 网络流不能为了字幕把整个流下载一遍 ⇒ `Off`（不适用，不报错）。
- **内嵌位图字幕（PGS / VobSub / DVB）仍然不列出、不显示、也不解释原因**，排在 v0.9.0-alpha.1；
  预读对它们同样是 `Off`（解出来是图片，我们的层画不出来）。
- **预读表是整表替换，没有「先给一半」的渐进发布。** 中途换表会让 cue 的 `index` 漂移，
  而人工译文是按 `index + 原文` 存的（`TranslationEditsStore`）——译文会串行。
  所以要么用流式表，要么用预读表，切换只发生一次。
- **速率是「本次播放」的状态**：换条目归零、不记住（与时间轴偏移一致）。它不是一个设置项。
- 更新系统与后台保活的限制同 v0.7.0-alpha.1（未变）。

## 七、这一版的测试

- 全量：`testDebugUnitTest` + `testReleaseUnitTest` + `assembleDebug` → `BUILD SUCCESSFUL`
- 用例：**147 suites / 1860 cases / 0 failures / 0 errors**（两个 variant 一致；
  报告目录整个删掉后重新全量跑过一遍，不是增量刷新的结果），上一版是 144 / 1789
- 增量 71 条 = 新增文件 32 + 16 + 13 条，加在已有文件里的 10 条
- 新增 / 改动：
  - `EmbeddedPreReadTest`（新增，32 条）：不预读的三种理由（网络流 / 没有选中的文本轨 / 位图字幕）、
    轨匹配键只用语言+标签（MIME 两边一定不同）、两条同语种同标签的轨在「条数不一致」时**宁可失败也不猜**、
    样本 → cue 表的时长规则（有真实时长就用它、缺失时退回下一条的起点、最后一条用 10 秒兜底、
    绝不出 `Long.MAX_VALUE`、至少 1ms）、时刻约定（cue 包用样本时刻，不再叠加起点）、
    状态描写（`Ready` 打范围而不是打条数）。
  - `AudioLyricsSpaceRulesTest`（新增，16 条）：封面的四档退让与「中间没有值」、`portraitArtworkSize` /
    `portraitLyricsHeight` 成对使用（封面为 0 时空隙一起收）、紧凑阈值、横屏判据在 711dp 两侧的方向、
    退化输入（0 / 无界）给出确定答案。
  - `SubtitleRateTest`（新增，13 条）：五档与累加步长的取值、钳位区间、`查表时刻 = 位置 × 速率 − 偏移`、
    换条目归零。
  - `SubtitleEmbeddedClaimTest` / `SubtitleEmbeddedTrackTextTest` / `SubtitleStateResolutionTest`
    补上预读与速率接进状态之后的新组合：整表**替换**流式表（不是并起来——并起来会让同一个
    时间点有两条 cue，屏幕上同一句台词上下各一遍）、刚切进片子就能出字幕、
    预读失败/不适用时照旧走流式（把 `Failed` 当成「没有字幕」会让一个纯优化把字幕吃掉）、
    `Reading` / `Failed` / `Ready` 三种阶段各自在面板上说什么、速率有没有真的带进状态。
  - 三套语言资源键双向对齐（新增 6 个键：预读进行时 / 预读失败 / 字幕速率 / 速率当前值 /
    速率步长 / 速率提示语）。
- **一处覆盖不到的地方**：`CueDecoder`（`application/x-media3-cues`）分支只在「跨容器转码过的字幕轨」
  上才走到，而本地的 Matroska/SRT 素材走的是原始 SRT 路径（用 `SubtitleParser` 自己解析）——
  所以那段 `Parcel` 解码本身只能在真机上验证，单测覆盖的是它的**起点约定**
  （`cuePacketSampleOf`，也就是 §三.1 那个 bug 的修复）。
- 本版**没有**做「音视频同步」（用户已明确不做），也没有做此前排给 0.8 的
  拖动排序自动滚动与均衡器——那两项的排期待定。
