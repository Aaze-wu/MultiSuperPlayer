# v1.2.1 字幕匹配：带发行标记的文件名 / 系统文件选择器添加的目录

发布日期：2026-10-09
基于版本：v1.2.0

## 一、这一版做了什么

| 问题 | 症状 | 修在哪 |
| --- | --- | --- |
| 带发行标记（`[电影天堂www.dygod.net]片名 HD1080p 国语中字.mp4`）的文件名配不上干净的字幕名（`片名.chs.srt`） | 字幕面板一直说找不到，手动选一次又能用 | `core:data` 的 `SubtitleFileNaming` |
| 用**系统文件选择器**添加的目录，里面的字幕一条都查不到 | 同一个文件夹用「内部存储」加进去就正常，用文件选择器加进去就找不到 | `core:model` 的 `BrowserEntry` / `Playlist` |

两处都是**静默失效**：不报错、不崩溃、也没有日志，界面上只是「没有字幕」。
所以这一版的重点不在改了多少代码，而在**把这两类失效各自钉上一条不会退化的判据**（第六节）。

既有能力（媒体库、浏览、最近、播放列表、字幕、翻译、网络播放、外部打开与分享、
清空识别缓存、播放时禁止熄屏）一行没动。

## 二、第一个 bug：不是「文件名太长」，是「片名外面挂了东西」

### 症状骗人，原因与长度无关

报告写的是「长度较长的文件名（含中文和空格等特殊字符）无法正常自动识别字幕」。
真凶是**发行标记**：中文发布组的书写习惯是把组名 / 站点名 / 画质标签整段挂在片名前后——

```
[电影天堂www.dygod.net]某某电影 HD1080p 国语中字 修复版.mp4
某某电影.chs.srt
```

字幕名是干净的，视频名是多出来的那一个。**名字越长、空格越多，挂着的段就越多**，
所以看起来像「长文件名不认识」，其实写短一点带同样的标记一样匹配不上。

### 为什么会配不上：标记被粘进片名里

比较用的是**归一化**后的名字（只留字母数字，把所有分隔符丢掉），
于是 `[电影天堂www.dygod.net]某某电影` 变成 `电影天堂wwwdygodnet某某电影`——
与 `某某电影` 既不相等、也不互为前缀，两条明明对得上的文件被判成「不是它的字幕」。

### 修法：不猜，两种写法都当候选

同一段方括号，在视频名里常常装**片名**，在字幕名里常常装**发布组**：

- `[阿凡达：水之道].Avatar.The.Way.of.Water.2160p.mkv` ← 删掉就再也认不出是哪部片
- `[某某字幕组]某某电影.chs.srt` ← 不删就永远对不上 `某某电影.mkv`

**「这段括号里到底是不是片名」在文件名里没有可靠判据**
（`[电影天堂www.dygod.net]` 与 `[阿凡达：水之道]` 的结构一模一样），所以这里不猜：
每条名字都生成**两种写法**（原样 / 去掉装饰段），两两比一遍，**取最高分**。

这不是「两种证据取平均」——它们是同一个东西的两种叫法，一种相等就足以断定是同一条。

### 装饰段的判据：整段被一对括号包住

- 逐对写清楚（`[]`、`【】`、`〖〗`、`{}`、`《》`、`<>`、`()`、`（）`），
  而不是用一个「所有括号」的字符类：**配对不完整时（`[a.b`）整段保持原样**，
  只吃掉半截等于把片名改了。
- **两处例外，整段保留**（它们是片名的一部分）：
  - **光是年份**（`The.Thing.(1982)` / `(2011)`）：那正是区分翻拍片的东西，
    删掉会让两部不同的电影变成同一个核心名；
  - **圆括号里的纯中文短语**（`（上）`、`（下）`、`（剧场版）`）：
    发行标记几乎全是 ASCII（`(Uncut)` / `(1080p)` / `(Director's Cut)`），
    而中文短语多半是片名，删掉「上 / 下」会让上下两部互相匹配。
- 去装饰之后**什么都不剩**时（`《片名》.srt` 这种整段被包起来的），
  不去装饰的那一份仍在候选里——否则这条文件会从候选里静默消失。

### 集号那一侧是**不对称**的，这条必须说清楚

- **字幕名这一侧总是把集号也去掉**：`某某电视剧.mkv` 配 `某某电视剧 第01集.srt`
  是最常见的用法，字幕多写一个集号不该让匹配降一格。
- **媒体名这一侧只在「两侧都写了集号、而且指向同一集」时才去掉**：
  媒体名是「这一条到底是第几集」的唯一来源。凭空去掉会把 `Show.other.srt`
  变成 `Show.S01E01.mkv` 的匹配——**挂错集比完全没有字幕更糟**，
  用户会以为播放器把字幕串台了，而且这种「看起来正常的错误」会一路用到
  他发现台词对不上为止。

另外补了一条**跨写法**的退让：视频写 `Show.S01E01.1080p.mkv`、字幕写
`Show 第01集.chs.srt`（两者常常来自不同的发布组），片名明明一样，
却因为集号写法不同而互相不认识——两侧都写了集号且指向同一集时，
把集号从比较里去掉再比一次（上面那条否决已经保证不会挂错集）。

### 一个**故意没做**的取舍

没有实现「简体 ↔ 繁体互认」：`某某电影.chs.srt` 仍然配不上 `某某電影.mkv`。
那需要引入一套简繁映射表或依赖系统 ICU 转换，属于新功能而不是修 bug，
留到以后的版本单独处理。

## 三、第二个 bug：浏览页的 SAF 目录，来源被判成了文件系统

### 「来源」这一个字段决定去哪儿找字幕

媒体条目的 `source` 决定字幕去哪儿查（见 `core:data` 的 `subtitleLookupOf`）：

| 来源 | 字幕怎么找 |
| --- | --- |
| 文件系统 | 把**路径的上一级目录**拿出来列一遍 |
| SAF | 拿 **document uri** 去问 provider 要兄弟文件 |
| 系统媒体库 | 按 MediaStore 的 `relative_path` 查 |
| 网络 / 分享 | 不查 |

### 错在哪

浏览页里能点开的目录有两种：本地卷（`ref` 是绝对路径）和用户用**系统文件选择器**
授权的 SAF 目录（`ref` 是 `content://…` 的 document uri）。

`BrowserEntry.toMediaEntry()` 把来源**写死成 `MediaSource.FILE_SYSTEM`**。
于是 SAF 目录里的文件被当成路径去「取上一级目录」，取到的是
`content://com.android.externalstorage.documents/tree/…/document`
这串**字符串**而不是任何真实目录 ⇒ 字幕就在同一个文件夹里躺着，一条也找不到。

三个特征让这个 bug 很难定位：

1. **与文件名无关**：整个目录都是这样，所以不会联想到「来源判错」；
2. **不报错**：列目录失败只是「没找到字幕」，日志里没有异常；
3. **换成「内部存储」再加一次就正常**：同一个文件夹、同样的文件，
   换个入口就好了——于是很容易被归到「文件选择器不好用」。

### 修法：来源从 `ref` 推

`ref` 的形态就是来源本身：

- `content://…` ⇒ `MediaSource.SAF_TREE`（浏览页里的 document uri 都是
  `DocumentsContract.buildDocumentUriUsingTree` 拼出来的，带着 tree 段，
  正是 SAF 那一支需要的东西）；
- 其余 ⇒ `MediaSource.FILE_SYSTEM`。

判据只能是**前缀**，不能是「哪个字段恰好有值」。

### 顺带修掉第二个入口：播放列表回放

条目写进播放列表之后就只剩一个字符串了。回放时靠
`PlaylistItem.sourceOf(mediaId)` 把来源还原出来，而那里原本**只分了两支**
（「浏览页前缀 / 其余都是媒体库」），`file:` 后面是什么它不看 ⇒
从播放列表点开 SAF 目录里的文件，第二个 bug 会原样复现一遍。

现在这一支再分一层：`file:` 后面的 `ref` 交给同一个 `sourceOfRef` 判。
同时把 `if / else` 改成了 `when`：

> 原本只有两个分支，于是「新增一个来源」这件事在编译期没有任何提示，
> 新来源的条目回放时会**静默退化成媒体库**。改成 `when` 之后至少每条前缀
> 各占一行，加来源时这里会在 diff 里显形。

## 四、为什么这一版没有 `beta.1`

两处改的都是**纯函数与来源判定**：`ref` 怎么判来源、名字怎么生成候选、
哪些段该保留、集号什么时候才能忽略——全部能在 JVM 单测里穷尽。
没有清单变化、没有新权限、没有系统 intent 匹配，也没有新的系统 API。

**但这一版的真机验证确实抓到过一个单测永远抓不到的问题**（见第六节后半），
它恰好说明了另一件事：`beta.1` 不是「有风险就发」的仪式，
真正的判据是**这套验证能不能在本地做完**。这一版能，所以直接发正式版。

## 六、测试怎么盖住这两处，以及一个单测**永远**盖不住的东西

### 盖住的那部分

- **匹配规则**（`core:data` 的 `SubtitleFileNaming`）：全部是纯函数，
  喂两个文件名给分就行。`SubtitleFileNamingTest` 本版 18 → **24** 条，
  新增的重点是**反向锁**而不是正向：
  - `片名整个被方括号包住时不能当装饰删掉`（`[阿凡达：水之道]` 这类，
    去掉装饰就什么都不剩了）；
  - `括号里的年份是片名的一部分`（`The.Thing.(1982)` 与 `(2011)` 不能变成同一条）；
  - `只有一边写了集号时不许靠去掉集号蒙对`（这正是第二节那条不对称的另一面）；
  - `去掉集号不能把片名削掉一截`（四个集号正则都带一个「吃掉前一个字符」的组，
    替换时必须把它放回去，否则 `某某电视剧第01集` 会变成 `某某电视`）；
  - `集号写法不同也认得出是同一集`（跨写法那条退让）。
- **自动挂载门槛**（`core:data` 的 `SubtitleSourceSelectionTest`，14 → **15**）：
  新增 `带发行标记的长文件名也够得着自动挂载门槛`——这一条盯的是
  **用户看到的那一件事**（界面上的 `AUTO_MATCH_SCORE = 85`），
  而不是内部那个打分函数。前面几条都绿、这一条红，就说明匹配好到了
  「能选」但没到「能自动挂」。
- **来源判定**（`core:data` 的 `BrowserEntryTest`，12 → **15**）：
  `SAF 目录里的文件来源是 SAF 而不是文件系统`、`本地路径的来源是文件系统`、
  `id 前缀能被原样取回来`（`mediaIdOf` 与 `refOf` 必须互为逆运算，
  否则读的一侧还原出的 `ref` 是错的）。
- **播放列表那一支**（`core:model` 的 `PlaylistItemTest`，7 → **8**）：
  `浏览页里的 SAF 条目按 ref 回到 SAF 来源`——这条专门盯着
  「第二个入口忘了改」这种情况。

### 单测盖不住的那部分：**这次真的踩到了**

真机验证时点开一个视频，**应用直接闪退**：

```
FATAL EXCEPTION: main
java.lang.ExceptionInInitializerError
  at com.multisuperplayer.core.data.subtitle.SubtitleFileLocator.scanDirectory(SubtitleFileLocator.kt:84)
Caused by: java.util.regex.PatternSyntaxException: Syntax error in regexp pattern near index 39
  at com.multisuperplayer.core.data.subtitle.SubtitleFileNaming.<clinit>(SubtitleFileNaming.kt:129)
```

第二节那个装饰段正则里，闭合的花括号没有转义（`\{[^{}]*}`）：

- **JVM 的 `Pattern` 接受落单的 `}`**，所以单测全绿；
- **Android 的正则引擎（ICU）不接受**，它抛 `PatternSyntaxException`。

花括号在正则里是量词符号（`{1,3}`），要当字面量就必须转义。而
`\{`（落单的开括号）**两个引擎都拒绝**，所以历史上只有开括号被转义了——
这是个**新可能出现**的一类错。更麻烦的是它写在一个类的字段初始化里，
于是第一次用到那个类就是 `ExceptionInInitializerError`：**栈顶指向离它很远的
调用点**（`scanDirectory`），顺着栈往下还要跨两层才看到真话。

**为什么是这一版才冒出来**：装饰段正则是这一版新写的。也就是说，
如果没有「先跑真机再提交」这一步，闪退会跟着版本一起发出去。

修好之后补了一条**结构守卫**（`core:data` 的 `KotlinRegexBracesTest`，新文件 **2** 条）：

- `正则里的花括号只能是量词`——扫描全部模块 `src/main` 下的 Kotlin 源，
  把 `Regex("""…""")` 里的模式文本抽出来，先摘掉**合法**的两类花括号
  （量词 `{1,3}`、转义过的字面量 `\{` `\}`），剩下还有花括号就红；
- `这个用例真的能扫到正则`——反向钉住提取规则本身（扫到的少于 20 条就失败），
  否则「没找到违规」和「根本没读到正则」是同一个结论（都是全绿）。

守卫写完**第一次运行就抓到了第二处**：字符类里面的花括号
（`[^{}]`）同样要转义，写成了 `[^\{\}]`。

另一条同一类事的边界：**ICU 与 JVM 的语法差异无法用 JVM 单测覆盖**，
除非引入 `icu4j`（十几 MB 的依赖，只为一个花括号不值）。所以这里走的是
和 `AppLanguageTest` 同一个路子——**锁写法，而不是锁引擎**：
「不许出现不是量词、也没转义的花括号」这条规则比「跑一遍 ICU」便宜得多，
而且失败信息直接告诉你该写成什么。

顺带记下那个**这一版又一次确认的构建期陷阱**（1.2.0 也记录过，这里再写一遍因为它
会让「文案守卫根本没跑」完全静默）：

> `res/values*/strings.xml` **不是** JVM 单测任务的声明输入。改完三语文案之后跑
> `gradlew test`，这些测试任务会被判成 `UP-TO-DATE`，甚至**从构建缓存里 `FROM-CACHE`
> 恢复**——改坏的文案照样「全绿」。可靠做法是删掉各模块的 `build/test-results`
> 并加 `--no-build-cache`。

## 九、已知限制

- **不做简繁互认**：`某某电影.chs.srt` 仍然配不上 `某某電影.mkv`。
  需要一套简繁映射或系统 ICU 转换，属于新功能，留到后续版本。
- **装饰段只在「整段被一对括号包住」时才去掉**：配对不完整（`[a.b`）时整段保留。
  这是有意的——只吃掉半截等于把片名改了。
- **年份与圆括号里的纯中文短语不去**：`(1982)` / `（上）` 会被当成片名的一部分。
  代价是 `某某电影 (2023).mp4` 与 `某某电影.srt` 只剩前缀关系（仍然算匹配，但降一档）。
- **只有一边写了集号时不做任何猜测**：`Show.S01E01.mkv` 旁边的 `Show.other.srt`
  留在手动列表里让用户选。
- **系统文件选择器添加的目录仍然要用户手选一次**：那是 SAF 的设计
  （应用拿不到整卷的读权限），不是缺陷。**同一棵树重复授权会出现两行**，
  现在可以用行尾的「移除」清掉。
- **内部存储 / 存储卡那两行仍然需要「所有文件访问」**：本条 bug 修的是
  「用系统文件选择器添加的目录」，这两行走的是另一条路，没变。
- 沿用 1.2.0 与 1.1.0 的全部已知限制：清空生成的字幕只删本机识别出来的文件；
  「播放时禁止熄屏」只在真的在播放时生效，播放页上的临时开关不写回设置；
  网络播放没有自定义请求头 / User-Agent 的入口；只支持 http / https；
  外部打开与分享进来的条目不进「最近播放」，且与媒体库里的同一个文件算两个身份；
  「允许不受信任的证书」打开后不再校验任何 https 证书；不含 32 位原生库。

## 十、升级注意

- `versionCode` **10201 > 10200**，可直接覆盖安装 v1.2.0（以及更早的版本），不报降级。
- **升级之后不需要做任何事**：两个修复都在查询与比较那一层，没有设置项、没有迁移。
- **已经手动选过的字幕不受影响**；受影响的是**自动挂载**的结果——
  之前「明明有字幕却找不到」的那些文件夹，升级后再播一次就会自动挂上。
- **从播放列表 / 最近播放点开的 SAF 条目同样受益**（第三节后半），
  不需要把条目删掉重加。
- 关于页不显示「测试版」徽章（正式版不显示徽章）。
