发布日期：2026-10-03
基于版本：v0.6.3-alpha.1

## 一、这一版做了什么

v0.6.4 的主题是**本机离线翻译**：字幕翻译这条路多出一个「不联网也能用」的服务商。

这是路线图上「音频翻译（本地 + 云端）」里的本地那一半，也是 v0.6「本机离线语音识别」
的对称动作——那边把音频转成字幕，这边把字幕转成另一种语言，两者都不出网。

### 1. 「翻译服务商」里多了一项「本地（设备上运行）」

设置 → 字幕与翻译 → 服务商列表里新增一项，与 DeepSeek / OpenAI / Ollama 等**并列**：

| 项 | 本地这一家 |
| --- | --- |
| 服务地址 | 不需要（这一栏不显示） |
| API 密钥 | 不需要，选项上直接写「不需要密钥」 |
| 模型 | 设备端模型清单里的模型（当前只有一条 `qwen3-0.6b`） |
| 网络 | **一次都不出网**：字幕内容不离开手机 |

之所以做成「列表里的又一家里服务商」而不是另开一个开关，是因为**翻译这件事只有一套**：
批量、上下文、术语表、缓存、失败重试、只重试失败的行、导出，这些逻辑与「译文从哪来」无关。
做成并列的一项，上面那一整套一行代码都不用改；另开开关则会立刻分叉成两套行为，
而它们迟早会不一样。

判定走的是**请求自带的属性**（`onDeviceModelId`），不是「用户现在选的是哪家」：
引擎拿到的是配置快照，让它在跑到一半时去读当前服务商，就会出现半途换家、
缓存里混进两套结果的问题。

> 本页所有路径均可在应用内到达：**设置 → 字幕与翻译 → 服务商 → 本地（设备上运行）**，
> 模型在 **设置 → 字幕与翻译 → 本地模型** 一栏下载。

### 2. 模型按需下载，不打进 APK

首条模型是 **Qwen3-0.6B（int4 量化）**，**约 345 MB**。它不随安装包分发，第一次用之前要下载一次。

- **为什么不进 APK**：它是 345 MB，而整个安装包现在约 135 MiB。让每个用户为「可能会用一次」
  的功能多付近三倍体积不划算。
- **但安装包本身还是变大了：约 88.6 MiB → 约 134.7 MiB（+约 46 MiB）。** 涨的不是模型，
  而是**推理运行时** `liblitertlm_jni.so`（arm64-v8a 21,802,960 B + x86_64 25,968,008 B，
  共约 45.6 MiB，`.so` 不压缩存放），这一份是怎么都省不掉的——没有它就跑不了本机模型。
  真要再压，只能砍 ABI（比如去掉 x86_64，约 −24.8 MiB），代价是模拟器上没法用这个功能；
  本版没做这个取舍。如果你只在意安装包大小、不打算用本机翻译，这一版确实会大一圈。
- **为什么是 0.6B**：这是能在手机上跑得动的量级。字幕翻译不需要世界知识，而更大的模型
  （1.7B / 4B）在同一批字幕上要慢好几倍——宁可先给一条能用的，也不要给一个「点了要等十分钟」的选项。
- **为什么是 int4 那条**：同一个仓库里有四个变体（未量化 614 MB、联发科 NPU 专用 1.2 GB、
  int4 345 MB、混合 int4 498 MB）。取最小的那条：手机上的瓶颈是内存与算力，两者都随体积走，
  而 int4 在字幕翻译这种任务上的质量差别可以忽略。
- **下载源可改，默认走国内镜像 `hf-mirror.com`**。跟语音识别那边是**分开存的两个键**——
  一个源指错了不该悄悄改掉另一个源的配置。留空即回到默认源。
- **下载完成后校验 sha256**，对不上按「校验失败」处理并把那半截删掉，
  不留一个「看着下好了但装不上」的模型。
- **可以只删模型**：删除只清这一个模型的文件，**已经译好的字幕一个都不受影响**（确认框里就是这么写的）。
- **支持中途停止**；不支持断点续传，所以「上次没下完」这一状态会**如实说明**（已收到百分之多少），
  并讲清会从头开始，而不是假装续着传。

### 3. 约束解码：把输出结构钉死

本机这一路的 JSON Schema 不是「建议」，而是**真的**被编译成解码约束——
模型在解码期就走不到「不合法 JSON」那条路上。这和远端完全不同：远端那套
`response_format: {"type": "json_object"}` 只保证「是合法 JSON」，**字段名根本没发给模型**，
实测模型会自己发明键名，所以远端靠的是提示词里那段格式说明。

也就是说：**同一件事的两种说法**（提示词里说一遍、本机解码器强制一遍）。
两处必须一致，改一处就得改另一处（提示词那边还有 `TRANSLATION_PROMPT_VERSION` 要跟着 +1，
因为缓存键跟着它走）。

Schema 里**只加了两个关键字**（`minItems` / `maxItems`），而且是**真机实测过**才留下的：
每多一个关键字，就多一个「约束解码器可能不认识」的东西，而失败的代价是整条本地路径都不能用。
为什么要钉这两个关键字，见下面第 5 节。

### 4. 失败原因按「下一步该做什么」分开

本机这一路新增三条**各自需要不同动作**的失败，而不是一句「翻译失败」：

| 界面说的事 | 下一步动作 |
| --- | --- |
| 「本机模型「qwen3-0.6b」还没下载好。」 | 去本地模型那一栏把它下下来 |
| 「本机推理引擎没能启动。」 | 下载模型解决不了这档——多半是内存不足或本机不支持，先重启应用，或换更小的模型 / 改用云端 |
| 「本机模型这次没能给出结果。」 | 重试通常就好；反复出现就换更小的模型或改用云端 |

第二条**专门写清「下载模型解决不了这一档」**：不写的话，用户看到「本机」两个字的第一反应
就是再下一次模型，而下一次当然还是一样。

另有一处产品可见的小改动：缺项提示的顺序变成**「服务地址、模型名、API 密钥」**——
把密钥排在模型名之后（原先在之前）。填配置时是先有地址、再选模型、最后才去找密钥，
提示的先后顺序跟着这个走比较不容易漏。

## 二、两个只有真机上才会暴露的问题（都已修）

这一版的功能在模拟器/单测里全绿，但一上真机就有两处「一定不会成功」，两处都不是逻辑写错，
而是**库的行为与文档/直觉不一致**。

### 1. 「生成成功」这条路上挂着一句必然抛异常的代码

引擎初始化好之后，代码会去读一次 benchmark 信息（用了多少 token、有没有被截断）来填日志。

**问题**：`conversation.getBenchmarkInfo()` 在 LiteRT-LM 0.17.1 上**每次调用都抛**
（`Benchmark is not enabled`）。它写在「生成成功之后的必经路径」上，
于是**每一次生成都被判成失败**——日志里能看到引擎就绪、紧接着就是失败，
看起来像「模型不行」，实际是一次查询统计数据的行为把整个功能判了死刑。

**修复**：把它降级成**可选值**——读不到就是读不到，`outputTokens = 0`、`truncated = false`，
不影响生成结果本身。

> 附带一个判断技巧：`EngineConfig` 在 0.17.1 里**根本没有** `BenchmarkParams` 这个字段
> （用 `javap` 反编译 AAR 确认过）。也就是说这个开关**没有地方能打开**，
> 那那句调用在任何配置下都不会成功——它从一开始就不该长在必经路径上。

### 2. 0.6B 会把一整批译文并成一个数组元素

**症状**：模型返回的是**合法 JSON**，但 `translations` 数组里只有 **1 个**元素——
句与句之间用 `\n\n` 粘在一起。解析器于是每次都报「找到了译文数组，但条数是 1，期望 8」，
本地翻译**一条都出不来**。

**为什么重试没用**：这不是「模型偶尔不听话」，而是它对这种形状的**默认理解**。
实测重试三次，输出**逐字相同**；拆成小批之后仍然是「1 vs 4」。

**修复**：按调用方给的条数把数组长度钉死。解码约束在**解码期**就排除「只写一个元素」这条路，
模型只能在 N 个元素里写 N 段。

条数从哪来？**调用方本来就知道**——这一批要翻几行是引擎自己定的。
提示词里要求模型「回显一个它无法自己决定的数字」是一类典型错误（每多一个必填字段，
就多一次被静默漏掉的机会），所以这个数字**不进提示词**，而是直接进 schema。

拆批之后条数要跟着变小（实测一次 8 条失败 → 拆成 4 / 4，再拆成 2 / 2 都成功），
所以 `minItems`/`maxItems` 是**每一批**按它自己的行数算的。

### 3. 真机验证结果

| 项 | 结果 |
| --- | --- |
| 模型下载 | 345 MB / 328.7 MiB，约 83 秒（镜像站） |
| 引擎启动 | 日志 `initializing engine for qwen3-0.6b` → `engine ready` |
| 约束解码 | 8 条一次成功，**日志里没有条数不匹配、也没有拆批重试** |
| 计数 | 一条 3 条素材显示「**已译 3/3**」「本次：3/3，实际请求 1 次」；一条 10 条素材显示「**已译 10/10**」 |
| 画面 | 截图上同时出现英文原文行与中文译文行 |
| 「测试连接」 | 设置页显示「连通。模型翻出来的是：…」 |

## 三、已知取舍

1. **必须先用网络下完模型。** 翻译本身不需要网络，但模型得先下一个 345 MB。
   没有网络就装不上模型——这与语音识别那边的取舍完全一样（见 README「已知限制」）。
2. **只跑 CPU。** 不用 NPU / GPU，好处是不挑机器、结果可复现，代价是慢。
   33 秒素材上「已译 3/3」大约几秒；长片按比例更久。**字幕是一批一批翻的**，
   所以进度条能看到推进，不是一次等到天亮。
3. **0.6B 会把提示词里的示例照抄。** 实测：一句没有实义的短行（`Line two.`）被翻成了
   提示词里那段「输入 / 输出」示范的输出（`- 回家。\n- 等等！`），一字不差。
   相邻的两条都翻对了，所以**不是对齐问题**，是这条模型在「没什么可翻」时直接抄了示例。
   修法方向（让示例内容不可抄、或者干脆去掉示例）会牵动提示词的整套校准，
   本版按「这一版不动现有提示词」的决定**先不动**，留到后续版本。
4. **本机模型只有一条，还不能换。** 清单是留了多条的位置的（设置页直接渲染那份清单），
   候选也都在同一个仓库里可选，但要等实际测过速度与质量之后再加。
5. **翻译缓存没有「清空」入口。** 缓存只增不减（按「内容 + 目标语言 + 模型」哈希去重），
   想强制重译目前得改字幕文件内容、或者换目标语言 / 换模型。
   「自己翻译过的东西不该被一键清掉」是这个取舍的出发点，但确实少了一个强制重来的出口。
6. **译文会被缓存，且缓存路径是应用私有目录。** 放在 `filesDir` 而不是 `cacheDir`：
   已经付过钱（或已经算过）的结果，不该被系统在一次空间不足时顺手清掉。

## 四、升级提示

- 从 v0.6.3 升级**不需要任何迁移**：新目录、新文件、新设置项，老配置一律照旧。
- 不下载本地模型也用得上这一版：服务商照旧可以用云端那几家，
  「本地（设备上运行）」只是列表里多出来的一项。
- 已经译好的字幕、人工修正、术语表都**不受影响**（本版没有改动它们的存储格式）。
