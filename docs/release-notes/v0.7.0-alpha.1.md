## 一、这一版做了什么

**应用内检查更新**。设置入口页新增第 8 行「检查更新」（在「关于」之前），进去是一页三段：

1. **当前版本**：写着本机版本，右边一个「检查」按钮（进页面时也会自动查一次）。
2. **发现新版本**（只有真的查到才出现）：tag、发布时间、完整发行说明、`下载并安装` / `忽略此版本`。
3. **更新设置**：更新通道（正式版 / 预发行版）、自动检查开关、GitHub 令牌（可选填）。

更新源是 **GitHub Releases**（`Aaze-wu/MultiSuperPlayer`），走匿名 API。
令牌是**可选**的——不填也能用，填了只是把「每小时 60 次」提到 5000 次。
令牌只存在本机、用系统密钥库（`Keystore`）加密，不上传；界面上明确写着这一句。

顺带把新声明的 `REQUEST_INSTALL_PACKAGES` 登记进权限页的折叠区，清单覆盖测试保持双向一致。

## 二、检查那层留了数据源抽象

用户已经说过「后续会加其他渠道」（比如自己的服务器、其他托管平台）。所以**检查逻辑里没有一处 GitHub**：

```
UpdateSource（接口）           ← 只有 listReleases(): List<UpdateRelease>
    ↑
GitHubReleasesSource           ← 唯一知道 GitHub JSON 长什么样的地方
    ↑
UpdateManager                  ← 版本比较、节流、忽略、设置，全在这里
```

`UpdateRelease` 是渠道无关的：tag、版本、是否预发行、发布时间、说明、**一个（或零个）APK 资产**
（地址 / 大小 / sha256）。换渠道 = 新写一个 `UpdateSource` 实现，
上层（`UpdateManager`、ViewModel、界面）一个字都不用改。

**Koin 注册也必须写成接口**（`single<UpdateSource> { … }`）——这一点在真机上吃到过一次教训，见 §四。

### 版本比较是纯逻辑，单独测

`UpdateVersion` 自己实现 `Comparable`，认 `v1.2.3-alpha.1` 这类 tag，
按「数值三段 → 预发行标识符逐段比较」排序（`1.0.0-alpha.1 < 1.0.0-beta.1 < 1.0.0`）。
`UpdateRules.decide(current, releases, channel, ignoredTag)` 是**零 Android 依赖的纯函数**，
输入「本机版本 + 候选列表 + 通道 + 被忽略的 tag」，输出四种状态之一：

| 状态 | 界面说的 |
| --- | --- |
| `NotChecked` | 还没有检查过 · 当前版本 x.y.z |
| `UpToDate` | 已是最新版本 · 当前版本 x.y.z |
| `Available(release)` | 有新版本 vX · 当前版本 x.y.z |
| `Ignored(release)` | 此版本已被忽略 · 当前版本 x.y.z |

### 两个容易写错的地方

- **「还没有检查过」和「已是最新」不是同一件事**。进页面时会自动查一次，但**受 12 小时节流**——
  被节流跳过时返回 `null`，界面**什么都不改**。把「跳过」当成「已是最新」的后果是：
  每次进这一页都把上次查到的「有新版」擦掉一次，用户再也看不到它。
- **「解析不出当前版本」时不能猜**。`UpdateVersion.parse` 失败 ⇒ `decide` 直接返回 `NotChecked`，
  而不是拿一个 `0.0.0` 去比较（那会让每个版本都显示成「有新版本」）。

## 三、下载与安装：一个 140 MB 的文件，四道防线

升级包是**会拿去执行安装**的东西，风险等级和「下载一个模型」不同。规矩照抄
`AsrModelDownloader`（那边同样是「下到一半断了，用户看不出区别」）：

1. **先写 `<name>.part`，校验通过才 `renameTo`**。直接写目标名的话，一次中断会留下一个
   「大小差不多、内容不全」的 APK，下次进来看到文件已存在就以为下好了——安装时才报
   「解析包时出现问题」，而那时已经没人会想到是下载的锅。同目录内的 rename 是原子的，
   所以**目标名出现 ⟺ 内容完整**。
2. **失败或取消必须删掉 `.part`**。不删的话用户看到「占了几十 MB 却什么都没有」，
   而且他会再点一次下载，再占几十 MB。清理放在统一的 `catch (Throwable)` 里，
   这样**将来新加的失败分支自动也享受这条规矩**。
3. **校验用 sha256**，不用「能不能打开」或「大小对不对」。发布信息里给了 sha256 就用它比对；
   没给就在日志里说明「跳过摘要校验」（此时仍有下面第 4 条兜着）。
4. **安装前校验包名与签名**。只允许「包名相同」且「签名与本机已安装版本相同」的包进入安装器。
   包名不同 ⇒ 装上去是另一个应用；签名不同 ⇒ 系统本来也会拒绝，但那要等到用户在系统安装器里
   点完「安装」才报一句 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，不如自己先拦住并说清原因。

另外：**服务端给了长度、发布信息里也有长度、两者不一致**时立刻失败，
不必等把 140 MB 读完再让摘要失败——失败消息也会从「摘要不符」变成一句能查得出真因的话。
进度按「1% 或 512 KB（取大的那个）」节流，141 MB 那一千多次 `read` 不会每次都推一次 Compose 状态。

### 安装要过系统两道门

- **「安装未知应用」授权**：Android 8 起，一个应用要拉起安装器必须先去系统里打开这个开关。
  页面在未授权时会显示一行提示 + 「去允许」，点了直接跳到本应用的授权页
  （`ACTION_MANAGE_UNKNOWN_APP_SOURCES`）。授权状态在**每次回到页面**（`ON_RESUME`）重读系统，不存本地副本。
- **`FileProvider`**：安装器拿不到我们的私有目录，包必须通过 `content://` URI 递过去。
  Authority 是 `${applicationId}.update.fileprovider`，`update_apk_paths.xml` 里**只放开了
  `cache/updates/` 这一个目录**——放别处或放开整个 cache 都会在调用安装器时抛
  `Failed to find configured root`。
  包放在 `cacheDir` 而不是 `filesDir`：升级包装完就没用了，放缓存里系统能在空间吃紧时自己回收。

## 四、真机验证结果

在 `emulator-5554`（Android 17 / API 37，zh-Hans-CN）上实测。
**这一版的两个崩溃都是这一步抓出来的**，都不是「写错了」，是「编译期完全看不见」的那一类：

### 崩溃一：进「检查更新」页直接退出到桌面

```
FATAL EXCEPTION: main
org.koin.core.error.InstanceCreationException: Could not create instance for
  '[Factory: '…feature.settings.UpdateViewModel']'
Caused by: NoDefinitionFoundException: No definition found for type
  '…core.data.update.UpdateSource' on scope '['_root_']'
```

`UpdateManager` 要的是 `UpdateSource` 接口，而注册时写的是
`single { GitHubReleasesSource(…) }`——**只登记了具体类**。Koin 按**类型**解析，
接口于是没人认领，进页面那一刻就炸。

**编译期零提示**（类型是对的、依赖方向也是对的），而且项目里没有 `checkModules()` 这类
能提前发现它的测试。修法就是把注册写成 `single<UpdateSource> { … }`，
并把「这就是后续加渠道的接缝」写进注释，免得下次又有人改回具体类。

### 崩溃二：点「下载并安装」约 45 秒后应用自己消失

```
FATAL EXCEPTION: main
java.net.SocketException: Connection reset
    at …ConscryptEngineSocket$SSLInputStream.read(…)
    at …HttpURLConnectionImpl.getResponseCode(…)
    at …UpdateDownloader$download$3.invokeSuspend(UpdateDownloader.kt:109)
```

下载器的失败清理是 `catch (e: Throwable) { part.delete(); throw e }`——**原样重抛**；
而 ViewModel 只 `catch (e: UpdateException)`。`SocketException` 不匹配，于是它一路冒到
`viewModelScope`，而**协程里的未捕获异常就是进程崩溃**。用户看到的是「应用突然关了」，
不是「下载失败」。

两处都补上：

- **下载器**把 `IOException` 包成 `UpdateException.Network(e)`，保持
  「这个组件的所有失败都是 `UpdateException`」这个契约（`GitHubReleasesSource` 本来就是这么写的）；
- **ViewModel** 的每个协程改成三级：
  `catch (CancellationException) { throw e }` → `catch (UpdateException)` → `catch (Exception)`
  兜底。`CancellationException` **必须原样透传**，否则「用户离开页面」会被当成一次失败。

顺手给已知失败补了 `MspLog.w`：修之前连续两次下载失败，logcat 里**一条自己的记录都没有**，
排查全靠截图猜。

### 验证过的 / 没验证到的

| 项 | 结果 |
| --- | --- |
| 设置入口页第 8 行 | `检查更新` / `当前版本 0.6.7-alpha.1`（当时为测「发现新版本」临时降了版本号），位置在「后台保活」与「关于」之间 ✅ |
| 进页面自动检查 | `正在检查…` → 约 5–9 秒后 `已是最新版本 · 当前版本 …` ✅ |
| 发现新版本 | `有新版本 v0.6.8-alpha.1 · 当前版本 0.6.7-alpha.1` + `发现新版本` 段 + 完整发行说明 + `展开全部` ✅ |
| 更新通道 | 对话框两项（正式版 / 预发行版）；选「正式版」后副标题与右侧同步更新，并自动重查 ✅ |
| GitHub 令牌行 | `未填写，也能检查` + 说明文案 ✅ |
| 「去允许」 | 跳到系统「安装未知应用」页，包含本应用与「允许从此来源安装应用」✅ |
| 授权状态重读 | `appops set … REQUEST_INSTALL_PACKAGES allow` 后重进页面，提示消失 ✅ |
| 下载失败的表现 | `网络不可达，请检查网络连接后重试。`；`cache/updates/` 干净（无残留 `.part`）；**进程仍在**（`pidof` 有值）✅ |
| 下载成功 → 摘要校验 → 签名校验 → 拉起系统安装器 | ⚠️ **未在模拟器上走通**，原因见下 |

**为什么下载成功路径没验到**，两条都是环境问题，不是代码问题：

1. **模拟器到 GitHub 资产的连接每次被重置**。`api.github.com` 是通的（所以能查到新版本），
   但资产会 302 到 `objects.githubusercontent.com`，这台模拟器到这个域名每次 `Connection reset`。
   同一 URL 在主机上 `HEAD` 返回 `200` + `141371221` 字节。所以「下载中途被重置」这条路径
   **恰好被反复验到了**（也正是它暴露了崩溃二），而「下载跑完」没验到。
2. **模拟器里装的是 debug 签名包**，与 release 资产的签名必然不符 ⇒ 即便下完也会被
   签名校验拦下（这正是 §三 第 4 条要的效果）。

⇒ 这两条都需要**一台能正常访问 GitHub 资产的设备 + 一个 release 签名包**才能验证。
**如果这个包在你的机器上走通了完整流程（进度跑到 100% → 弹出系统安装界面），欢迎到
[Issues](https://github.com/Aaze-wu/MultiSuperPlayer/issues) 留个记录**；如果卡在某一步，那里的报错文案就是我们要的信息。

## 五、已知限制

- **只支持 GitHub Releases 这一个渠道**（但检查那层已经是接口，见 §二）。
- **匿名请求限流 60 次/小时**。12 小时的自动检查节流会让正常使用远低于这个数；
  真被限流了会**单独报一句**（`GitHub 拒绝或限流了这次检查`），不会和「网络不通」混成同一句话——
  前者的解法是「过一会儿再试或填 token」，后者是「检查网络」。
- **更新检查不会自动下载/安装**。查到新版本只是显示出来，点不点、什么时候点，由用户决定。
- **`REQUEST_INSTALL_PACKAGES` 是一条敏感权限**。它的作用范围仅限于「拉起系统安装器」，
  我们不解析也不静默安装任何包；从系统安装器点到「安装」仍然需要用户确认。
  它在权限页的折叠区里（安装即授予的那组），说明这一条是**安装时就有的**、不是运行时申请的。

## 六、这一版的测试

- 全量：`testDebugUnitTest` + `testReleaseUnitTest` + `assembleDebug` → `BUILD SUCCESSFUL`
- 用例：**143 suites / 1773 cases / 0 failures**（两个 variant 一致），上一版是 138 / 1726
- 新增测试：
  - `core/data` 的 `update` 包单测：版本解析与比较（含预发行排序、非法 tag）、
    `decide` 的四态与通道过滤、忽略版本、GitHub JSON 解析（含「没有资产」「资产名叫别的」
    「没有 sha256」这些真实会遇到的形态）
  - `UpdateDownloaderFailureTest`：这条是**崩溃之后补的**。它钉的不是「异常类对不对」，
    而是「下载阶段的失败一律是 `UpdateException`」这条契约——连接被重置、读超时、
    域名解析不了都必须归成 `Network` 且保留 cause；同时钉住两个反向边界：
    已经分好类的失败不许被套两层（否则「限流」会说成「网络不通」），
    取消和编程错误必须原样透传（否则未来任何一个 `NPE` 都会被显示成「请检查网络连接」）。
  - `UpdateSummariesTest`：四种状态各有各的一句话、两个通道的说明不是同一句、
    八种失败各有各的一句话、以及**三套语言的资源键双向对齐**（英文里不许有汉字、
    繁体文案必须是真繁体而不是抄过来的简体）
