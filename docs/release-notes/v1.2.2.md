# v1.2.2 文件名里的 `#` 与 `%` / 音频旁边的同名字幕

发布日期：2026-10-09
基于版本：v1.2.1

---

## 一、这一版做了什么

| 问题 | 症状 | 修在哪 |
| --- | --- | --- |
| 文件名含 `#` 或 `%` 时，从「浏览」（文件系统）入口打开 | 点开就报播放失败；同一个文件夹里的同名字幕 / 歌词也读不到——字幕面板里空着，手动选也读不出来。同一个文件从「媒体库」点开却一切正常 | `core:model` 新增 `LocalPathUri`，接到 `core:data` 的 `SubtitleFiles`、`core:player` 的 `MediaItemMapper`、`core:data` 的 `AsrSubtitleGenerator` |
| 音频旁边的同名字幕 / 歌词（`歌.mp3` + `歌.srt`、`曲.mp3` + `曲.mp3.srt`）不会自动挂上 | 字幕面板里列得出来、手动选也能用，就是不肯自动挂（面板写着「未自动选中」） | `core:data` 的 `SubtitleFileNaming` / `SubtitleSource` |

两条都是**静默失效**：不崩溃、日志里也没有异常，界面上只表现为「播不了」或「没有字幕」。
所以这一版的重点同样不在改了多少代码，而在**把「格式对不对口」与「名字对不对得上」拆成两个字段**（第三节），
并给地址编码补上一条 JVM 单测盖得住的规则（第二节）。

既有能力（媒体库、浏览、最近、播放列表、字幕、翻译、网络播放、外部打开与分享、
语音识别、清空识别缓存、播放时禁止熄屏）行为不变。

## 二、第一个 bug：`file://$path` 这个字符串拼接

### 症状看起来像两个 bug，其实是一个

- 点开文件，播放失败（Media3 报 `FileDataSource$FileDataSourceException`，底层是
  `uri has query and/or fragment` 或者 `FileNotFoundException: Invalid file path`）；
- 同一个文件夹里的同名字幕 / 歌词也读不到——但**字幕的匹配逻辑本身是好的**。

第二点最容易被误判成「匹配又坏了」：`#` 与 `%` 在**归一化**之后都会被丢掉（只留字母数字），
所以两边的名字一样干净、一样对得上。坏的是**读文件那一步**：
`SubtitleSource.uri` 与播放器用的 uri 由同一个拼接函数产出，读的时候 `Uri.parse` 一样会截断。
两处要么一起修，要么就会出现「能播但字幕读不出来」这种更难看懂的状态。

### 为什么 `"file://$path"` 是错的

`Uri.parse` 不是「把字符串装起来」，它在**解析**：

| 路径里的字符 | 被解析成 | 症状 |
| --- | --- | --- |
| `#` | fragment 的开头 | 路径在 `#` 处被截断，Media3 直接拒绝 |
| `%` | 百分号转义的开头 | `100% 完成` 里的 `% ` 不是合法转义 ⇒ `Invalid file path` |

（`?` 同理会被当成 query 的开头。这一版一并处理了，只是 Windows 上造不出带 `?` 的文件，
所以没有对应的真机素材。）

### 修法：编码成合法的 `file://` uri，并且能反解回路径

新增 `core:model` 的 `LocalPathUri`：

- `localFileUri(path)`：已经是带 scheme 的 uri（含 `://`）就原样返回；
  否则补上 `file://` 并按码点做百分号编码——**只编码不是「URI 安全字符」的那些**；
- `localFilePath(uri)`：反解，认不出来（别的 scheme）返回 `null`。
  必须能反解，因为读的一侧（`SubtitleRepository`）与测试断言都要拿回真实路径。

`#` 编码成 `%23`、`%` 编码成 `%25`、中文与空格编码成 UTF-8 的 `%XX`；
斜杠、冒号这类**结构性**字符不编码（把它们编码了，`file://%2Fa` 就不再是一个路径）。

**只编码 `#` 和 `%` 是不够的**：`"` `<` `>` `[` `]` `^` 这些字符在不同解析器下的归宿各不相同，
挨个打补丁迟早漏一个；「不是安全字符就编码」是一条**可枚举**的规则，
将来新增字符时不会有人忘了改。

### 为什么不用 `Uri.fromFile(File(path))`

那是 Android 的 API，而本项目的 JVM 单测跑在 `unitTests.isReturnDefaultValues = true` 下——
`Uri.parse` 与 `Uri.fromFile` 都返回 **null**，任何依赖它们的规则在单测里**根本跑不起来**，
只能靠真机手点。这条规则必须能被单测穷尽（第六节），所以它写成了纯 Kotlin。

## 三、第二个 bug：「够不够格自动挂」与「谁排前面」曾经是同一个数

### 分数是怎么算的

`SubtitleFileNaming.associationScore` 给候选字幕打分，两部分相加：

- **名字分**：`歌.srt` 配 `歌.mp3` ⇒ 归一化后相等，满分 100；
  `歌.mp3.srt` 配 `歌.mp3` ⇒ 互为前缀那一档，85；
- **对口分**（`kindAffinity`）：歌词格式（`.lrc` 等）配音频 +25、配视频 −25；字幕格式配音频 −25。

**自动挂载的门槛是这一个总分**（`AUTO_MATCH_SCORE = 85`）。于是：

| 旁边的文件 | 名字分 | 对口分 | 总分 | 自动挂？ |
| --- | --- | --- | --- | --- |
| `歌.mp3` + `歌.srt` | 100 | −25 | 75 | ✗（差 10） |
| `曲.mp3` + `曲.mp3.srt` | 85 | −25 | 60 | ✗ |
| `调.mp3` + `调.lrc` | 100 | +25 | 125 | ✓ |

`歌.srt` 明明和 `歌.mp3` **同名**，却因为「srt 不是歌词格式」被扣到门槛以下——
这就是报告里那句「名字一样却要手动选一次」。

### 修法：拆成两个字段

- `titleMatchScore`：**只看名字**（归一化后相等 / 互为前缀 / 带发行标记 …）。
  **能不能自动挂，只看它**；
- `matchScore`：名字分 + 对口分。**只决定谁排前面、以及列表里怎么展示**。

`isAutoMatchable` 因此改成 `titleMatchScore >= AUTO_MATCH_SCORE`。

判决：**「对不对口」是偏好，「名字对不对得上」才是资格。**
把偏好算进资格，就会让「名字完全一样」的候选被静默剥夺资格——而且**界面上看不出来**，
它只是「没自动选中」，用户会以为应用压根没找到那个文件。

`.lrc` 优先的那条规则没丢：`调.mp3` 旁边同时有 `调.lrc` 与 `调.srt` 时，
两者都够资格自动挂，排序仍然把 `.lrc` 放在前面（第七节有这一条的真机结果）。

## 四、为什么这一版也没有 `beta.1`

判据与 1.2.1 相同：**这套验证能不能在本地做完**。

两处改的都是纯函数——一个是路径 ⇄ uri 的编解码，一个是两个分数各自代表什么。
没有清单变化、没有新权限、没有系统 intent 匹配、没有新的系统 API，
用户能看见的功能集与 1.2.0 / 1.2.1 完全一样。

但第二处**有一半只能在真机上验**：`MediaKind`（这一条是音频还是视频）在 JVM 里造不出来，
它取决于文件与 MediaStore。真机验证（第七节）把三种组合都跑了一遍，
所以这一版同样是直接发正式版。

（本版与 v1.2.1 同日发布：第一条 bug 是 v1.2.1 记录下来的已知问题，
当天就补上了第二条同类问题的修复。）

## 六、测试怎么盖住这两处

- **地址编解码**（`core:model` 新增 `LocalPathUriTest`，**10 条**）：
  `普通路径补上 file scheme`、`中文与空格能被原样还原`、`井号不会变成 fragment`、
  `百分号不会变成转义开头`、`问号不会变成 query`、`斜杠与冒号不被编码`、
  `已经是 uri 的输入原样返回`、`别的 scheme 反解不成路径`、`裸路径原样返回`、
  `认不出的转义原样保留`。断言全部用**往返**（`localFilePath(localFileUri(p)) == p`）
  而不是拼期望字符串——拼接等于把实现抄一遍，实现错了测试会跟着一起错。
- **字幕读文件那一侧**（`core:data` 的 `FileSystemSubtitleLocatorTest` 8 → **9**、
  `SubtitleFilesTest` 13 → **14**）：新增 `文件名含井号或百分号时产出的 uri 仍指向那个文件`
  与 `路径里的井号与百分号不会被 uri 语法吐掉`。这两条盯的是**用户看到的那一件事**：
  「扫到的这个 `uri` 拿去读，还能不能读回原文件」。
- **匹配与门槛**（`SubtitleFileNamingTest` 24 → **26**、`SubtitleSourceSelectionTest`
  15 → **17**）：新增 `字幕名是媒体全名加字幕后缀时按「互为前缀」这一档算`、
  `音频旁边的同名字幕名字分够门槛，只是排序上让位给对口格式`、
  `音频旁边的同名字幕会被自动挂上`、`名字对不上时连门槛都不沾边`，
  并把原来的 `比这一档更弱的匹配分数确实低于门槛` 改名为
  `排序分比这一档更弱只决定先后，不再决定资格`——**用例名必须跟着语义改**，
  否则下一个人会照着旧名字写出相反的新用例。
- **单测盖不住的那一半**：`MediaKind` 来自文件与 MediaStore，JVM 里造不出来。
  所以「音频旁边的 `.srt` 会不会自动挂」这件事，单测只能喂一个**假的** `MediaKind`，
  真机上跑通才算数（第七节第 8～10 行）。

### 又一次确认的构建期陷阱

> `res/values*/strings.xml` **不是** JVM 单测任务的声明输入。改完三语文案之后跑 `gradlew test`，
> 这些测试任务会被判成 `UP-TO-DATE`，甚至从构建缓存里 `FROM-CACHE` 恢复——改坏的文案照样「全绿」。
> 可靠做法是删掉各模块的 `build/test-results` 并加 `--no-build-cache`（本版就是这么跑的）。

## 九、已知限制

- **这一版只处理「本地路径拼成 uri」这一条路**：`content://`（媒体库、SAF、
  外来打开与分享）与网络地址本来就带 scheme，`localFileUri` 对它们原样返回，行为不变。
- **字幕仍然要能被扫到才算数**：带 `#` / `%` 的文件名现在能扫能读，
  但字幕放在**别的目录**里仍然需要手动选一次。
- **名字对不上时仍然不自动挂**：`歌.mp3` 旁边放一个 `别的名字.srt` 会留在手动列表里。
  这一版放宽的是**已经同名**的候选，没有放宽「不同名」。
- **`.lrc` 优先于 `.srt`**：同一个文件夹里两者都在时自动挂 `.lrc`
  （歌词带时间轴、更适合音频），想要字幕就在面板里手点一下。
- 沿用 1.2.1、1.2.0、1.1.0 的全部已知限制：不做简繁互认；装饰段只在整段被一对括号包住时才去掉；
  年份与圆括号里的中文短语不去；只有一边写了集号时不做猜测；系统文件选择器添加的目录仍需手选一次
  （重复授权会出现两行，可用行尾「移除」清掉）；「内部存储」「存储卡」两行需要「所有文件访问」；
  清空生成的字幕只删本机识别出来的文件；「播放时禁止熄屏」只在真的在播放时生效、
  播放页上的临时开关不写回设置；网络播放没有自定义请求头 / User-Agent 的入口；只支持 http / https；
  外部打开与分享进来的条目不进「最近播放」，且与媒体库里的同一个文件算两个身份；
  「允许不受信任的证书」打开后不再校验任何 https 证书；不含 32 位原生库。

## 十、升级注意

- `versionCode` **10202 > 10201**，可直接覆盖安装 v1.2.1（以及更早的版本），不报降级。
- **升级之后不需要做任何事**：两个修复分别在「地址怎么拼」与「分数怎么算」这两层，
  没有设置项、没有迁移、没有缓存要清。
- **已经手动选过的字幕不受影响**；受影响的是**自动挂载**的结果——
  升级后再播一次那些要手点的音频，同名字幕会自己挂上。
- **播放历史不受影响**：带 `#` / `%` 的文件名只影响本次打开时用的 uri，
  收藏、续播位置、播放列表里存的都是原始标识，不会因为这一版而失效。
