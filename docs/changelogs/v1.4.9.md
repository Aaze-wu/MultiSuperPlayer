## 一、这一版做了什么

`todo/` 里同一优先级（`[0]`）的两项，同属 `feature:library` 的 `BrowserPane`，本版一起做：

1. **`thinks.txt` 1**：目录列表记住滚动位置 —— 从子目录返回、或点面包屑跳到某一层，列表停在原来那一处，而不是回到顶部。
2. **`bugs.txt` 1**：面包屑（顶端路径）没有显示到「当前目录」那一端 —— 长路径时屏幕上只剩开头，当前层被挤到右边看不见。

两者合起来才是「我在这个目录的哪个位置」的完整体验：纵向停在原处，横向也停在原处。

改动落点：

| 关注点 | 落点 |
| --- | --- |
| 位置的数据结构与淘汰策略 | 新增 `BrowserScrollMemory.kt`（纯 Kotlin，可单测） |
| 位置的持有者 | `BrowseViewModel`（一个 `private val`，不出现在 `BrowseUiState` 里） |
| 纵向恢复 / 保存 | `BrowserPane.kt` 新增 `DirectoryList`（`rememberLazyListState(initial…)` + `snapshotFlow`） |
| 横向停靠 | `BrowserPane.kt` 的 `CrumbRow`（`rememberLazyListState()` + `LaunchedEffect(trail.crumbs)`） |
| 接线 | `BrowseScreen.kt` 两个默认参数 + `BrowseRoute` 里绑到 ViewModel |

## 二、滚动位置为什么必须记在组合外面

症状是「从子目录返回父目录，列表回到顶部」。直觉答案是「加个 `remember` 记住它」，但
`remember` 在这个位置**必然**失效，原因是设计上的：

```kotlin
// core/data/…/BrowserRepository.kt —— listing 的第一帧永远是 Loading
fun listing(ref: String): Flow<BrowserContent> = flow {
    emit(BrowserContent.Loading)
    …
}
```

切目录时 `content` 先变成 `Loading`，`BrowserBody` 走到转圈那一个分支，
`Ready` 分支里的 `LazyColumn` **整棵离开组合**，它自己 `remember` 的
`rememberLazyListState()` 跟着一起被丢弃。等真正的内容到达，是一列**全新的**列表，
`initialFirstVisibleItemIndex` 拿到的是默认 0。

所以位置只能记在组合外面。放哪儿有两个候选，只有一个是安全的：

| 候选 | 结果 |
| --- | --- |
| `BrowseUiState` 里加一个字段 | 每一帧滚动都在写 `StateFlow` ⇒ 整页重组（列表本身也会被标脏）。滚动越顺，重组越频繁 |
| ViewModel 里一个普通 `Map`（**采用**） | 写它不触发任何重组；界面读它只在 `remember(directoryRef)` 里读一次 |

于是 `BrowserScrollMemory` 刻意**不是**状态容器：没有 `State`、没有 `StateFlow`，
只在主线程读写。这正是「可以每滚动一下就写一次」的前提（见第三节）。

`internal` 可见性 + 构造参数 `capacity` 只是为了让单测能测淘汰逻辑，
生产路径上 `BrowseViewModel` 用的是默认容量 20。

## 三、为什么保存用 `snapshotFlow` 而不是 `DisposableEffect { onDispose { … } }`

「离开时保存」看起来更省（不用每帧写），但在这个具体位置上有一个不容易发现的时序问题：

- `DisposableEffect.onDispose` 在 **applyChanges** 阶段执行；
- 新分支里的 `remember { … }` 在 **composition** 阶段执行，**早于** applyChanges。

于是「同一个 `DirectoryList` 调用点、内容换了一份」（`content` 从 `Ready` 直接变到另一个
`Ready`，中间没经过 `Loading` 的情形，比如刷新）时，新列表会先读到**旧值**，
旧的列表之后才把真实值写进去 ⇒ 恢复永远错一间。

`snapshotFlow { index to offset }` 没有这个时序：值一变就写，写入时机与组合生命周期无关。
代价是每帧一次 `Int` 写入 —— 因为这份 Map 不被 `State` 包着，不产生重组，可以忽略。

另外两个配套细节：

- `LaunchedEffect(listState, directoryRef)` 的 key 里带 `directoryRef`：`DirectoryList` 的
  实例被复用到另一个目录时（同一个组合位置），不会把新目录的位置写进旧目录的记录。
- `remember(directoryRef) { … clampTo(entries.size) }`：恢复时按**现在**的条目数夹一下
  （见下一节）。

## 四、`clampTo` 的两条规则，以及为什么两条都要

位置是**上一次**的事实。再回来时这个目录可能已经变了：删了文件、换了排序、关掉了「显示隐藏文件」。
把越界的下标直接交给 `rememberLazyListState` 不会崩，但会落在一片空白上 —— 屏幕上看像
「这个文件夹打不开」，实际只是列表比记忆里短了。

```kotlin
internal fun BrowseScrollPosition.clampTo(itemCount: Int): BrowseScrollPosition {
    if (itemCount <= 0) return BrowseScrollPosition.TOP      // ← 不能省
    val clamped = index.coerceIn(0, itemCount - 1)
    return BrowseScrollPosition(
        index = clamped,
        offset = if (clamped == index) offset.coerceAtLeast(0) else 0,
    )
}
```

1. **`itemCount <= 0` 必须提前返回**：`coerceIn(0, -1)` 会抛
   `IllegalArgumentException: Cannot coerce value to an empty range`。空目录恰好是
   「进来过一次、什么都没看见」的最常见状态，这个分支一定会被走到。
2. **下标被夹过就把偏移清零**：偏移的语义是「第 N 行上方藏了多少像素」，它属于被换掉的那一行。
   留着它只会得到「第 N 行上方空出一大块」。

## 五、面包屑为什么 `scrollToItem(lastIndex)`

`CrumbRow` 的 `LazyRow` 之前没有传 `state`，横向滚动量固定在 0：深层路径从最左端开始画，
屏幕上只剩 `内部存储 › Download › …`，而「我现在在哪」被挤到右边 —— 路径越长越明显。

三点选择：

- **`scrollToItem` 而不是 `animateScrollToItem`**：这是「本来就该在那里」的位置，不是一次动作。
  每次进目录都演一段横向滚动只是噪音。
- **`LaunchedEffect(trail.crumbs)`**：只在路径真的变化时重跑。用户自己划走之后，
  只要不切目录就不会被拽回来（`crumbs` 是 `List<Crumb>`，它的 equals 按内容比较，
  同一个目录重组多少次都不会重跑）。
- **停在最后一段的 `item` 起点**：如果当前这一层自己的名字比屏幕还宽，`LazyRow`
  在滚动方向上不限宽，会把它铺开，这里露出的是它的**前半截**。这不是缺陷：
  面包屑要交代的是「在哪一级」，完整名字在顶栏标题上。

`key = { index, _ -> index }` 保持不变：面包屑按层级身份复用，切换目录时不希望
每个 `Crumb` 都被当成不同的 item 而丢掉滚动状态。

## 七、测试怎么盖住

`BrowserScrollMemoryTest`（8 例）—— 所有会出错的决定都在这里，因为 `LazyColumn` 本身在
`feature:library` 里测不了（该模块只有 `testImplementation(libs.junit)`，
没有 `compose-ui-test`，也没有 `coroutines-test`）：

1. `没去过的目录问出来是 null，而不是顶格` —— **`null` 与 `(0, 0)` 必须是两个值**：
   前者「没记过」（走默认初始值），后者「记过，就是顶格」。合并两者会让将来的
   「恢复失败」无法与「本来就在顶部」区分。
2. `不同目录各记各的，不会互相顶掉`
3. `同一个目录再记一次以最新的为准`
4. `超过上限时淘汰最久没碰过的那一层` —— 20 个之后再加一个，最早那个被淘汰；
   并且**重新记一次等于「又被碰过」**（`remember` 先 `remove` 再 `put`，靠 `LinkedHashMap`
   的插入序把最近用过的挪到末尾）。
5. `条目变少时下标夹到最后一条，偏移清零` ← 本版最容易写错的一条
6. `条目够多时原样恢复，偏移保留`
7. `空目录恢复成顶格，不会拿到负数下标` ← 挡 `coerceIn(0, -1)` 的崩溃
8. `负的下标和偏移都收成顶格` —— 防御性：外部若喂进负数（例如将来的持久化读盘），不会传给列表

未覆盖（JVM 上测不了）：`rememberLazyListState(initial…)` 的实际落点、`snapshotFlow` 的
写入时机、`LaunchedEffect` 的重跑条件、`CrumbRow` 的横向停靠。这几处只能实机看，
本版没有可连的设备（第十节）。

## 八、已知限制（工程视角）

- 位置**只活在内存里**，进程结束就没了。要让「上次翻到哪儿」跨进程，得落盘成一个
  「ref → 位置」的持久表，且必须处理「ref 已经不在了」（SAF 撤销授权、文件被删）——
  这属于新需求，不在本版。
- 键是 `ref`，不是路径。好处是 SAF 与文件系统目录各自自洽、同一层从不同入口进来落到
  同一条记录；代价是**同一棵目录树的两条不同 `ref`**（例如文件系统路径
  和 SAF 文档 uri 指向同一个目录）会有两条独立记录。这在本项目里不构成问题：
  「浏览」页内部的来源是互斥的，同一层只有一种 `ref`。
- 记的是**位置**（第几条 + 像素偏移），不是**是哪条文件**。目录内容被大幅改动后，
  恢复的位置按新列表夹住，可能不再对着同一个文件。按文件记被否决（见第九节）。
- 恢复只发生在 `DirectoryList` **初次组合**时。同一个目录内容**原地刷新**（例如返回后
  `Ready` 直接换成新的一份、且条目数没变）不会重新应用记忆位置 —— 此时列表自己
  已经停在原处，反而是正确的。
- 容量 20 是硬编码常量（`BrowserScrollMemory.DEFAULT_CAPACITY`），没有设置项。20 层之外
  返回顶部，与「压根没记过」表现一致。
- 面包屑停在最后一段的**开头**，见第五节。

## 九、被否决的方案

| 方案 | 否决原因 |
| --- | --- |
| 在 `LazyColumn` 上 `remember { mutableStateOf }` 记住位置 | 列表随 `Loading` 帧离开组合，`remember` 必然丢；这正是本 bug 的成因 |
| 把位置放进 `BrowseUiState` | 每帧滚动都写 `StateFlow` ⇒ 整页重组；滚动越顺重组越密 |
| `DisposableEffect { onDispose { 保存 } }` | `onDispose` 在 applyChanges、新分支 `remember` 在 composition ⇒ 内容原地刷新时读到旧值，恢复错一间（第三节） |
| 按「首条可见的 `entry.ref`」记，恢复时 `scrollToItem(key)` | 文件被删/改名后找不到 key，只能二选一地猜；且 `scrollToItem(key)` 拿不到「这一行被推上去多少像素」，恢复会跳一截 |
| 恢复时用 `LaunchedEffect { scrollToItem }` 事后纠正 | 会先画一帧顶部再跳过去（可见的闪动）；`initial…` 参数本来就是为这件事存在的 |
| `snapshotFlow` 里加 `distinctUntilChanged` | 相邻两次 `(index, offset)` 变化本就不同；加了只是多一层算子，不减少写入 |
| 位置存到 `SavedStateHandle` / 磁盘 | 见第八节第一条：跨进程不是本版需求，且要额外处理 ref 失效 |
| 面包屑用 `animateScrollToItem` | 位置是「本来就该在那里」，每次进目录演一段横向滚动是噪音 |
| 面包屑改成「只显示最后两层」 | 用户需要往上跳任意一层，砍掉层级等于砍掉导航；滚动是更小的代价 |
| 面包屑的 `key` 改成 `crumb.label` | 同一目录下重名的层（两个同名文件夹）会 key 冲突；层级序号才是稳定身份 |
