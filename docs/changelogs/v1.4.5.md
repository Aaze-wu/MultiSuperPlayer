## 一、这一版做了什么

`todo/bugs.txt` 里挂着的三条 v1.4.5，三条都是「用户先看见症状，代码里找不到对应的一行」：

| 问题 | 表面症状 | 真正坏在哪 |
| --- | --- | --- |
| 浮窗拖动满屏抖 | 手指一拖，窗口乱窜、来回弹，100% 复现 | 位移用「**窗口内坐标** + 自己请求的目标位置」算，而窗口实际位置**滞后约两帧** ⇒ 每帧过补 100~1000px |
| 浏览页文件不进「最近」 | 播完了，「最近」一条都没有 | 记录**写进去了**，但「最近」的投影只认媒体库里的 id，而浏览页的文件刻意不在库里 |
| 发版构建两条 lint 报错 | 每次 release 都打两行 `FullBackupContent` | 排除的是一个从未被 `include` 的域（`file`）⇒ 这条 exclude 无效 |

三条的共同点：**没有任何一条会抛异常**。第一条是数值错（每帧抖动 100~1000px），第二条是
「数据在但视图不要它」，第三条是纯噪音。所以这一版的重点不是改代码，是**把判据写成能测的东西**。

另外还加了一条不算 bug 的改动：**浮窗宽度固定为屏幕的 92%**（以前 `widthIn(max = ...)`，
窗口会随那一句的长短伸缩）。它和第二节是同一个窗口对象上的两件事，所以顺手一起做了，
理由与坑都写在第二节末尾「顺带：宽度也固定下来」。

## 二、浮窗抖动：补偿的基准错了

### 症状与测量

手指匀速往下走 200px，窗口纵坐标走成
1750 → 1650 → 1600 → 1557 → 1582 → 1649 → 1741 → 1894 → 1878 → 1545 → 982 → 811 → 1749 → 2150：
先跟手、再倒着窜、再顺着窜。不是「跟不上」，是**被过补**，一帧错 100~1000px。

### 根因：混用了两种坐标系，而前提不成立

拖动那几行原来的算法是：

```text
位移 = 手指在**窗口内**的位置 − 按下时的窗口内位置
新窗口坐标 = 我们**刚请求**的窗口坐标 + 位移
```

第二行有个没写出来的前提：**窗口已经挪到我们请求的位置了**。前提不成立——
`WindowManager.updateViewLayout()` 是异步的，实测窗口的真实位置比 `layoutParams`
里的请求值**慢大约两帧**。于是：

1. 第一帧：`layoutParams.x` 已经变成「目标值」，窗口还停在旧位置；
2. 手指在窗口内的坐标仍然以**旧位置**为原点；
3. 两者相减，差出来的就是「窗口还没挪到位」的那一段；
4. 这段差值被当成手指的位移再加一次 ⇒ **过补**，下一帧反方向再来一遍。

误差不会自己收敛：每次补偿都在读一个滞后的值，抖动就一直在。

### 修法一：位移只用屏幕绝对坐标，全程不回读窗口位置

`MotionEvent.rawX / rawY` 是**屏幕**坐标，跟窗口有没有动过完全无关。于是：

```text
新窗口坐标 = 按下那一刻的窗口坐标 + (当前 raw − 按下时 raw)
```

算一次就到位，中间不读任何「窗口现在在哪」，也就没有反馈回路、没有误差累积。
贴到屏幕边缘被夹住之后再往回拖，也不会像以前那样粘住不动。

配套还有三件麻烦事（都是实机撞出来的，每一条都会让「拖不动」看起来像没写代码）：

- **`pointerInteropFilter` 必须返回 `true`。** 返回 `false` 时 `AndroidComposeView.onTouchEvent`
  也返回 `false`，系统发过一次 `DOWN` 就不再往下发（实测整个手势只有一条 `actionMasked 0`）。
- **返回 `true` 的代价：按钮不能再用标准点击手势。** `clickable` / `detectTapGestures` 靠
  「事件有没有被消费」判断要不要取消点击，而 `DOWN`/`UP` 全被标成已消费 ⇒ 按钮永远不响应。
  那几个按钮因此改成自己判「按下之后有没有移动超过一个手指抖动的容差」。
- **判定要能被单测钉住。** 拖动状态机抽成 `WindowDragTracker`（纯 Kotlin，9 例：没过阈值不上报、
  刚过阈值报开始并保留按下点、开始之后每帧报移动、拖动中松手报结束、结束之后不再报移动、
  斜向按直线距离算阈值、第二次按下重新开始……），窗口那边只负责把 `START/MOVE/END` 接到
  `params` 上。

同一批用例还抓出一个真 bug：`up()` 之后如果还收到一个迟到的 `MOVE`，光看「不在拖动中」
会把它当成**新的一次拖动开始**，窗口被莫名拽走一大截。加一个 `released` 标志位解决。

### 修法二：坐标的仲裁（顺带做掉的第二层）

除了手指，还有两个写入方，它们之间也会互相拉扯：

- **拖动中只有手指说了算。** 设置值到达时直接返回，而且**连 `lastSeenPosition` 都不更新**
  （否则松手后同一个值会被当成「新值」再摆一次）。
- **设置值只在真的变了的时候应用。** `lastSeenPosition` 记住上一次见到的值，重复的丢弃。
- **松手后短暂「等自己存的值回环」。** `dragEnd` 把坐标交给 `controller.savePosition()`，
  数据层回来时会再触发一次 `show()`；这一次**不能**再摆（窗口已经在手指放下的位置），
  所以 `settlingPosition` 记下刚存的值，等它回来时只结束等待、不应用。
- **这个「等」必须有超时（1.5s）。** DataStore 在值没变时**不会再发**，那设置页的
  「重置位置」就永远不生效。
- **布局变化只做收边，不算位置。** `onLayoutChanged()` 拖动中直接返回；否则先试
  `pendingPosition`（窗口尺寸还没量出来时暂存的设置值），再否则 `clampCurrent()`。

判定本身抽成一个**纯函数**（`desktopLyricsPositionStep`），五种结果：

| 结果 | 什么时候 | 应用 | 结束等待 |
| --- | --- | --- | --- |
| `IGNORE_WHILE_DRAGGING` | 拖动中 | ✗ | ✗ |
| `IGNORE_REPEATED` | 与上次见到的值相同 | ✗ | ✗ |
| `IGNORE_ECHO` | 与刚存的值相同（自己存的那次回环） | ✗ | ✓ |
| `IGNORE_STALE` | 在等回环，来的又不是它（旧值） | ✗ | ✗ |
| `APPLY` | 新值，且不在等回环 | ✓ | ✓ |

优先级：拖动 > 重复 > 回环。写成 `when` 而不是一堆 `if`，是为了「新增一种情况时必须显式归类」。

> 这一层**不是**抖动的主因（主因见「修法一」）。它挡的是另一类症状：
> `controller.state` 里带着 `positionMs`，播放中大约每 200ms 发一次值，
> 把每次重发都当成「用户改了位置」去摆窗口，等于在拖动中每 200ms 把窗口
> 从手指底下拽回原地。两层都修掉之后「拖着走就是走」才真正成立。

### 顺带：宽度也固定下来

改动前宽度是 `widthIn(max = 屏幕的 92%)`，也就是**窗口本身随那一句多长而伸缩**：
五个字是一个小方块，二十个字是一条长条，切歌时左右两边一起跳。更麻烦的是位置按
**左上角**存 ⇒ 宽度一变视觉中心就漂（同一个 `x`，宽窗口看着偏右、窄窗口偏左），
用户会以为「它自己挪了」。现在改成固定宽度（屏幕的 92%，沿用原来的上限），
**高度仍然包裹内容**（有没有译文决定是两行还是三行）——把高度一起钉死就得为
「没有译文时」预留一整行空白，比高度变一下更难看。

这里有个必须记下来的坑：**宽度只能在窗口层给，不能在 Compose 里 `.width(...)`**。
`WRAP_CONTENT` 的浮窗交给 Compose 的父约束上限**不是屏幕宽**——实测 411dp / 420dpi
的屏幕上 `constraints.maxWidth == 840px`（正好 320dp），而 `Modifier.width` 和
`Modifier.requiredWidth` 最终都会走 `Constraints.constrainWidth`，算出来 993px 也会
被夹回 840。症状极具迷惑性：代码里写着 92%，量出来永远是 78%，怎么调都到不了。
正解是显式给 `WindowManager.LayoutParams.width`（`fixedWidthPx()`），Compose 那边
只要 `fillMaxWidth()`；转屏/分屏时在 `onLayoutChanged()` 里 `syncWidth()` 跟着改。

## 三、浏览页的文件为什么不进「最近」

### 事实核对

先证明**记录是有的**：`ExoPlayerController.persistTrackedPosition()` 用
`positionStore.write(trackedMediaId, position)` / `markPlayed(id)` 落盘，
`trackedMediaId` 对浏览页文件是 `file:<ref>`（`BrowserEntry.isBrowserMediaId` 认的那种）。
再证明**视图不要它**：`RecentPlayRules.project()` 每一步都要求 `mediaId` 命中
`MediaLibraryState.Ready.entries`，而浏览页的文件**按设计不进媒体库**（那是它和媒体库的分界）。
两边都「没错」，错的是它们的接缝。

### 修法：库外再解析一次，且只解析「库里没有的」

```
records ──unresolvedIds()──► [库里查不到的 id] ──RecentMediaResolver.resolve()──► [临时 MediaEntry]
    └────────────────────────── project(records, entries + resolved) ─────────────────────────┘
```

- `RecentPlayRules.unresolvedIds`（纯函数）负责**点名**：按 `savedAtMs` 倒序、跳过
  `positionMs < 0`（播完的不需要位置）、去重、`take(limit)`。有上限是因为每个 id 都要付出
  一次跨进程 `query` / `stat`。
- `RecentMediaResolver`（`core:data`，注入 Context）负责**取数据**：
  - `file:` → `localFilePath()` → **要求 `isFile`**（不用 `exists`：U 盘重挂之后同名目录会顶替文件）；
  - `content:` → 先 `query(Document)` 拿名字 / 大小 / MIME；**故意不查 `last_modified`**
    （MediaStore 那边它叫 `date_modified` 且单位是秒，列名不存在会直接抛）；查询抛异常或
    返回空行时退一步 `openAssetFileDescriptor(uri, "r")` 试打开，打得开就当还在；
  - 名字回退：`Uri.decode(最后一段).trim()`；
  - `SafScanRules.kindOf(name, mimeType)` 返回 `null`（例如 `.lrc`）⇒ 丢弃，**不生成点不动的行**。
- 结果只活在**当次 `recent()` 的内存里**：不写回库、不改记录、不删记录。所以文件回来自动出现，
  文件没了自动消失（`runCatching` 逐 id 兜住，一次失败不影响其它条）。

## 六、被否决的方案

| 方案 | 为什么不做 |
| --- | --- |
| 拖动中干脆把整个 `sync()` 停掉 | 拖动以外还有「切换歌曲」「内容变化」要重绘；把 `sync()` 停掉会连带停掉别的更新 |
| 拖动时给 `sync()` 加一个 `if (dragging) return` 就完事 | 它只能挡住「别的组件回写坐标」，挡不住**每帧内部的过补**；抖动的主因在算法本身 |
| 每帧回读一次 `layoutParams.x/y` 再算补偿 | 读回来的是**滞后两帧**的值，补偿永远在追一个追不到的目标，误差不会收敛 |
| 用 `event.positionChange()` 累加位移 | 它等于 `position − previousPosition`，而 `previousPosition` 在 Android 后端取自 `MotionEvent` 的历史采样点；一次事件里没有历史点时 delta **恒为 `0.0`**。症状是长按成立、拖动不生效，且只在特定设备/采样率下出现——手边另一台机器可能永远看不出来。自己用 `raw` 差才语义明确 |
| 用 `Modifier.width(92%)` 固定宽度 | `WRAP_CONTENT` 浮窗里 Compose 拿到的 `constraints.maxWidth` 是 **840px**（`Modifier.requiredWidth` 也走 `Constraints.constrainWidth`）⇒ 993px 被夹回 840，代码里写着 92%，量出来永远是 78% |
| 在 Compose 里给 `widthIn(min = ...)` / `defaultMinSize` | 同样受 840px 上限约束；而且即使生效也只是「硬撑」，不如在窗口层把它定下来干净 |
| 连高度一起固定 | 行数取决于有没有译文（双语三行 / 仅原文两行）与字号；高度定死就得为「没有译文时」预留一行空白，比高度变一下更难看 |
| 拖动中把 `savedPosition` 实时写成当前坐标 | 每移动一像素写一次 DataStore；而且回环会和手指抢坐标，抖动照旧 |
| 等回环不设超时 | DataStore 在值没变时**不发**，设置页的「重置位置」会静默失效 |
| 用 `SystemClock` 之外的时间（`elapsedRealtime` / 墙钟）做超时 | 本版只需要单调时钟；`uptimeMillis` 语义正好（不含深睡） |
| 布局变化时按「居中」「贴边」重算位置 | 那等于替用户决定窗口在哪；只收边（clamp）是唯一不撒谎的行为 |
| 把浏览页的文件**加进**媒体库再从「最近」显示 | 违反既有分界（媒体库 = 系统扫到的），会让「最近」「媒体库」两个入口互相污染，且库表会被临时的播放记录改写 |
| 解析不到就删掉那条播放记录 | 记录是「我看过这个文件」的事实，文件暂时不可读不代表事实作废 |
| 让 `project()` 自己去做 IO | 它现在是纯函数、被单测钉着；一旦掺 IO，7 条既有用例全变成 Mock |
| `content:` 也查 `last_modified` | MediaStore 那边叫 `date_modified` 且单位是秒，列名不存在会抛；这一版不需要它 |
| 解析时用 `exists()` 判断文件 | U 盘重挂、同名目录顶替文件时会误判成「还在」，然后点开报错 |
| 把 `cache` 那两条改成 `include` 了 `file` 域再排除 | 等于顺带开始备份 `files/` 下的下载与模型，比留两条 lint 报错更糟 |

## 七、已知限制（工程视角）

- **浮窗不再自动归位**：只保证不出屏。这是第二节「修法二」里那条「布局变化只收边、不算位置」
  的直接代价，写在用户说明的已知限制里。
- **`settlingPosition` 是「猜」**：它靠 `position == 刚存的值` 判断这是自己的回环。如果用户在
  1.5s 内从设置页把值改成**同一个数字**（例如拖动后又把「重置位置」按回同一个坐标），这次修改
  会被当成回环吞掉。概率极低，且后果只是「那一次没生效」。**它不是抖动的原因**——抖动是
  第二节「修法一」里那个滞后补偿，`settlingPosition` 只影响「谁有权改坐标」。
- **宽度固定后短歌词两侧会留白**：一句五个字也占屏幕的 92%，文字居中，两边是空的。
  这是「宽度不随内容跳」的代价（反过来就是以前那个「切歌时左右伸缩、视觉中心漂」）。
- **宽度只在屏幕尺寸变化时重算**：转屏、分屏、改显示大小会在下一次布局变化时跟上去；
  不重启、不重建窗口。
- **库外解析的成本是 O(名单长度)**：每个 id 一次 `query` / `stat`，跑在 `dispatchers.io` 上，
  上限沿用「最近」页的 `DEFAULT_LIMIT`。文件在慢速云盘上时会拖慢「最近」页首帧（列表其它行先出）。
- **解析结果不缓存**：每次进「最近」都重新查一遍。缓存要失效策略（文件可能被删/被恢复），
  这一版选择不缓存。
- **`content:` 的条目没有缩略图**：它不是媒体库里的东西，要另外解码一次。
- **`unresolvedIds` 与 `project()` 各算一次排序**：多一次 O(n log n) 的排序，n 是播放记录数
  （本地量级，可忽略），换来 `project()` 完全不改。
- **两条备份规则的删除不改变备份内容**：`file` 域本来就没被 include。

## 八、发版核查

按 `docs/release-process.md` 的顺序：改版本号 → 写两份文档 → **先提交、再打 tag** → 编译
→ 归档 → 建 Release。`assembleRelease` 在配置阶段执行 `git describe --tags --always --dirty`，
所以提交与 tag 必须在编译之前，否则包里的抬头会是上一版的 tag 加 `-dirty`。

```powershell
git add -A
git commit -m "fix(v1.4.5): 浮窗拖动不再抖 + 浮窗宽度固定 + 浏览页文件进最近 + 清掉两条无效备份规则"
git tag -a v1.4.5 -m "v1.4.5"
.\gradlew.bat assembleRelease
Get-FileHash dist/MultiSuperPlayer-v1.4.5.apk -Algorithm SHA256
gh release create v1.4.5 dist/MultiSuperPlayer-v1.4.5.apk --latest `
    --title "v1.4.5 桌面歌词浮窗拖动 / 浮窗宽度固定 / 浏览页文件的播放记录" `
    --notes-file docs/release-notes/v1.4.5.md
```

`versionCode` = `major*10000 + minor*100 + patch` = **10405** > 10400，可直接覆盖安装。

实际执行结果（2026-10-19）：`aapt2 dump badging` 确认 `versionCode='10405' versionName='1.4.5'`；
`lintVitalRelease` 无输出（两条 `<exclude domain="file" path="cache"/>` 删掉后不再报错）；
`gh release list` 里本版带 **Latest** 标记、`isPrerelease=false`；Release 附件的 `digest`
与本地 `Get-FileHash` 完全一致。

**这一版不发 beta**：三条改动都在应用内的界面与数据投影上，没有清单 / 权限 / 系统 intent 变化；
`backup_rules.xml` 的改动不影响运行期行为（见第七节）。照 v1.2.3 / v1.4.0 那条路直接发正式版。
