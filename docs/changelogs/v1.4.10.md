## 一、这一版是什么

v1.4.9 发出去之后，用户拿到真机反馈两句话：

> 「顶部的路径显示还是有点问题，建议用虚拟机测试」
> 「而且滚动状态不是百分百触发」

两句都是对的，而且都指向同一类问题：**v1.4.9 的思路对了，实现里各留了一个「有时候」**。

| 症状 | v1.4.9 的实现 | 真实成因 |
| --- | --- | --- |
| 当前层被切掉尾巴、没有省略号 | `LazyRow` + `scrollToItem(lastIndex)` | `scrollToItem` 对齐的是**这一项的开头**，不是末尾；且到末尾会被夹住 ⇒ 尾巴在屏幕外 |
| 最左边露出「半个字」 | `contentPadding` 左右各留 12dp | `contentPadding` 只让内容**停在**那里，可滚动内容仍然会滑到 padding 下面并被裁切 |
| 滚动位置「有时」记不住 | `rememberLazyListState(initial…)` + `snapshotFlow` | ①`rememberLazyListState` 复用 `rememberSaveable` 的**同一个实例**，`initial…` 被忽略；②`snapshotFlow` 首次发射是 `(0, 0)`，它不是用户动作，却把恢复好的位置写回去了 |

改动仍然只落在 `feature/library` 的一个文件里（`BrowserPane.kt`，+155 / −39），
不落盘、不加权限、不改清单。

## 二、`CrumbRow` 为什么不再用 `LazyRow`

`LazyRow` 在这个场景里没有任何好处，只有三个坏处：

1. **它按项对齐。** `scrollToItem(lastIndex)` 把最后一项的**左边缘**放到视口左边缘，
   剩下的一截仍在右边看不见。而约束其实只有一句「最后一项要完整」——
   这个约束的正确答案是 `scrollTo(maxValue)`，即把内容推到尽头。
2. **项宽不受约束。** 这是 v1.4.9 里 `overflow = TextOverflow.Ellipsis` 完全没生效的原因：
   在滚动方向上 `LazyRow` 给子项的宽度是无界的，文本永远「装得下」，也就永远不会省略。
3. **项会回收。** 面包屑最多几十项，惰性没有任何收益。

换成一个普通 `Row` + `horizontalScroll(rememberScrollState())`，三件事同时解决：
`maxValue` 是**测量后的真实值**（右对齐天然成立），子项在滚动方向上仍然无界，
所以**必须**给最后一段显式 `widthIn(max = …)` 才能让省略号出现：

```kotlin
val scrollState = rememberScrollState()
LaunchedEffect(trail.crumbs) {
    withFrameNanos { }                 // ← 见第三节
    scrollState.scrollTo(scrollState.maxValue)
}
BoxWithConstraints(modifier = modifier) {
    val lastCrumbMaxWidth = maxWidth - CrumbEdgePadding * 2
    Row(Modifier.fillMaxWidth().horizontalScroll(scrollState), CenterVertically) {
        Spacer(Modifier.width(CrumbEdgePadding))      // ← 见第四节
        trail.crumbs.forEachIndexed { index, crumb -> … }
        Spacer(Modifier.width(CrumbEdgePadding))
    }
    if (scrollState.value > 0) { /* 左边缘遮罩，见第五节 */ }
}
```

## 三、`withFrameNanos { }` 那一帧不能省

`ScrollState.maxValue` 在**测量之前**的初值是 `Int.MAX_VALUE`（不是 0，也不是 `Int` 的类型上限
之外的某个哨兵 —— 就是字面上的 `Int.MAX_VALUE`）。`LaunchedEffect` 在 composition 之后、
首帧测量之前启动，此刻读 `maxValue` 拿到的是 `Int.MAX_VALUE`，`scrollTo` 到一个不存在的
量会被夹到当前可滚范围（此时是 0）—— 表现就是「首帧不滚，第二次进才滚」，
一个典型的「有时」。

`withFrameNanos { }` 让出到下一帧，测量已经完成，`maxValue` 是真实值。

## 四、两端的留白必须是 `Spacer`，不能是 `contentPadding`

`Modifier.horizontalScroll` 的内容区包含 `padding`，`padding` **不能**阻止内容滑进它下面：
滚到底时第一段会滑到 `padding` 区域内、被 `BoxWithConstraints` 的边界裁掉，
屏幕上就是这个字的一半。

用 `Spacer` 把留白**变成内容的一部分**，它就跟着内容一起滚，两端留白永远在内容最外侧，
中间任何位置都不会有字被裁。

## 五、左边缘要「盖住」，不能「渐隐」

半截字最有欺骗性的地方是它看起来像**另一个字**：截图里「内部存储」被切掉左边后
读起来像「𠈌部存储」，繁体里「儲」被切一半直接变成「諸」。渐变（`alpha` 从 1 到 0）
解决不了这个：0.4 透明度的一半笔画仍然是一个可辨认的**错误字形**。

所以左边缘是一个**不透明的遮罩**：先一个背景色的方块 + 一个「…」，再向右 12dp 渐隐。
形状如下（`matchParentSize()`，不是 `fillMaxHeight()` —— 后者会把整行撑高）：

```kotlin
if (scrollState.value > 0) {
    Row(Modifier.matchParentSize(), CenterVertically) {
        Box(Modifier.fillMaxHeight().background(surface), Center) {
            Text("…", style = labelLarge, color = onSurfaceVariant,
                 modifier = Modifier.padding(horizontal = 6.dp))
        }
        Box(Modifier.fillMaxHeight().width(CrumbTailFade).background(
            Brush.horizontalGradient(listOf(surface, surface.copy(alpha = 0f)))))
    }
}
```

两个条件：

- 只在 `scrollState.value > 0` 时画。没滚动时叶子内容本来就从留白之后开始，
  遮罩会把第一段的第一个字吃掉。
- 遮罩层不加任何指针输入修饰符，点击照常穿透到下面的 `TextButton`。

## 六、滚动恢复为什么「不是百分百」

两个独立的时序问题，各自都能造成「有时记住、有时回到顶部」。

### 6.1 `rememberLazyListState` 复用的是同一个实例

`rememberLazyListState` 内部是 `rememberSaveable(saver = LazyListState.Saver)`。
当 `DirectoryList` 的调用点没变、只是 `directoryRef` 变了（`Ready` → `Ready`），
组合位置相同 ⇒ **同一个 `LazyListState` 实例被返回**，`initial…` 参数被完全忽略
⇒ 新目录继承了旧目录的滚动量。

v1.4.9 依赖「切目录时会先经过 `Loading`，`LazyColumn` 整棵离开组合」这个前提。
但 `BrowseRepository.listing()` 的 `Loading` 帧可能被同一帧内的内容帧合并掉
（`shareIn` + `replay = 1` 的时序），此时 `LazyColumn` **从未离开组合**，
前提不成立。

### 6.2 `snapshotFlow` 的首次发射不是用户动作

`snapshotFlow { … }` 在收集开始时会**立即发射一次当前值**。如果恢复还没生效
（`scrollToItem` 在下一帧），这次发射就是 `(0, 0)`，而它被当作「用户滚到了顶部」写进记忆
⇒ 恢复被自己抹掉。

修法是一个显式的「正在恢复」闸门：

```kotlin
val restored = remember(directoryRef) { scrollPositionOf(directoryRef)?.clampTo(entries.size) }
val listState = rememberLazyListState(
    initialFirstVisibleItemIndex = restored?.index ?: 0,
    initialFirstVisibleItemScrollOffset = restored?.offset ?: 0,
)
val restoring = remember(directoryRef) { mutableStateOf(restored != null) }

LaunchedEffect(listState, directoryRef) {
    if (restored != null) listState.scrollToItem(restored.index, restored.offset)
    restoring.value = false                       // ← 恢复之后才开闸
}
LaunchedEffect(listState, directoryRef) {
    snapshotFlow { listState.firstVisibleItemIndex to listState.firstVisibleItemScrollOffset }
        .collect { (index, offset) ->
            if (!restoring.value) onScrollPositionChanged(directoryRef,
                BrowseScrollPosition(index = index, offset = offset))
        }
}
```

两层保险：`initial…` 覆盖「实例是新的」那条路，`scrollToItem` 覆盖「实例被复用」那条路，
闸门负责不让中间那一帧的 `(0, 0)` 反过来覆盖记忆。

验收方法上的两条教训（写在这里，下次别再犯）：

- **不要在可滚动列表上盲点坐标。** 上一次盲点「子文件夹」时命中的是 `hi10p` 影片，
  直接进了播放页。每一步之间都 `dump` 一次取真实边界，比事后读日志便宜。
- **中文字符串不要经过控制台读**。PowerShell 控制台按 GBK 渲染，中文全是乱码，
  判读会全错；用 `io.open(..., encoding='utf-8')` 或
  `[System.Text.Encoding]::UTF8.GetString([System.IO.File]::ReadAllBytes($p))`。

## 八、发现但本版不处理的缺陷

验收过程里发现第三个问题，**与本版两处改动无关**：切底部标签（例如 浏览 → 媒体库 → 浏览）
会让「浏览」页回到**根目录**，目录栈和每个目录的滚动位置全部丢失。

根因在 `MspApp.kt` 的 `navigateToTab`：

```kotlin
navController.navigate(route) {
    popUpTo(navController.graph.findStartDestination().id)   // ← 弹出所有非起始标签
    launchSingleTop = true
}
```

起始标签是「播放」，其余四个标签的 `NavBackStackEntry` 都会被 `popUpTo` 弹掉，
它们的 `koinViewModel()` 随之销毁 ⇒ `BrowserScrollMemory` 一起没了。
`git log -S 'popUpTo(navController.graph.findStartDestination().id)'` 指向
`c6a1814`（v0.1.0）/ `42caaa0`（v0.3.0），即**从有底部标签起就是这样**。

不修的理由与修法记录在 `todo/bugs.txt`：改这里要么把「浏览」的状态提到 Activity 作用域
（改动面大），要么给每个标签加 `saveState` / `restoreState`（会重新引入
「在播放页点媒体库没反应」那个老问题 —— 当初正是为了它才去掉的）。属于独立的一版。

## 九、测试统账

`.\gradlew.bat test --continue` ⇒ `EXIT=0`，**186 suites · 2509 tests · 0 失败 · 0 错误**，
与 v1.4.9 逐位相同（±0）。

本版没有新增用例，原因是结构性的：两处修复全在 Compose 的测量 / 时序层面
（`ScrollState.maxValue` 的测量时机、`rememberLazyListState` 的实例复用、
`snapshotFlow` 的首次发射），而 `feature:library` 只有 `testImplementation(libs.junit)`，
既没有 `compose-ui-test` 也没有 `coroutines-test`，这些行为在 JVM 上测不到。
能测的纯逻辑（`clampTo`、LRU 淘汰）在 v1.4.9 已经测过，本版未改动。

所以本版的验收证据是**虚拟机上的节点边界比对**，不是单测数量。这也是 v1.4.9
那条「本版未连实机逐项验收」被用户当场抓到之后，刻意改掉的做法。

## 十一、已知限制

- 左边缘遮罩用的是纯背景色，若将来「浏览」页顶栏加了渐变或图片背景，遮罩需要跟着改。
- 末段 `widthIn(max = maxWidth - 2 * CrumbEdgePadding)` 在**极窄**窗口（分屏 320dp 以下）
  会把一段压到只剩省略号。此时仍可通过返回上一层得知位置，但没有「点开看全名」的入口。
- 恢复闸门是 `remember(directoryRef)` 的 `mutableStateOf`：同一个目录**原地刷新**
  （条目数变化）不会重新走一遍恢复流程，这是刻意的（此时列表仍在原处）。
- 第八节的切标签问题仍在，**「浏览」页的持久感只在「不切标签」的前提下成立**。
