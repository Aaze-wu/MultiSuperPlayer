## 一、这一版做了什么

`todo/bugs.txt` 的下一项：「歌词滚动错误，如果某句歌词较长，会有一段还藏在下面。」

只改一处行为：**音频页歌词的自动滚动**。但它踩的是同一个坑的另一面——
**用「第几行」这种离散量去表达「多少像素」这种连续量**。

| 问题 | 表面症状 | 真正坏在哪 |
| --- | --- | --- |
| 长句歌词被切掉尾巴 | 自动滚完以后这一句只能看到前面一部分，剩下的一截贴着歌词区下沿被裁掉，用户得自己往上滑才能读完 | `animateScrollToItem((activeIndex - ANCHOR_OFFSET).coerceAtLeast(0))`（`ANCHOR_OFFSET = 2`）按**索引**滚动，隐含假设「每行一样高」；而歌词行高可以是 1 行，也可以是 3~4 行（折行）+ 1 行（译文），当前行还比其余行大一号 |

之所以说它是「同一件事的另一面」：v1.4.6 修的是「**用了不该用的判据**」（后缀表不全 ⇒
落到 `UNKNOWN`），这一版修的是「**用错了度量单位**」（用行数代替像素）。两者都不抛异常、
不打日志，都只在特定内容下才看得出来。

## 二、为什么按行号滚一定会漏掉一截

旧代码想表达的是「让当前行停在歌词上方第 2 行」，这在**行高恒等于 X** 时确实等于
「当前行在歌词区里居中偏上」。于是它把「居中」这件几何问题翻译成了「索引减 2」这件算术问题。

而实际的行高有三种来源的不一样：

```text
1) 折行：一句 40 个字，视口宽度 / 字号不同 ⇒ 2 行、3 行、4 行都出现过
2) 双语：SubtitleDisplayMode 里原文 + 译文时，CueTextBlock 多渲染一行译文
3) 字号：LyricLine 对当前行用 titleMedium、其余行用 bodyLarge
        ⇒ 同一个 cue 在「变成当前行」的那一刻会长高
```

第 3 条最阴：`LaunchedEffect(activeIndex)` 只知道「换到第几行了」，**看不见当前行自己长高**。
于是「锚点上方 2 行」这个假设哪怕一开始成立，也会在当前行变高的同一帧失效。歌词区越窄、
句子越长，误差越大——到极端情况当前行整行都在视口下方，屏幕上只剩上一句的尾巴。

## 三、修法：先量，再滚

新的问题只有一句话：**这一行现在在哪、多高，还差多少像素才能让它整行待在歌词区里。**

`LazyListState` 恰好只提供像素级的那一步（`animateScrollBy`），
`animateScrollToItem` 没有任何「居中 / 对齐」选项——所以这条判断只能自己写。

```kotlin
private suspend fun LazyListState.animateScrollToLyric(index: Int) {
    if (layoutInfo.visibleItemsInfo.none { it.index == index }) {
        animateScrollToItem(index)          // ① 还没被组合出来：先按索引带进视野
    }
    val info = layoutInfo.visibleItemsInfo.firstOrNull { it.index == index } ?: return
    val delta = LyricsScrollRules.anchorDelta(
        viewportStart = layoutInfo.viewportStartOffset,
        viewportEnd = layoutInfo.viewportEndOffset,
        beforeContentPadding = layoutInfo.beforeContentPadding,
        afterContentPadding = layoutInfo.afterContentPadding,
        itemOffset = info.offset,
        itemSize = info.size,               // ② 实测高度，不猜测
    )
    if (delta != 0) animateScrollBy(delta.toFloat())
}
```

两个必须写进注释的地方：

- **① 只在「行根本没被组合出来」时用。** 拖动进度条跳到很远的位置、或者当前行自己长到
  把视口下沿撑满，才会走到这一步。正常换句时目标行本来就在 `visibleItemsInfo` 里，
  于是只有 ② 那一次动画，观感是**一次连续的滚动**，不是「先跳再挪」。
- **② 之后必须重新读 `layoutInfo`。** `animateScrollToItem` 会改写布局信息，用滚动前的
  快照算出来的位移一定是错的。代码里是「先 if 判断，再重新 `layoutInfo`」，顺序不能合并。

规则本身抽成纯对象 `LyricsScrollRules`，理由和本模块其他 `*Rules` 一样：
`:feature:player` **没有 `compose-ui-test`**，`LazyListState` / `LazyListItemInfo`
在 JVM 单测里造不出来，判断留在 composable 里就等于没测。

两条不变量（写进了类 KDoc，也被单测逐条钉住）：

1. **放得进内容区 ⇒ 滚完整行可见**（居中，上下各留一半余量）；
2. **放不进 ⇒ 顶边对齐**。整块放不下时让用户从**第一个字**开始读是唯一还有用的选择，
   居中只会把开头也切掉。

另外，居中是在**内容区**里居中，不是在整个视口里居中——`beforeContentPadding` /
`afterContentPadding`（`compact` 与否取 24dp / 8dp）必须扣掉，否则「贴着上沿」其实还压着
一段留白，视觉上仍然像被切了。

### 第二遍修正：像素算对了，方向反了

上面这套「先量再滚」的几何本身没错，第一版实测也确实把长句拉回来了。**但它只在
开头一两秒是对的**：滚过几句之后，屏幕上最前面的句子会一条一条消失，用户看到的是
「开头那几句不见了」——一个和长句毫无关系的新症状。

原因是一个符号：`anchorDelta` 算的是「**这一行要移动多少像素**」，而 `animateScrollBy(x)`
移动的是「**列表滚动多少像素**」，两者数值相同、方向相反（往下滚 ⇒ 行的 `offset` 变小）。
第一版直接把前者喂给后者，于是每换一句列表都朝错方向滚，把上文顶出视口。

| 输入 | `itemOffset` | 期望停在 | 第一版返回（错） | 现在返回 |
| --- | --- | --- | --- | --- |
| 第 1 句（已在上沿之上） | 0 | 171 | +171（往下滚 171 ⇒ 更看不见了） | −171 |
| 第 4 句（正好居中的位置附近） | 553 | 171 | +382 | −382 |

为什么第一轮实机没抓到：**它在时间上是有延迟的**。第一句自己的 `desiredTop` 恰好在视口
内，滚动量很小；错误累积到「开头被推出视口」要换过两三句，也就是 8~15 秒之后。

定位方式是**加日志实测而不是继续猜**（`MspLog.d` 打到 `itemOffset` / `itemSize` /
`viewportStart` / `viewportEnd` / `delta`，连续 5 句读数）：

```text
0 位置=0   高=85  补位移=+305   first=2/71   ← 第 1 句被自己的「修正」顶走了
1 位置=71  高=71  补位移=+188   first=3/71   ← 同上，一路往上顶
2 位置=142 高=71  补位移=+71    first=4/71
```

符号一改，同一份日志变成 `−305 / −188 / −71 / +46 / +117`，`first` 稳定在 0。

**新增的用例就是钉住这个符号**：`正数代表往下滚负数代表往回滚`，并且原有全部断言都从
「滚完以后上沿 = `itemOffset`」改写成「滚完以后上沿 = `itemOffset − 返回値`」——
第一版那 11 条之所以全绿却漏掉了符号，正是因为它们断言的是「移动量」而不是
「移动之后的位置」，符号错两次就互相抵消了。**纯函数写错符号时，「看起来对不对」这件事
完全靠不住，必须把最终位置写成断言。**

## 五、测试怎么盖住

新增 `LyricsScrollRulesTest`（12 条，全部走 `anchorDelta`）：

> 所有期望值都以「**滚完以后这一行的上沿在哪**」的形式断言：`top = itemOffset - 返回值`。
> 第一版按「返回多少位移」断言，符号反过来也照样全绿——这是它漏掉方向 bug 的直接原因。

| 用例 | 钉住什么 |
| --- | --- |
| `长句的尾巴被视口切掉时滚完以后整行可见` | 本 bug 的直接回归：行尾超出内容区下沿 ⇒ 返回正数（往下滚），滚完上沿落在 160 |
| `正数代表往下滚负数代表往回滚` | 符号契约本身（第二遍修正新增）：当前行在上沿之上 ⇒ 必须返回负数 |
| `已经在中间的行不动` | 已经居中的行返回 0 ⇒ 调用方不会再动画一次（避免「每换一句抖一下」） |
| `上面的行很长把当前行顶出视口时往上滚回来` | 另一种失败形态：当前行被上文挤出视口下方 |
| `比内容区还高的行顶边对齐而不是居中` | 第 2 条不变量 |
| `正好和内容区一样高的行按顶边对齐` | 边界：`itemSize == bandHeight` 走「放不下」那一支（`>=` 而不是 `>`） |
| `内边距算进内容区` | `compact` 那档 8dp 与常规 24dp 的结果不同 ⇒ 居中基准是内容区不是视口 |
| `视口还没量出来时不动` | `viewportEnd` 为 0 / 负 ⇒ 返回 0（首帧） |
| `内边距比视口还大时不动` | 内容区高度 ≤ 0 ⇒ 返回 0 |
| `行高还没量出来时不动` | `itemSize` 为 0 / 负 ⇒ 返回 0（还没组合出来） |
| `同时平移视口和行位置时结果不变` | 返回值是**相对位移**，视口与 item 同时平移 137px 结果不变（坐标系一致性） |
| `放得下的行滚完一定整行可见` | 扫 `itemSize` 40…451 × `itemOffset` −400…900 的组合，逐组验证不变量 1 |

断言里**没有魔法像素数字以外的假设**：期望值都是从「滚完以后上沿应该在哪」反推出来的
（例如 `160 = 24 + (500 − 24·2 − 200) / 2`），行高一改、期望值仍然成立。

### 没被单测盖住的部分，以及为什么

- **`LazyListState` / `LazyListItemInfo` / `animateScrollBy` 都不可测**：`:feature:player`
  只有 `testImplementation(libs.junit)`，没有 `compose-ui-test`。能测的只有
  `LyricsScrollRules` 这个纯函数；「量到的数字真的传进去了」这一环靠代码只有一处传参
  （`animateScrollToLyric`）来保证。
- **「两步」里的第 ① 步（目标行没被组合出来时先按索引带进去）无法在 JVM 里构造**：
  它需要一个真实的 `LazyListState` 布局。实机路径覆盖方式是「拖动进度条跳到很远处」，
  已手工走过一次（见第九节）。
- **横屏 `compact = true` 那一支没有实机确认**：见第七节与第九节。
- **桌面歌词浮窗（`DesktopLyricsRules.desktopLyricsRows`）不受本版影响**，它按行数排布、
  不用 `LazyColumn`，因此没有同一条假设。

## 六、被否决的方案

| 方案 | 为什么否决 |
| --- | --- |
| **保留 `animateScrollToItem`，把 `ANCHOR_OFFSET` 调大**（比如 3、4） | 换一个「多数情况下还行」的常数而已。折成 2 行的句子会被调好、折成 4 行的句子仍然漏；而且短句会滚过头变成「当前行贴着上沿」。本质仍然是拿离散量猜连续量 |
| **按 cue 文本长度估行数，再算索引偏移** | 估计依赖字号 / 视口宽度 / 字体度量，估错的概率不比猜常数低；而且**当前行变高的那一帧**依然观测不到 |
| **给 `itemsIndexed` 加 `key`，缓存每行实测高度** | 高度会在「变成当前行」时变化，缓存要么过期要么需要失效通知；更直接的问题是本列表**不能加 key**——字幕 cue 的 index 由解析器给，重复时 `LazyColumn` 直接抛 `Key was already used` |
| **缩字号 / 单行省略号截断长句** | 用户报的就是「读不完全句」。截断等于把 bug 变成产品特性 |
| **把当前行做成 `stickyHeader` / 固定居中** | 那是另一种交互（卡拉 OK 式），改动面远超一个 bug 修复，也改变了短句的观感 |
| **只在 `LaunchedEffect` 里延迟几十毫秒再滚** | 猜测布局已完成，命中率随机；而且不解决「行高不是常数」这个根因 |

## 七、已知限制（工程视角）

- **自动滚动仍只在「行号变化」时触发**（`LaunchedEffect(activeIndex)`）。手动滑开之后要
  等下一句才回到当前行——这是刻意的（否则「怎么滑都被弹回当前行」，见 `LyricsPane` KDoc 第 2 条）。
  代价：用户在长句中途滑走，这一句剩下的部分不会自己回来。
- **横屏 / `compact = true` 路径只有代码对称性保证**。它走的是同一个 `LyricsPane`、
  同一个 `animateScrollToLyric`，只是 `contentPadding` 与行距不同（这两个值都从
  `layoutInfo` 读，不是写死的），但**没有在真实旋转的横屏上用手指验证过**：
  这个环境里模拟器旋转试了四种办法（`accelerometer_rotation` + `user_rotation`、
  `cmd window user-rotation lock`、`adb emu rotate`、`wm size 2400x1080`）全部没能让
  真实设备方向变化；`wm size` 那一次确实渲染出了横屏版面，但当时屏幕上的文件没有歌词。
  ⇒ 这是本版最大的验证缺口，已同时写进用户文档的「已知限制」。
- **第 ① 步（`animateScrollToItem` 兜底）本身仍按索引**，但它只负责「让目标行进入
  `visibleItemsInfo`」，随后一定由像素规则纠正 ⇒ 它按在视口上沿这件事不会残留。
- **`LyricsScrollRules` 假设「行的主轴起点 + 高度」足以描述可见性**。如果将来给
  `LyricLine` 加外边距 / 缩放动画，`LazyListItemInfo.size` 与实际绘制高度会不一致，
  那时需要把 `size` 换成实测值。
