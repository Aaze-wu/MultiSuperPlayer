## 一、这一版做了什么

**bug 修复版，没有新功能。** 两条都来自 `todo/bugs.txt`，用户可见功能集与 1.2.3 完全相同。

| 问题 | 入口 | 以前的现象 | 现在 |
| --- | --- | --- | --- |
| 状态栏 / 导航栏图标撞色 | 全局（设置 → 外观换主题基底，或系统切深浅色） | 图标明暗只在 `onCreate` 里按**系统**深浅色算一次；应用主题与系统不一致时图标与背景同色；系统切深浅色时 Activity 不重建（`configChanges` 带 `uiMode`），图标停在旧颜色上直到冷启动 | 图标跟着**应用主题**走，主题一变立即重设；全屏播放期间一律浅色（背景是系统画的深色遮罩），退出全屏 / 离开播放页交还主题 |
| 播放列表里的「文件已不在」 | 浏览 → 系统文件选择器添加目录 → 把里面的文件加进播放列表 | 条目立刻被标成「已不在」，点开报「找不到文件」 | 按 uri 的种类分路判断，文件还在就照常播放；同目录字幕也照旧能找到 |

这两条在代码上没有任何交集（一条在 `core:ui` + `feature:player`，一条在 `core:model` +
`core:data` + `feature:library`），但**症状的形状是同一个**：界面状态算过一次之后不再跟着
数据走，或者判据用错了表。第十三节记了它们各自的残量。

## 二、图标那一半：明暗有两个来源，两个都不认「用户选的主题」

旧的实现里，窗口图标的明暗由两处决定：

1. `app/src/main/res/values(-night)/themes.xml` 里的 `windowLightStatusBar`：只认**系统**的
   深浅色（`-night` 资源目录就是系统色的意思）；
2. `MainActivity.onCreate` 里的 `enableEdgeToEdge()`：默认按 `isSystemInDarkTheme` 挑图标颜色，
   而且**只挑那一次**。

于是有三种撞色：系统深色 + 应用里选浅色 ⇒ 白色图标画在近白背景上；系统浅色 + 应用里选
深色或纯黑 ⇒ 深色图标画在黑背景上；以及最容易被忽略的一种——用户在系统设置里切了深浅色，
但因为 Manifest 的 `configChanges` 带 `uiMode`，Activity **不会重建**，`onCreate` 不再跑，
图标就停在旧颜色上，直到下次冷启动。

关键的一点：这**不是某个页面**的问题。媒体库、设置、播放页全都一样，因为窗口只有一个。
所以修在主题层，而不是在各个屏幕里各加一句。

## 三、为什么是 Compose 副作用，而不是改 XML / 在 MainActivity 里再算一次

- **改 XML 不行**：XML 拿不到 DataStore 里的「主题基底」。冷启动那一帧它只能按系统色画，
  而用户可能选的是浅色、深色或纯黑——这正是撞色的来源之一。
- **在 `MainActivity` 里再算一次也不行**：`enableEdgeToEdge()` 只在 `onCreate` 跑，
  而主题设置在 Compose 里是 `StateFlow`，读到它的时候 `onCreate` 早过了。要在 Activity 里
  跟就得收 collect、判生命周期、再和 `enableEdgeToEdge` 的时机对齐——那是在 Activity 里
  重写一遍 Compose 已经有的东西。
- **挂在 `MspTheme` 上**刚好：全应用只有 `MspTheme` 知道「现在到底是浅色还是深色」
  （它算出的 `isDark` 就是界面真正用来取色的那个值，纯黑也算深色）。副作用挂在它上面，
  就自动获得了两种重跑：主题设置变了 ⇒ `isDark` 变 ⇒ 重跑；系统深浅色变了 ⇒
  `isSystemInDarkTheme()` 变 ⇒ 重组 ⇒ 重跑。

实现是 `SystemBarIconAppearanceEffect(useDarkIcons)`（`core:ui` 的 `chrome/SystemBarIcons.kt`），
内部 `DisposableEffect(window, useDarkIcons)`——**键里带 `useDarkIcons`**，因为这地方只在
「明暗变了」的时候才该写窗口，不是每次重组都写。`LocalInspectionMode` 时直接 `return`：
预览里没有真窗口，去碰 `WindowInsetsController` 只会崩。

写入走的是公开的 `applySystemBarIconAppearance(window, useDarkIcons)`，两个 flag 一起写
（只改状态栏会让底部导航栏在横屏时留一半错色）。`WindowInsetsControllerCompat` 已经把
API 26/27 的 `SYSTEM_UI_FLAG_LIGHT_*` 和 30+ 的 `WindowInsetsController` 的差异吃掉了，
这里不需要版本判断。

还有一处**必须**用 `tailrec` 剥 `ContextWrapper` 的 `findActivity()`：Compose 给的
`LocalContext` 可能是包了好几层的 wrapper，`as? Activity` 会静默拿到 null，症状是
「副作用跑了但什么都没发生」，不报错。`feature:settings` / `feature:player` 里已经各有一份
同名函数，那两处先于这里存在，改它们属于无关重构，所以这一版先各留一份。

## 四、全屏是唯一的例外，而它的「另一半」是本版一起修的

全屏播放时系统栏是隐藏的，用户从边缘划出来那一刻它浮在画面上，系统会在它后面画一层深色
遮罩。这时如果按主题算——浅色主题 ⇒ 深色图标 ⇒ 压在深色遮罩上等于看不见。所以
`PlayerFullscreenEffect` 里再声明一次：

```kotlin
applySystemBarIconAppearance(window, useDarkIcons = !fullscreen && !isDark)
```

规则本身没变：图标的作用是对比它**身后那一层**的颜色，只是全屏时身后不是应用的主题色。
`DisposableEffect` 的键从 `fullscreen` 变成 `(fullscreen, isDark)`，于是「全屏中换主题」
也会重跑。

**本版顺带修掉的另一半**：`onDispose` 里只 `show(systemBars)` 是不够的——在全屏中直接离开
播放页（返回键 / 收起）时，上面写的「浅色图标」会留在媒体库、设置页上，浅色主题下就是
白图标画在白背景上。所以 `onDispose` 里补一句 `applySystemBarIconAppearance(window, useDarkIcons = !isDark)`，
把图标还给主题。这条在真机上单独点过（第十一节「全屏中直接离开」那一行）。

## 五、播放列表那一半：两个各自独立的原因，修好一个还是看不见文件

用户的描述是一句话（「加入播放列表后报找不到文件」），但代码里有**两条**路会走到同一个症状：

1. **判据错了**：`PlaylistItem.sourceOf` 把 `saf:` 前缀的 id 归到 `MEDIA_STORE`，
   而探活用的是一句 `File(path).exists()`——对 `content://` 判据必然返回 false。
2. **查错了表**：`LibraryMergeRules` 去重时，同一个文件既在 MediaStore、又在授权的 SAF 目录里
   时保留 MediaStore 那条（它的 artist/album/duration 更全），SAF 那条不进库。于是播放列表里
   存着的 `saf:` id 在 `byId` 里**永远**查不到。

只修第一条不够：`saf:` 条目仍然会在 `resolvePlaylistItem` 的第一步 `byId[mediaId]` 上落空并
直接 `return null`；只修第二条也不够：即使探活跑了，`File(...)` 对 content uri 仍然是 false。
两条都必须修，而它们各自都有单测守着（第十节）。

## 六、`saf:` 归到媒体库不是「保守」，是判错

代码里原来那条注释的理由是「不能因为看起来不像数字就下结论，猜错会把 SAF 条目送去按文件
路径查字幕」。这个担心是对的，但结论反了：

- `saf:` 背后是 `DocumentsProvider` 里的一棵树，**有完整的目录层级**；
- 把它当 `MEDIA_STORE`，回放时字幕查找会去问 `MediaStore` 的 `RELATIVE_PATH`——而 SAF 目录里
  的文件 MediaStore 根本看不见（云盘、应用私有目录、SD 卡受限目录都是这样），
  `relativePath` 从 `PlaylistItem` 快照里读出来也永远是 null。
- 症状就是**整个目录**的外挂字幕一条都找不到。

换句话说：它明明有目录可查，只是不在 MediaStore 的索引里。归到 `SAF_TREE`，它才能走
「按目录找同名字幕」那条路径——SAF 浏览页里早就在用同一条，只是播放列表这边没接上。

配套一处无关功能但必须做对的搬迁：`SAF_ID_PREFIX` 原来住在 `core:data` 的 `SafScanRules` 里，
而 `PlaylistItem` 在 `core:model`——依赖方向是 `core:data` → `core:model`，反向引用编译不过。
所以常量搬进 `core:model` 的新文件 `SafMediaIds.kt`（`PREFIX` / `idOf` / `isSafId` /
`documentIdOf`），`SafScanRules.SAF_ID_PREFIX` 变成 `SafMediaIds.PREFIX` 的别名、`safIdOf`
委托 `SafMediaIds.idOf`。**只搬不改语义**：写入的 id 字符串一个字节都没变，老播放列表里的
`saf:` 条目照旧认得出。

## 七、探针为什么必须按 scheme 分路（`MediaUriProbe`）

「这个条目背后的文件还在不在」这件事，只有一种问法是对的：**问那个 uri 自己**。

| uri 的种类 | 怎么问 | 为什么不能用别的 |
| --- | --- | --- |
| `content://`（SAF / 媒体库 / 第三方 provider） | 先 `DocumentsContract` 投影 `query`（只取 `COLUMN_DOCUMENT_ID`），抛异常再退化成 `openAssetFileDescriptor` | `File(path).exists()` 对任何 content uri **必然** false；只 `query` 会在个别 provider 上抛，退化路径是给它们的 |
| 文件系统路径 / `file://` / 相对路径 | `localFilePath` + `File.exists()` | 这类没有 provider，除了 stat 没有别的办法 |
| `https://` / `rtsp://` 等 | 一律 false（不支持） | 网络地址没有「文件还在不在」这个概念，硬探等于每次播放前发一个请求 |
| 空串 | 一律 false | 没有地址就是没有 |

分类本身是纯函数 `mediaUriKindOf(uri)`（`MediaUriKind`：`CONTENT` / `FILE_SYSTEM` /
`UNSUPPORTED`），因此**不需要碰 Android 就能单测**——9 条用例全在
`MediaUriKindTest` 里（第十节），其中包括 `scheme` 大小写不敏感（`CONTENT://` 也认）。

`MediaUriProbe` 由 Hilt 提供（`DataModule` 里 `single { MediaUriProbe(context = androidContext()) }`），
`PlaylistsViewModel` 的 `fileExists` 随之改名为 `uriExists = { mediaProbe.exists(it) }`——
改名不是为了好看：`fileExists` 这个名字会让人以为它只处理文件路径，而它现在处理的是
「任何能问出存在性的 uri」。`PlaybackExportState` 里那个参数名和 Kdoc 一起改了
（导出播放列表和详情页走同一个探针，两处口径必须一致）。

## 八、`PlaylistRows` 里那一层的判据：谁「自己带地址」

```kotlin
private fun hasOwnUri(mediaId: String): Boolean =
    BrowserEntry.isBrowserMediaId(mediaId) || SafMediaIds.isSafId(mediaId)
```

`resolvePlaylistItem` 的顺序变成：先查库（`byId`），查不到再问「这个 id 自己带不带地址」，
带地址才去探活，探到了就用 `item.toEntry()` 拼一个能播的条目。

`MediaStore` 的数字 id **故意不在其中**：它代表「索引里的一行」，不是某个位置的文件。
拿 uri 去验它等于把「库里没有」偷偷改成「文件还在」，而筛掉它的正是索引本身（比如媒体被
移出索引、或应用没有读该卷的权限）。这一类条目「查不到就是真的没了」，这条判定从 1.2.1 起
就是对的，本版没动。

默认值仍然是**坏的那一边**（`uriExists: (String) -> Boolean = { false }`）：忘了传探针最多
多标几条「文件已不在」，反过来会把已经删掉的文件说成还能播。

## 十、测试怎么盖住

- **uri 分类**（`core:data` 新增 `MediaUriKindTest`，**9 条**）：SAF document uri 算 content、
  媒体库 content uri 算 content、第三方 content uri 算 content、裸绝对路径算 file system、
  `file://` 算 file system、相对路径也算 file system、`https://` / `rtsp://` 算不支持、
  空串算不支持、**scheme 大小写不敏感**。
- **播放列表那一层**（`PlaylistRowsTest` 15 → **18**）：
  - `被去重挤掉的 SAF 条目只要 uri 还在就不标成不在`——这条直接对应第五节的原因 2：
    构造一个 `byId` 里**没有** `saf:` id 的库状态，断言条目仍然有 `entry`。
  - `SAF 的 uri 读不到时仍然标成已不在`——反向那条：文件真的没了就照旧标。
    （两条都留着，因为「永远不标」和「永远标」是两种不同的坏。）
  - `SAF 条目的队列项带着 SAF 来源`——回放时 `sourceOf` 必须给出 `SAF_TREE`，
    否则字幕查找会退回到问 MediaStore。
- **来源反推**（`PlaylistItemTest` 8 → **8**，改写两条）：`SAF 扫描来的条目回放时仍然是 SAF 来源`
  （原来是断言它是 `MEDIA_STORE` 的，注释里那句「猜错会把 SAF 条目送去按文件路径查字幕」
  就是被这条旧用例锁住的错结论）；`五条来源的前缀互不包含`（加了 `saf:` 之后前缀集合仍互不包含）。
  **条数不变本身是证据**：改的是「归到哪一类」，不是「加了一类」。
- **UI 状态**（`PlaylistsUiStateTest` 11 → **11**）：只把 `fileExists` 参数改名为 `uriExists`，
  断言一条没动——这一层只关心「探针说什么」，不该因为探针换了实现而有任何变化。
- **单测盖不住的那一半**：图标明暗真的写到窗口上没有（`dumpsys window` 的
  `mLastAppearance`）、全屏进出时那串**粘性**的窗口状态有没有被正确覆盖回来、
  以及 `DocumentsProvider` 的投影 query 在真实 provider 上的行为——都在真机上验
  （第十一节）。

### 又一次确认的构建期陷阱

> `res/values*/strings.xml` **不是** JVM 单测任务的声明输入。改完三语文案之后跑 `gradlew test`，
> 这些测试任务会被判成 `UP-TO-DATE`，甚至从构建缓存里 `FROM-CACHE` 恢复——改坏的文案照样「全绿」。
> 可靠做法是删掉各模块的 `build/test-results` 并加 `--no-build-cache`（本版就是这么跑的）。
>
> 这一版还有一条同样的陷阱换了个面貌：`app/build.gradle.kts` 里的 `GIT_COMMIT` /
> `GIT_TAG` / `GIT_DIRTY` 是 **buildConfigField**，它们的「输入」是 `git describe` 的输出，
> Gradle 并不知道这个依赖。所以**先提交、再打 tag、最后从干净树重打包**这个顺序不是洁癖：
> 提交前打的包，日志抬头会写着 `v1.2.3-1-gxxxx（含未提交改动）`。

## 十三、已知限制

- **图标是「按应用主题算」的，不是「按身后那一像素的实际颜色算」的。** 应用内没有让用户在主题
  之外单独指定「状态栏图标深色 / 浅色」的开关；即使用一个和界面主体色差很大的强调色，图标
  仍然按主题基底（浅色 / 深色 / 纯黑）判断。真要按实测亮度算，就得在每一帧取背景像素，
  代价远大于收益。
- **全屏播放期间是一律浅色**，不看主题。这是第 4 节那条规则的推论，不是例外：
  那时身后的背景是系统画的深色遮罩。
- **「找不到文件」只覆盖两种自带地址的条目**（浏览页的 `file:` / `content://` 与 SAF 扫描的
  `saf:`）。MediaStore 的数字 id 仍然按「库里还有没有这个编号」判断——它的磁盘路径在没权限时
  读不到，强行探只会把能播的文件误标成失效。
- **共享 / 网络地址进不了这套判断**（它们没有「文件还在不在」这个概念）。
- **探活是同步 `query` / `stat`**，跑在 `Dispatchers.IO` 上（`buildPlaylistsUiState` 与
  `playlistExportCollections` 都在 `flowOn(io)` 之内）。播放列表条目很多、且都在极慢的
  云 provider 上时，进入详情页会跟着变慢——这一版没有为它做并发或缓存。
- 本版没有改动字幕匹配规则、翻译、语音识别、更新通道与自动检查间隔的任何行为。
