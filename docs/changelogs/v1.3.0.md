## 一、这一版做了什么

`todo/thinks.txt` 里挂着两条 v1.3 的想法，这一版**都做了**，一条是清单，一条是窗口：

| 功能 | 入口 | 一句话 |
| --- | --- | --- |
| 文件 / 文件夹收藏 | 媒体库右上角星标 → 收藏页；浏览页顶栏星标 = 收藏当前目录 | 「常用的东西」从「每次翻三层目录」变成「一次点开」 |
| 桌面歌词 | 设置 → 桌面歌词；播放页控制条另有快捷按钮 | 播放器退到后台、屏幕上是别的应用时，歌词浮在它上面 |

两条互不依赖，但共用同一条原则：**界面状态必须能算出来，不能靠记性**。收藏页显示的顺序、
数量上限、某个文件已收藏与否全都是「当前收藏清单 + 当前选择集」的纯函数；桌面歌词的
「现在该不该出现」也是一个穷尽枚举（`DesktopLyricsGate`），而不是散在几处的布尔开关。

顺带做了**最近播放页的多选**：收藏的两个入口（媒体库、最近播放）里，媒体库本来就有多选，
而「最近播放」没有，于是「收藏一条刚播过的」这条路只能靠单行按钮——本版把那一页补齐成
和媒体库同一套多选（长按进入、顶栏操作条、返回键退出）。

## 二、收藏：为什么是「星标 + 独立页」而不是第六个底部标签

产品的第一版设想是把收藏做成底部导航的第六格。否决理由有两条，都不涉及工作量：

1. **底部五个标签回答的是「在哪儿找东西」**（媒体库 / 浏览 / 最近 / 播放列表 / 设置），
   收藏回答的是「我手里有一批东西」，它属于内容而不是分类维度。塞进底栏会让
   「最近播放」「播放列表」「收藏」三者的关系变得无法解释——它们本来就是同一类东西。
2. **底栏多一格的代价是全局的**：五个标签在 360dp 窄屏上已经是极限，第六格会把
   每个标签的文字压到需要缩字号。

最终形态：媒体库顶栏右上角一颗星 → 打开独立收藏页（文件与文件夹**混排**，按收藏时间倒序）。
星标本身不是「新页面」，所以不需要导航参数、不需要新的 tab 状态保存，返回键就是 `popBackStack`。

### 收藏存的是什么

`Favorite` 是 sealed interface，两支：

```kotlin
data class File(val item: PlaylistItem, override val addedAtMs: Long)
data class Folder(val kind: BrowserSourceKind, val crumbs: List<FavoriteCrumb>, override val addedAtMs: Long)
```

- **文件**直接存 `PlaylistItem` 而不是 `MediaEntry`：这是播放列表那条链上已有的「可持久化
  的条目形状」（`mediaId / uri / title / artist / durationMs / kind`），回放时靠
  `PlaylistItem.sourceOf(mediaId)` 就能还原「该去哪找同目录的字幕」。复用它的另一个好处是
  导出、失效判断这些既有逻辑不用为收藏再写一份。
- **文件夹**存**整条面包屑**（`kind` + 每段的 `label`/`ref`）。只存最末一段是不行的：
  `BrowserTrail` 的定义就是「走过的每一层」，`enterSource` 之外没有办法凭一个 ref 还原
  上层路径（SAF 的 `content://` 树 uri 能推，文件系统的绝对路径也能推，但两条推导规则
  会分叉——而分叉点正好是「收藏的目录打得开、上一级打不开」这种没人会想到的情况）。
- `BrowserCrumb.label` 是 `MspText`，落盘时必须变成字符串，所以 `FavoriteCrumb.label` 是
  `String`。这是**刻意的信息损失**：收藏名是「收藏那一刻的语言」。用户切到英文界面之后，
  一个中文名文件夹在收藏页里仍然显示中文——这与「媒体标题是用户数据」的判定一致
  （媒体标题本来也不翻译）。转换发生在 `FavoriteRules.folderOf(trail, addedAtMs, resolve)`，
  `resolve` 由 store 注入（它是唯一能碰 `Resources` 的一层）。

### 上限与去重都在纯函数里

`FavoriteRules` 是 `object`，全部纯函数，没有 Android 依赖：

| 函数 | 不变式 |
| --- | --- |
| `fileKey(mediaId)` / `folderKey(kind, ref)` | key 带前缀（`file:` / `folder:`）+ `\u001F` 分隔，文件与文件夹不会撞 key；同名不同来源的目录也不会撞 |
| `withAdded` | 幂等（已存在 ⇒ **同一个实例**返回）+ 新的排在最前 + `MAX_FAVORITES = 200` 截断 |
| `withRemoved` / `withAddedAll` | 一个都没变时返回同一个实例 |
| `contains` / `containsFolder` / `allFavorited` / `unfavorited` | `allFavorited` 对空输入返回 false（空集不能算「全部已收藏」，否则操作条上的星会凭空点亮） |

「没变就返回同一个实例」不是为了省内存，而是给 `FavoriteStore.update()` 一个
**要不要写盘**的判据：`if (after !== before)` 才写。多选 20 项里 5 项已经收藏时，
这一次写盘是必须的（有新增）；但用户点了一个已收藏的条目、动作的实际结果是「什么都不用变」
时，不该产生一次 DataStore 事务（那会连带触发一次全应用的重组）。

### 编解码：为什么手写而不是用 JSON

`FavoriteCodec` 与 `PlaylistCodec` 同一套手法：`\u001E` 分记录、`|` 分字段、`\` 转义
（`\e` / `\n` / `\R` 三个控制字符）。理由不是「我们有洁癖」，是两条实际约束：

1. **`decode()` 绝不能抛异常**。它跑在 `datastore.data.map { }` 里，抛一次整个
   `favorites` Flow 就永久坏掉（DataStore 的 map 不会重试），而用户看到的只是
   「收藏页一直是空的」。所以格式不对 ⇒ 返回 null 或跳过这一条记录。
2. **单元测试跑在 JVM 上**，`isReturnDefaultValues = true` 让 `Uri.parse` 之类返回 null。
   用 `kotlinx.serialization` 就得为它准备一套 JSON 配置与 `PlaylistItem` 的序列化器，
   而那套东西在单测里恰好是能跑通的——问题在别处：`PlaylistItem.kind` 是枚举、
   `durationMs` 是 Long，`JSON` 里 `null` 与缺失、`1e3` 与 `1000` 的差异会让
   「能读回来吗」变成一件靠猜的事。手写编解码的每一处容错都是显式的，且能被测试逐条钉住。

**认不出的 `BrowserSourceKind` 一律跳过该条记录，不退回 `FILE_SYSTEM`**。这一条是踩过
的：默认值会把一条 SAF 目录读成文件系统路径，于是「收藏的文件夹」在收藏页里显示正常、
点开却报「打不开」——错误发生在几天之后，与真正的原因（枚举改名）相隔不知道多少次启动。
跳过则只是少一条收藏，看得见、说得清。

### 写盘：`FavoriteStore` 与 DataStore 的两个坑

- 委托必须是 `androidx.datastore.preferences.preferencesDataStore`。写成
  `androidx.datastore.preferences.core.preferencesDataStore` 会因为 `core` 包里也有一个
  同名的内部扩展而编译通过、运行期抛「Context 上没有这个属性」的找不到委托。这个坑
  本版踩过一次，记在这里。
- `update()` 里只会吞 `IOException`。其它异常继续往上抛——`IllegalStateException`
  （同一个文件被两个 DataStore 实例打开）必须炸出来，静默吞掉的表现是「收藏有时保存、
  有时不保存」，而那种 bug 在真机上只能靠运气复现。

### 三个入口 + 一个信箱

| 位置 | 动作 |
| --- | --- |
| 媒体库顶栏 | 打开收藏页（`Icons.Outlined.StarBorder`） |
| 媒体库 / 浏览 / 最近的多选操作条 | 收藏或取消收藏选中项（实心/空心星 = 是否**全部**已收藏） |
| 浏览页目录顶栏 | 收藏当前目录（排序按钮左边） |

`FavoriteEditing` 是三个入口共用的一层小门面（`toggleFiles` / `toggleFolder`），返回
`MspText?`（`null` = 空输入，调用方什么都不做）。它存在的意义是把「方向判定 + 批量 + 文案」
收在一处：三个 ViewModel 各自实现一遍，迟早会出现「媒体库取消收藏、浏览页收藏」这种
同一批文件方向相反的错。

**「在收藏页点文件夹」怎么跳到浏览页**是这一版唯一需要跨页传值的地方。`Favorite.Folder`
带着整条面包屑和来源类型，塞不进导航参数（那是字符串）。做法与既有的「外部打开字幕」
完全一致：`MspApp` 里 `var pendingFolder`，收藏页写入 + `navigateToTab(BROWSE)`，浏览页
`LaunchedEffect(pendingFavorite)` 消费后回调 `onPendingFavoriteApplied` 清空。**必须清空**：
留着它之后每次点「浏览」标签都会强制跳回那个目录，用户刚进的两层子目录会被上一次的请求顶掉。

`BrowseViewModel.openFavoriteFolder` 换完整条 trail 之后**再单独查一次** `browser.listing`，
`Unreadable` / `NotADirectory` 时提示「这个文件夹已经打不开了」。不查的话用户看到的是一个
空目录——一个几天前撤销过授权的 SAF 目录，在界面上的表现和「我的文件被删了」一模一样。

## 三、桌面歌词：一个窗口，五个门

### 数据层先独立

`DesktopLyricsSettings`（`core:data/settings`）刻意**不复用** `SubtitleStyle`：

- 字幕样式的每一条都在回答「画在画面里的那行字长什么样」；桌面歌词回答的是
  「另一个窗口里的那两行怎么摆」。默认值、合法区间、消费方全都不同。
- 共用的是**时间轴**，不是外观：浮窗与播放页字幕层查的是同一份 `SubtitleDocument`、
  同一个 `subtitleCuePosition`（先缩放再平移）、同一个 `cueFocusIndexAt`、同一个
  `cueLinesFor`。这些东西已经是纯函数且有测试，浮窗**不重新实现一遍**——两处对不上
  才是最难查的那类 bug（「画面里已经显示了，浮窗还停在上上句」）。

档位仍是枚举（`DesktopLyricsFontSize` 14/18/22/28sp、`DesktopLyricsOpacity` 40/60/80/100%），
理由与 `SubtitleStyle` 相同：存浮点数既没有默认值也没法解释，滑块没人敢拖。字号这一处
**与字幕相反**，存的是绝对 sp 而不是倍率——浮窗画在别人的应用上面，那里没有「当前主题」，
倍率乘谁的基准字号都说不通；`sp` 本身仍跟随系统字体缩放。

不透明度只作用于**背景**。乘在整窗 alpha 上会让字也跟着变淡，而「看不清字」正是这个设置
要解决的问题的反面。最低档也有 40%：再淡的话浅色桌面上白字直接看不见（浮窗没有画面可以
借用对比度）。

### `enabled` 是意图，不是「现在有没有浮窗」

这一位是 `DesktopLyricsSettings.enabled` 的注释里写死的一条：没授权 / 应用在前台 /
没在放东西时它仍然是 `true`，而浮窗不出现。合成一个布尔的话，用户从系统设置里授权回来看
到开关自己关了，然后会再关一次再开一次——一个纯粹的假故障。

「现在该不该出现」由 `desktopLyricsGate(...)` 判定，返回**穷尽枚举** `DesktopLyricsGate`：

| 值 | 用户可见后果 |
| --- | --- |
| `TURNED_OFF` | 自己关的，安静地不出现 |
| `NO_PERMISSION` | 开关开着但没「显示在其他应用上层」——必须能区分，否则就是「点了没反应」 |
| `SUBTITLES_OFF` | 字幕显示模式是「关闭」（关闭字幕 = 不看文本，这一条排在「应用在前台」之前，理由见 KDoc） |
| `NO_LYRICS` | 没有正在播放的媒体，或这条没有歌词 |
| `APP_VISIBLE` | 应用在前台，播放页自己会画，不重复 |

判定顺序就是「谁的话更该听」：用户意图 → 系统授权 → 显示模式 → 有没有内容 → 前台。

### 浮窗本身

- 用 `WindowManager` + `TYPE_APPLICATION_OVERLAY`，**不是 Service**。挂窗口只需要一个
  有权限的 `Context`，application context 挂的窗口不随 Activity 销毁而消失；播放中的进程
  本来就活在 `MspPlaybackService` 的前台服务里。省掉一个前台服务就省掉一条
  `FOREGROUND_SERVICE_*` 权限、一条常驻通知，以及「凭什么它一直在跑」的质疑。
- 前台判定自己数 Activity：`registerActivityLifecycleCallbacks` 数「有几个在 resumed」，
  而不是拉 `lifecycle-process` 依赖。**计数归零后要等一个宽限期**（`LEAVE_GRACE_MS`）：
  应用内换页是 pause→resume、授权悬浮窗时系统设置会盖上来，立刻显示等于在那些界面上
  硬塞一块歌词。
- 内容最多三行：当前行（仅原文 / 仅译文 / 双语原文+译文）+ 下一行预览。行**角色**由
  `DesktopLyricsRowRole` 带出来，而不是让渲染点按下标猜（「仅译文」时第 0 行就是译文、
  双语时第 2 行又是原文——按下标猜必然猜错）。
- 窗口上的按钮：播放 / 暂停、减小字号、增大字号、锁定。
- 只含空白的 cue 当成「不画」：字幕层可以接受一条全空格的 cue（画出来就是一片空），
  但浮窗是一块有背景的板子，只含空格的 cue 会让用户看到「歌词变成了一个空框」。
- **锁定 = 触摸穿透**（`FLAG_NOT_TOUCHABLE`），只禁拖动与按钮，不解锁就再也点不开——
  所以解锁口子必须留在**别处**：设置 → 桌面歌词，以及播放页那个按钮
  （`desktopLyricsEntryAction` 在「锁着」时返回 `UNLOCK`）。把解锁做在浮窗上等于做出一个
  只能杀进程才能退出的小窗。
- 位置每次变化都要重新夹：`clampDesktopLyricsPosition` 是**纯函数**，因为三种
  「浮窗跑到屏幕外」的场景（竖屏摆好再转横屏 / 换设备或改显示大小 / 字号调大导致变高）
  在 JVM 单测里都能钉住，而在真机上只能靠肉眼发现。窗口没有标题栏可以拖回来。

### 播放页那个按钮的四种走向

`desktopLyricsEntryAction` 也是纯函数，因为四个分支的正确性只有在真机上才看得出来：

1. **没权限**优先于一切（开没开、锁没锁都无所谓，浮窗根本挂不上）⇒ `REQUEST_PERMISSION`，
   调用方**顺手把开关拨到开**（用户按这一下的意图就是「我要用」）。反过来先只开开关、
   让用户回到桌面发现什么都没有，是最容易发生的体验事故。
2. 关着 ⇒ 去开。3. 锁着 ⇒ 解锁（「解除当前障碍」而不是「关掉功能」）。4. 剩下才是关掉。

## 四、权限：第四种「特殊授权」

`SYSTEM_ALERT_WINDOW` 进 `AppPermissions` / `PermissionRules`，新增
`PermissionKind.OVERLAY`。这一项与既有的三项（媒体读取 / 所有文件访问 / 通知 / 蓝牙）不同：

- 它**不是运行时权限**，`requestPermissions` 对它无效，只能跳系统设置页；
- 状态读取走 `Settings.canDrawOverlays(context)`，而这是一个**没有回调**的查询
  （与「所有文件访问」同一类）。所以浮窗宿主在构造时读一次、之后只在
  `onActivityResumed` 重读——用户改完权限必然要从那个页面回来，而我们自己不会在后台被改。
- Manifest 上必须带 `tools:ignore="ProtectedPermissions"`：AAPT 对
  `android.permission.SYSTEM_ALERT_WINDOW` 会报「受保护权限」。这条 ignore 是必须的，
  `PermissionManifestCoverageTest` 会检查「代码里申请的每一项都在 Manifest 里声明」，
  同时 `PermissionRulesTest` 钉住「OVERLAY 不进运行时申请清单」（它申请不了）。

## 五、顺带补的：最近播放页的多选

「最近播放」此前没有多选。收藏要求「媒体库 / 最近播放的多选操作条」，于是这一页补上
与媒体库完全同一套形状：

- 选择集是**界面瞬态**（`rememberSaveable(MEDIA_SELECTION_SAVER)`），有序（点选先后就是
  播放 / 加入播放列表的顺序），进 ViewModel 之前就剪枝（`pruneSelection`，刷新后记录可能少几条）；
- 长按进入多选、返回键退出（`BackHandler` 后注册者优先，必须写在别的 `BackHandler` 之后）；
- 顶栏换成 `SelectionTopBar`（与媒体库/浏览页同一个 composable，含新加的星标）；
- 行的删除按钮**只在非多选时出现**：多选时左边的封面已经换成勾选框，行内再放一个叉号
  会被读成「从选择里去掉这一项」。
- `RecentViewModel` 因此新增 `PlaylistStore` / `FavoriteStore` 两个依赖 + `playlists` /
  `favorites` / `message` 三个输出，`viewModelOf` 自动解析，DI 不用改。

## 八、被否决的方案

| 方案 | 为什么不做 |
| --- | --- |
| 收藏做成底部第六个标签 | 见第二节：底栏是「在哪儿找东西」，收藏是内容；五个标签在 360dp 已是极限 |
| 收藏做成媒体库里的筛选芯片 | 文件夹装不进「媒体库条目」这个概念（它不是媒体），混在筛选里会得到一个「筛出目录行」的列表 |
| 每个列表行加一颗常驻星 | 每行右侧已经有时长 / 删除 / 拖拽把手，再加一颗星会让「点哪里会发生什么」变得拥挤；而收藏不是高频动作，多选一次收藏 20 项更实用 |
| 收藏夹命名 / 分组 | 本版是「一个清单」，分组会把「上限 200」变成「每个分组的上限」，而没有搜索框的分组只是多一层要记的东西 |
| 收藏用 JSON 存 | 见第二节「编解码」：`decode` 绝不能抛 + JVM 单测的 `isReturnDefaultValues` |
| 桌面歌词做成前台 Service | 见第三节：多一条 `FOREGROUND_SERVICE_*` 权限与一条常驻通知，换不到任何东西 |
| 桌面歌词复用 `SubtitleStyle` | 见第三节：两个窗口的默认值/区间/消费方都不同，合起来会让「改字号」同时影响两个界面 |
| 桌面歌词锁定做成「整窗不接收触摸」 | 那样锁上之后就再也解不开——浮窗盖在所有应用上面，用户除了杀进程没别的出路 |
| 桌面歌词用 `ProcessLifecycleOwner` | 要拉 `lifecycle-process` 依赖；这里只需要「有几个 Activity 在 resumed」 |

## 九、已知限制（工程视角）

- **收藏没有搜索 / 排序选项**：一个清单按收藏时间倒序，上限 200。200 条以内靠滚动还可接受，
  再多就需要分组或搜索——那是下一版的事（见 `todo/thinks.txt`）。
- **收藏的文件不做自动失效清理**：文件被删/移走后，收藏页里那一行仍然在，点开会报「找不到
  文件」。删掉它需要用户手动点星标；自动清理要先能可靠地判「文件还在不在」，而那正是
  v1.2.4 修过的那个判断，故意不再叠一层。
- **收藏的文件夹可能打不开**：SAF 授权被撤销 / SD 卡拔出 / 目录改名之后，点开只会得到一句
  「这个文件夹已经打不开了」。本版不试图自动修复（比如退回上一级能打开的位置），
  因为「退到哪一级」没有正确答案。
- **桌面歌词只跟着「当前文件挂载的字幕」**：没有字幕的文件不会有桌面歌词，也不会自己去
  生成字幕；「桌面歌词」不是「桌面歌词搜索服务」。
- **桌面歌词在锁屏时不显示**，浮窗也不会盖在锁屏上（`TYPE_APPLICATION_OVERLAY` 的窗口本来
  就上不了锁屏）。
- **桌面歌词不做跑马灯 / 卡拉 OK 逐字高亮**：它与播放页字幕层共用渲染规则，而字幕层本来就
  不支持逐字效果。加逐字会让两处渲染规则分叉，那是这一版最不想引入的那类不一致。
- **浮窗上的按钮只有四个**（播放/暂停、字小、字大、锁定）：盖在别人应用上的窗口每多一个
  按钮就多一分误触；其余动作（跳转、进度、换字幕）都在播放页里。

## 十、发版核查

按 `docs/release-process.md` 的顺序：改版本号 → 写两份文档 → **先提交、再打 tag** → 编译
→ 归档 → 建 Release。`assembleRelease` 在配置阶段执行 `git describe --tags --always --dirty`，
所以提交与 tag 必须在编译之前，否则包里的抬头会是上一版的 tag 加 `-dirty`。

```powershell
git add -A
git commit -m "feat(v1.3.0): 文件/文件夹收藏 + 桌面歌词"
git tag -a v1.3.0 -m "v1.3.0"
.\gradlew.bat assembleRelease
Get-FileHash dist/MultiSuperPlayer-v1.3.0.apk -Algorithm SHA256
gh release create v1.3.0 dist/MultiSuperPlayer-v1.3.0.apk --latest `
    --title "v1.3.0 收藏与桌面歌词" --notes-file docs/release-notes/v1.3.0.md
```

`versionCode` = `major*10000 + minor*100 + patch` = 10300 > 10204，可直接覆盖安装。

本版进度：提交 `07e3c4d`、tag `v1.3.0`、`assembleRelease`、归档与 sha256 均已完成；
模拟器验收（第十一节）跑完后按验收结论补了一个修复（`9057a70`：从收藏页打开失效目录时
一次性提示从未弹出的问题），**tag 重新打在同一条链的末尾**，APK 也重新编译归档。
推送 `main` 与 `v1.3.0`、以及 `gh release create` 待维护者确认后执行（本地仓库已就绪）。
