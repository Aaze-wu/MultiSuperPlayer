## 一、这一版做了什么

`todo/thinks.txt` 里挂着的两条 v1.4 想法，这一版都做了。两条都很小，但性质完全不同：
一条是**数据**（数出来一个数），一条是**记忆**（记住用户不想再看见什么）。

| 功能 | 入口 | 一句话 |
| --- | --- | --- |
| 文件夹里的项目数量 | 浏览页：每个子文件夹右侧「N 项」，面包屑右侧「共 N 项」 | 不用点进去就知道哪个文件夹是空的 |
| 说明类提示可关闭 | 三处提示条右侧的 ×；恢复在设置页最后一行 | 看过一遍的「怎么用」不必每次都占一行 |

顺带把「恢复所有提示」做成了设置页的**第十行**（原先九行）：它是这一页唯一的写入动作，
其余九行都是「点开一页」。

## 二、数量：为什么不放进 `listing()`

### 数据形状

`BrowserContent.Ready` 新增 `totalCount`，取值是 `listing.entries.size` ——
也就是**未过滤、未截断**的那张原始表，而不是 `arranged.entries.size`。

理由和 `hiddenCount` 完全一样：「显示隐藏文件」开关会过滤、`MAX_ENTRIES_PER_DIRECTORY`
（5000）会截断，用渲染出来的表长度当「这个文件夹里有几项」，等于让两个界面开关
悄悄改掉一个本该是事实的数字。`hiddenCount` 当年已经踩过一次，同一个坑不踩第二次。

### 计数是一条独立的调用

```kotlin
suspend fun count(kind: BrowserSourceKind, ref: String): Int?   // BrowserRepository
suspend fun count(ref: String): Int? = null                     // DirectorySource 默认实现
```

**它不进 `listing()`。** 一个目录里可能有几十个子文件夹，如果列目录时顺手把每个都数一遍，
「打开目录」就会从一瞬间变成好几秒（云盘 provider 一次 `query` 就要几百毫秒）。所以顺序是
「先把表画出来 → 再逐个问 → 问到一个补一个」。代价是数字比列表晚到，这是刻意的取舍：
列表可滚动、可点进另一层，比数字早出现重要。

`FileSystemSource.count()` 直接 `File(dir).list()?.size`，一次系统调用，所以**不设 5000 上限**：
截断规则管的是「界面愿意画多少行」，不该让用户看到被我们编出来的「5000+ 项」。

`SafDocumentSource.count()` 才是真的贵：`resolver.query(childrenUri, arrayOf(COLUMN_DOCUMENT_ID))`
——投影只给一列，因为有的 provider 拿到 5 列投影会把每个子项的元数据全准备好，而这里一个字段都用不上。
顺带把 `list()` 里那段「拆 uri 成 tree + documentId + 拼 children uri」抽成 `locate(ref): Located?`，
`list()` 与 `count()` 共用一份：两处各写一遍，迟早有一次忘了「没有 tree 段就算问不通」那一条。

### `null` 不是 0

`DirectorySource.count()` 的默认实现返回 `null`，所有失败路径也返回 `null`。
界面把 `null` 当「这次不显示数量」，**不写「0 项」**。

这不是洁癖：`0 项` 是一个用户会相信的**断言**，而它对应的实际状态是「授权被撤销 / provider 崩了 / IO 出错」。
用户点进去明明有东西，界面却说这个文件夹是空的——这正是 `BrowserListing.Unreadable` 与
「空目录」分开的那条老规矩，在数量上的第二次应用。

### ViewModel：两张表，一条 `shareIn`

```kotlin
private val snapshot: Flow<BrowseSnapshot> = nav.flatMapLatest { ... }
    .shareIn(viewModelScope, WhileSubscribed(STOP_TIMEOUT_MS), replay = 1)

private val folderCounts: Flow<Map<String, Int>> = snapshot
    .flatMapLatest(::countsOf)
    .scan(emptyMap<String, Int>()) { known, (ref, n) -> known + (ref to n) }
```

三个决定，每个都有具体的失败模式：

1. **`shareIn` 是必须的。** 目录内容同时被 `uiState` 和 `folderCounts` 订阅，冷 flow 被收两次
   就会把同一个目录**列两遍**（云盘上这一下就是好几秒，而且日志里看着像用户连点了两次）。
2. **`BrowseSnapshot` 把 `trail` 和 `content` 绑在一起。** 计数要知道 `ref` 该交给哪种来源，
   而那个答案在 `trail.kind` 上。分成两条 flow 再 `combine`，切目录的瞬间会短暂出现
   「新的 trail + 旧的目录内容」这种并不存在的组合，于是拿新来源去数旧 `ref`。
3. **`scan` 累积成一张表，而不是 `map { it + ... }`。** 一个目录几百个子文件夹时，
   每来一个数就复制一整张表是 O(n²) 次拷贝。表**只增不减**：键是绝对 `ref`，
   换到别的目录之后旧键根本不会被界面查到（界面查的是当前 `entries` 的 `ref`）。

### 界面

- 「共 N 项」和面包屑放**同一 `Row`**（面包屑 `weight(1f)`，数字贴右）。放进 `LazyRow` 里当最后一项
  会变成「深层目录看不到总数」——面包屑本来就横向可滚。
- `totalCount == 0` 时不画：下面已经有一句「这个文件夹是空的」，两个数字叠在一起只是噪音。
- 「N 项」放在箭头**左边**。箭头是「点进去」的方向，必须始终贴在最右侧、位置不变；
  数字长短不影响它，也就不会让不同行之间「点哪里能进去」变得不一致。

## 三、提示：一张白名单，而不是逐处开关

### 分类是按「关掉之后会丢什么」定的

| 类别 | 例子 | 能否关闭 |
| --- | --- | --- |
| 说明类 | 「这里列的是可以开始浏览的位置」「长按条目可拖动排序」「按住右侧把手上下拖动」 | ✅ |
| 警告类 | 缺「所有文件访问」、条目被截断、播放列表里有失效项、随机播放时不能排序 | ❌ |

警告类关掉之后，症状会变成「莫名其妙不能用」——而屏幕上再没有任何东西指向原因。
所以「能不能关」不是逐处 `if`，而是 `HintIds.all` 这一张白名单：

```kotlin
object HintIds {
    const val BROWSE_SOURCES = "browse_sources"
    const val PLAYLIST_DRAG = "playlist_drag"
    const val PLAYER_QUEUE_DRAG = "player_queue_drag"
    val all: Set<String> = setOf(BROWSE_SOURCES, PLAYLIST_DRAG, PLAYER_QUEUE_DRAG)
}
```

`MutablePreferences.dismissHint(id)` 第一句就是 `if (id !in HintIds.all) return`：不在表里的 id
**连写盘都不写**。这样以后新增一条警告时，它天生不可关——不需要谁记得去关掉那个 ×。
反过来，拼错的 id 也不会在一份永远对不上的数据里长住。

**值会写进磁盘，所以改名等于让用户已经关掉的提示重新冒出来**，这一点写在 `HintIds` 的注释里。

### 存储

`HintSettingsRepository` 和 `ThemeSettingsRepository` 同一套写法——同一个 `msp_settings` 文件，
因为第二个 `preferencesDataStore(name = "msp_settings")` 会在运行时报
`There are multiple DataStores active for the same file`。

- 存 `stringSetPreferencesKey("hints.dismissed")`，不是「每条提示一个布尔键」：新增提示时不用改存储结构。
- 键名带版本前缀（`hints.`），因为改键名 = 清空用户已关掉的提示。
- 读盘失败（`IOException`）⇒ 当作「什么都没关过」并记一条 `MspLog.w`。宁可多显示一条提示，
  也不要因为一次 IO 错误让所有说明**永久**消失——后者用户完全没法自己恢复。
- `restoreAll()` 是 `remove(key)` 而不是写空集合：不留一个永久的空键。
- 写入逻辑全是 `internal` 的纯函数扩展（`dismissedHints` / `dismissHint` / `restoreHints`），
  只为了能在 JVM 单测里用 `emptyPreferences()` / `mutablePreferencesOf()` 直接测——
  `core:data` 的单测同样没有真 DataStore 可用。

### 三处接线

| 位置 | 接法 |
| --- | --- |
| 浏览页 | `BrowseUiState.dismissedHints`（跟着 `combine` 的大 StateFlow 走） |
| 播放列表页 | `PlaylistsViewModel.dismissedHints`：**单独一条 `StateFlow`**，不塞进 `uiState` |
| 播放队列面板 | `PlayerViewModel.queueDragHintDismissed: StateFlow<Boolean>`（`map { id in it }`） |

两张不同的接法不是随手写的：浏览页的 `uiState` 本来就是一个大 `combine`，多一路没有额外成本；
而播放列表页与播放页的 `uiState` 各自都很重（前者带 `PlaylistDetail` 与导出/导入状态，
后者带播放位置），为一条布尔值把整页重组一遍不划算。

### 那个「两个条件必须一字不差」的地方

播放列表页的 `LazyColumn` 上面插着「失效提示」和「拖动提示」，数据下标要减掉表头数：

```kotlin
val showDragHint = rows.size > 1 && HintIds.PLAYLIST_DRAG !in dismissedHints
val headerCount = (if (detail.missingCount > 0) 1 else 0) + (if (showDragHint) 1 else 0)
```

`headerCount` 和下面那两个 `if` **必须用同一个布尔值**。两处各写一个条件的话，迟早有一处忘了
加「用户关过提示」这一条，于是拖动排序会错一行——而这个 bug 只在「关过提示 + 两条以上」时出现，
测试数据稍微不巧就永远看不到。

队列面板那边同理，但用的是另一个判据：

```kotlin
val canDismiss = !shuffleEnabled
if (!canDismiss || !dragHintDismissed) { ... }
```

**随机播放那一条不能被关掉**：它说的是「现在为什么拖不动」，关掉之后用户只会得到一个拖不动的列表。

### 设置页第十行

`SettingActionButtonRow`（带按钮的整行，行本身不可点），而不是 `SettingActionRow`：
一个点一下就生效的东西如果整行可点，用户读到一半碰一下屏幕就把状态改了。
副标题按 `dismissedHintCount` 分两句，0 条时 `action = null`（按钮不出现）——
一个按下去什么都不会变的按钮只会让人怀疑自己点漏了。

| 测试 | 钉住的东西 |

`restoreAll` 的删键、`HintIds.all` 的完整性。

## 六、被否决的方案

| 方案 | 为什么不做 |
| --- | --- |
| 把计数塞进 `listing()` | 打开目录要多等 N 次 provider；云盘上一次 `query` 就是几百毫秒 |
| 计数返回 `0` 表示「问不到」 | 「0 项」是用户会相信的断言，而真实状态是「权限没了 / provider 崩了」 |
| 计数用 `entries.size` | 隐藏项过滤与 5000 条截断会让这个数字变小，而它本该描述磁盘 |
| 计数递归（连子里面的都数） | 一个 `Android/` 目录就是几万项，代价与「这层有几个」这个用途不成比例 |
| 计数带缓存 | 缓存要失效策略：文件变了谁知道？现在「重新进一次目录」就是刷新，语义清楚 |
| 每个提示一个布尔键（`hint.browse_sources = true`） | 每加一条提示都要改一次存储结构；`stringSet` 只是加一个 id |
| 可关闭的提示做成「任意 `Banner` 都能关」 | 警告类一旦可关就永久失去线索；白名单是唯一能防住「下一个加提示的人」的做法 |
| 「关掉的提示」存进 `ThemeSettingsRepository` | 那个类在 `core:data` 里已经很大，且主题与提示没有共同的生命周期 |
| 逐条恢复 / 提示管理页 | 一共三条提示，多一层列表反而要用户记「哪条关过」；一次性恢复就够了 |
| 关掉时弹二次确认 | 「关掉」就是不要再看见，确认框本身也是一次打扰；恢复入口固定在设置最后一行 |
| 关掉的通知/成功提示 | 关掉不会丢数据，也不影响任何功能，不需要一条「已关闭」的提示再去点掉 |

## 七、已知限制（工程视角）

- **数量是快照，不实时**：它是「列这个目录的那一刻」的值。要实时得盯盘（`FileObserver` 对
  SAF 无效，`ContentObserver` 只对注册过的 uri 有效），代价远大于这个数字。
- **数量不区分文件与文件夹**：`12 个文件 / 3 个文件夹` 这种拆开显示不做，界面上放不下三个数字。
- **`totalCount` 的默认值取 `entries.size`**：这里留了一个「为旧构造点不报错」的口子。
  目前只有 `of()` 一处构造 `Ready`，所以它不会错；但如果以后有人在别处 `Ready(...)` 手搓，
  拿到的就是一个「按视图算」的总数。KDoc 里写明了这一点。
- **`folderCounts` 是一张只增不减的表**：换目录之后旧键不会清掉。键是绝对 `ref`，
  界面查不到它们所以无害；但如果哪天有人想「导出全部计数」，得先想清楚这张表里有别处的键。
- **计数没有取消逻辑**：`countsOf` 的 `flow {}` 在切目录时会被 `flatMapLatest` 取消，
  但一次 `query` 已经开始就等它跑完。子文件夹很多、provider 很慢时，切目录后再回来会重新数一遍。
- **提示的关闭状态不随备份迁移**：它存在 `msp_settings`（DataStore），不参与「导出播放记录」。
  没有 Android 自动备份的适配（`allowBackup` 行为与系统设置有关，另说）。
- **只能一次性恢复全部提示**：见第六节，这是刻意的。

## 八、发版核查

按 `docs/release-process.md` 的顺序：改版本号 → 写两份文档 → **先提交、再打 tag** → 编译
→ 归档 → 建 Release。`assembleRelease` 在配置阶段执行 `git describe --tags --always --dirty`，
所以提交与 tag 必须在编译之前，否则包里的抬头会是上一版的 tag 加 `-dirty`。

```powershell
git add -A
```
