## 一、随机播放：从「一次洗好的表」换成「每次切歌重洗未播部分」

### 症状（两条其实是一个根因）

1. **一轮播完之后顺序完全复读**：第一轮把整个队列随机走一遍，绕回开头之后第二轮的顺序
   和第一轮一模一样。听第二遍等于把刚才那张歌单再放一次。
2. **中途打开随机，可能被扔回第 1 首**：听到第 7 首才想起来开随机，播放位置会跳。

### 根因

应用**从来没有写过一行 shuffle 代码**，只翻了 Media3 的 `shuffleModeEnabled` 这个开关。
Media3 的行为是：

- 队列建好时（或列表变化时）按当时的长度生成**一张** `ShuffleOrder`；
- 打开 `shuffleModeEnabled` 只是「开始使用这张表」，不会重新洗；
- 走到表尾之后按 `getNextIndex` 的语义**从头绕回去**，绕回去用的还是同一张表。

所以第 1 条是必然结果，第 2 条是因为那张表在整队列范围内随机，第 7 首的位置可能是任意值。

### 改法（路线 b：自己算表，装回 Media3）

没有选择「自己实现一个 `ShuffleOrder` 子类」（路线 a），理由见 §三。

新增 `ShuffleRules`（纯 Kotlin，没有任何 Android / Media3 依赖），三个函数：

```kotlin
internal object ShuffleRules {
    // 从 currentIndex 起步，后面跟 0..length-1 里其余下标的随机排列
    fun orderStartingAt(currentIndex: Int, length: Int, random: Random): IntArray

    // 保留 permutation 里「已播过的那一段前缀」，只重洗「还没播的后缀」
    fun orderAfterAdvance(permutation: IntArray, currentIndex: Int, random: Random): IntArray

    fun isPermutation(values: IntArray): Boolean
}
```

`ExoPlayerController` 里接三处线：

| 时机 | 动作 |
| --- | --- |
| `setShuffleEnabled(true)` | `installShuffleOrderStartingAt(player.currentMediaItemIndex)` —— **从现在这一首起步**，而不是从第 0 首 |
| `onMediaItemTransition`（随机开着） | `reshuffleAfterAdvance(...)` —— 把新位置之后的后缀重新打乱 |
| `setQueue(...)` | 队列长度变了 ⇒ 旧表长度对不上，按当前首重建 |

`installShuffleOrder` 里有一处必须有：**`order.size` 必须恰好等于 `player.mediaItemCount`**。
`ExoPlayerImpl.setShuffleOrder` 会把表长度和 `mediaSourceHolderSnapshots` 的大小做相等断言，
长度不匹配直接抛 `IllegalArgumentException`。所以这一层自己先校验，不满足就放弃这次重排
（保持 Media3 原来那张表），而不是把异常抛到播放循环里。

### 两个容易踩的细节

- **重入**：`player.setShuffleOrder(...)` 是**同步**回调 `onEvents` 的，而我们调它的地方
  已经在 `onMediaItemTransition` 里面 ⇒ 不设防会无限递归。用
  `reshufflingShuffleOrder` 布尔量在 `try / finally` 里挡住。
- **读回来，不缓存**：队列被编辑（增删、移动）时 Media3 会克隆那张表并平移下标，
  缓存一份拷贝必然过期。所以 `currentShufflePermutation()` 是用 `getFirstIndex()` /
  `getNextIndex()` 把当前表**读回来**；读不通（长度对不上、出现越界或重复）时返回 `null`
  而不是返回一张错的表。

### 「已播过的部分永不重排」为什么是硬约束

不是审美问题：`skipToPrevious()` 走的是同一张表。如果每次切歌把整张表重洗，
「上一首」就会落到一首用户**根本没听过**的歌上。所以重洗的范围严格限定在
`currentIndex` 之后的后缀，前缀一个元素都不动。

## 二、「本版更新说明」：只讲本版，并且能读完

### 症状

- 这一页从 1.2.0 起只增不减，每版往里追加，越读越长；用户在「关于」里想知道的是
  「我刚装上的这版改了什么」，不是两年份的变更史。
- 正文长到一定程度，`AlertDialog` 的 `text` 槽会把它自己的「关闭」按钮顶出屏幕，
  只能按返回键退出。

### 改法

**文案**：三套 `msp_settings_about_whats_new_body` 全部重写为
「一句总述 + 5 条要点 + 已知问题 1 段 + 已知限制 1 段」。旧版本的变化交给各版
`docs/release-notes/`，页内一句话指明去处。要点控制在 3~6 条是刻意的：再多就回到
「越读越长」那条老路。

**布局**：`text` 槽换成 `Box { Column(滚动) + 底部淡出遮罩 }`：

```kotlin
val maxBodyHeight = (LocalConfiguration.current.screenHeightDp * 0.78f).dp
val bodyScroll = rememberScrollState()
Box(modifier = Modifier.fillMaxWidth()) {
    Column(
        modifier = Modifier
            .fillMaxWidth()
            .heightIn(max = maxBodyHeight)
            .verticalScroll(bodyScroll),
    ) { Text(...) }

    if (bodyScroll.canScrollForward) {
        Box(
            modifier = Modifier
                .align(Alignment.BottomCenter)
                .fillMaxWidth()
                .height(20.dp)
                .background(
                    Brush.verticalGradient(
                        listOf(Color.Transparent, AlertDialogDefaults.containerColor),
                    ),
                ),
        )
    }
}
```

三个决定都值得记下来：

1. **上限按屏幕高度取比例，不写死**。最早是 `420.dp`（一个「看起来够」的整数），
   实测正好把第 5 条切在半句话上，而屏幕还有余量。改成
   `LocalConfiguration.current.screenHeightDp * f` 之后，小屏自动收、大屏自动放。
2. **`f` 只能到 `0.78`**。实测序列：`0.62` 已知限制整段在视口外；`0.72` 已知限制被切
   半行；`0.78` 中文（1802 px 正文）整段放得下、英文仍要滚 —— 再多，`AlertDialog`
   自己的窗口内边距会把「关闭」挤出去。所以这是上限而不是「尽量大」。
3. **遮罩只加 `background`，不接指针输入**。这一层盖在滚动容器上面，
   一旦它进命中测试，最后 20 dp 就滚不动了 —— 与仓库里既有的「渐变覆盖层不许吃
   指针事件」是同一条规矩。它只在 `canScrollForward` 为真时出现，滚到底自动消失。

遮罩解决的是**观感**而不是容量：正文仍然要滚，但最后一行是淡出而不是被硬切一刀
（硬切看起来像渲染坏了）。中文正文整段放得下 ⇒ `canScrollForward == false` ⇒ 不出现遮罩，
这一条在模拟器上确认过。

## 五、测试怎么盖住

- 全量 `.\gradlew.bat test`：**192 个 suite / 2592 个用例 / 0 失败**
  （v1.4.13 为 191 / 2576，本次 +1 suite、+16 用例，全部来自 `ShuffleRulesTest`）。
- 16 个用例分五组：
  - **置换合法性**：`orderStartingAt` / `orderAfterAdvance` 在各种长度（0/1/2/50）下
    都是 `0..n-1` 的排列，没有重复、没有越界。
  - **起点**：`orderStartingAt(7, …)[0] == 7`。
  - **前缀冻结**：`orderAfterAdvance` 之后，`0..currentIndex` 这一段与输入**逐元素相同**。
  - **后缀确实变了**：50 个随机种子跑下来，「后缀和原来一样」的次数 `< 5`，
    并且能走出的不同路线数 `> 10`。
  - **跨轮边界**（真机验证后补的）：走到表尾时当前项留在表尾、新旧路线一定不同、
    上一轮刚听完的那几首不会在下一轮开头立刻重播、连续 8 轮每轮都播满。
- **断言为什么是这两个不等号而不是 `==`**：5 个元素的后缀只有 `5! = 120` 种排列，
  要求 50 个种子里**一个都不重复**在概率上不成立（约 34% 会至少撞一次，实测撞了 2 次）。
  这里要防的是「后缀压根没被重洗」，不是「两次洗出同一个结果」——后者本来就可能。
  放宽断言没有改任何生产代码。
- **单测盖不住的部分**：`setShuffleOrder` 的同步回调、`mediaItemCount` 的相等断言、
  真机上「第二轮顺序变了」的听感 —— 这些只能在设备上看（见 §六）。所以 `ShuffleRules`
  被刻意做成**不依赖 Media3 的纯函数**，把「能单测的」和「只能实机看的」切开。

### 真机验证时发现并修掉的三个缺陷

第一版实现（只按「重洗未播后缀」写）在设备上**看起来能跑**、单测也全绿，但连听两轮
就暴露了三个问题 —— 三个都不会抛异常、不会打日志，只表现为「随机播放感觉不太随机」：

1. **绕回时把当前这一首跳过去了。** `RepeatMode.ALL` 下播完表尾的下一首是
   `getFirstIndex()`，不是「当前项」。第一版把本轮 leader 放在表**头**，于是绕回时
   正好落到 leader 上 —— 而 leader 就是刚刚那一首，`ExoPlayerImpl` 判定「没变化」⇒
   这一首**被跳过**，每轮实际只播了 n-1 首、下一轮的 leader 还被钉死。
   修法：`currentIndex` 放在新表的**末尾**，绕回目标 = 表头 = 真正的新一轮第一首。
2. **只剩一首未播时重洗是空操作。** `upcoming.size == 1` 时 `shuffle()` 什么也不做，
   新旧表完全相同 ⇒ 调用方按「新旧相同就跳过安装」短路 ⇒ 这一步仍走旧路线。
   修法：这是一轮里最后一格，数学上无解，保留跳过；但**跨轮重洗必须保证结果不同**，
   因此加了「重洗后若与原表逐元素相同，就交换前两位」的兜底（剩两格时重洗有 1/4
   概率恰好洗回原序，不兜底就会整轮失效）。
3. **「刚听完的那几首」取错了窗口。** 想把上轮末尾压到新一轮尾部，第一版取的是
   **表的尾部** —— 那是还没播到的曲目，于是「压到尾部」变成了「把没听过的提前」。
   修法：取 `position` **左边**的 `TRAIL_SIZE = 2` 首 + 当前项。

配套的常量 `TRAIL_SIZE = 2` 是一个刻意的权衡：跨轮边界不要「刚听完又是它」，但再大
就会让新一轮开头几首变得可预测（可选曲目少时随机感明显变弱）。所以**同一轮内**
不会重复，**跨轮边界**允许与最近 2 首中的一首重叠 —— 这是设计，不是遗漏。

**关于「新旧表相同」的诚实说明**：真机日志里仍能看到 `old == new` 的短路，但它们只
出现在「未播部分 ≤ 1 首」的位置（数学上唯一的走法），从未出现在跨轮重洗上。
